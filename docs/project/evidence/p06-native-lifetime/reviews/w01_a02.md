## Findings

1. `__wrap__ZN6vortex9Processor11run_checkedEv` currently records aggregate entries/completions/errors only. It holds the observation mutex and verifies processor identity, then invokes the real `void` function. There is no per-run before/after record and no pending-balance observation. Its 33-success count cannot establish any intermediate reset boundary.
2. `ModelState` captures ownership generation, platform idle/clock/reset, core running, cycles/instructions, and legacy `gp` exitcode. Add the actual processor const pending accessor here; do not infer zero from idle or completion.
3. Each raw `DcrRead` already records a global DCR sequence, completed-run count, before/after clock/reset/idle/running, response bits/status and typed overflow indication. Add actual pending-before/pending-after to this internal record. Keeping the v1 JSON printer's explicit field list unchanged preserves its schema.
4. Destructor handling already follows the correct lifetime structure: capture the live model before the actual real destructor, invoke it exactly once, then inspect only `SimPlatform`, mark completion, clear the saved processor pointer. Never call the pending accessor after that destructor. The final platform clock reset to zero is legitimate disposal behavior, while reset generation must remain unchanged.
5. `run_preflight` executes the unchanged complete warm caller and requires its success, 33 runs, 33 output flushes, four snapshots, 264 MPM replies, exact lifetime counts, and terminal/destructor equality. Its loaded-product and CP checks are useful and should be reused.
6. `p06_managed_preflight_records._split_output` intentionally requires v1 witness to be the final line immediately after `PASSED!`. A supplemental last line therefore requires an explicit new reader; silently modifying the old reader to ignore it would weaken version selection.

Remove exactly that option before passing the unchanged 13 arguments to BOTH the existing `options()` and `p06_unchanged_warm_main()`. Unknown, duplicate or misplaced mode selectors must fail; do not add environment fallbacks. The runner's v2/lifetime path must explicitly include this selector in its pinned argv and execution binding.

On successful opt-in completion, emit the complete original v1 output followed by exactly one `P06_MANAGED_COUNTER_LIFETIME ` JSON line. Give that record an independent contract ID and schema version, e.g. `p06-managed-counter-lifetime-v1`, schema 1. New validation strips only that final line, validates the remaining v1 text through the unchanged verifier, then binds all new observations to the validated witness and warm records. A v1 original fails new validation specifically because its lifetime line is absent, while old replay remains unchanged. This avoids duplicating the application, build graph, or hundreds of lines of original validation.

## Exact successful sequencing

Let `R` be the observed construction/opening reset generation; do not hard-code its current numeric value.

For run ordinal `j` in 1..33: before reset is `R + j - 1`, after reset is `R + j`. Both sides must be owned/live, idle, not running, and have zero pending balance. Exactly one reset is permitted inside the real run. Run outcome is a returned void call, no exception, combined with corresponding successful warm API/event evidence. A nonzero legacy `gp`, including -1, remains valid observation.

The read counts on both sides of the real run are 66 for run 1 and `131 + j` for j >= 2. Flush count on both sides is `j - 1`; the real run may not itself perform another host DCR read or output flush. The matching flush has completed-runs `j`, global DCR sequence 67 for j=1 and `132 + j` otherwise, reset generation `R+j`, pending zero before and after, success status, and no reset. Its ticks may increase. Bind run-after ticks <= flush-before ticks <= flush-after ticks; require the next run-before to preserve that reset and not move clocks backward. Where bound source guarantees no other ticking call between boundaries, equality is stronger; do not assert it without source inspection.

Snapshot reset progression is exactly `[R, R+1, R+33, R+33]`. The after-prime snapshot follows flush 1; after-batch follows flush 33. Terminal snapshot and actual destructor entry must be fully equal (including pending), with no later run/flush/reset/tick. All 264 half reads carry pending zero before and after. This covers the actual terminal counter read path, rather than only its endpoints.

Use globally ordered boundary ordinals only if they are recorded at every compared boundary; paired run counts alone do not order unrelated events. Existing DCR sequence plus explicit run boundary counts provides a smaller sufficient join for this route.

## Failure handling and required controls

- Check nonzero pending before calling real reset-bearing run, so a reset cannot erase the finding. Mark violation/failure and preserve the failed process; never continue into a fresh context and count it as the same valid lifetime.
- Capture typed `PerfCounterError` categories and unexpected exceptions with `completed=false`. Capture available after-state safely, but do not let a secondary observation exception replace the original failure. Preserve normal AsyncRun propagation.
- Never fabricate an integer return from `run_checked()`. Check actual warm API/event status separately. Add a positive nonzero-gp case and a real asynchronous-error rejection case.
- Test trace overflow, missing/duplicate/reordered pairs, per-run reset skip/extra, nonzero pending at every boundary, ownership change, post-terminal work, flush changes and destructor mismatch even after coherently repairing favorable surrounding records.
- Controlled accessor behavior must show nonzero request/reply transitions; an always-zero implementation must fail. Keep this injected test route outside seed-free measurement products.
- Re-run the original v1 archive reader unchanged and prove new lifetime reader rejects it for missing data. Native evidence must be freshly emitted; no reconstructed pending zeros from the historical original.
