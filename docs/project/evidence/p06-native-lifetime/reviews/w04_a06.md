## Environment and resources

The new workflow has the same hosted Ubuntu 22.04 runner, 90-minute job limit,
two build jobs and one simulation worker as the predecessor. It keeps cache
writes disabled. Exact comparison against the starting revision confirms that
`p04_ci_prepare.py` and the predecessor workflow are byte-for-byte unchanged.
A normalized comparison of the two workflow files exposed only the intended
new identities/paths, new trigger entries, additional false lifetime-result
field, selected execution wrapper and separate probe step.

The workflow writes the initial job identity and workflow bytes before rejecting
an insufficient resource observation. Its 15 GiB free-disk and 4 GiB available
memory checks run before cache restoration. The unchanged preparation helper
checks source and workspace free disk and memory again after cache restoration
and host dependency installation. The managed runner checks its source, tools,
work and output paths before execution, and the separate probe checks source,
model build, report directory and output before its compiler/probe commands.
Both executing paths pass the fixed budget into the bounded process supervisor,
which checks disk reserve and bounds process-group RSS/output/time. No new
resource limit was relaxed or replaced by an environment override.

Preparation requires an existing, outside-source workspace, exact source
revision, a fresh destination on the same filesystem and an untracked tools
directory before atomic relocation. It rejects dirty tracked source, unexpected
submodule identities and unrecognized restored source products. The permitted
unused cocogfx product quarantine preserves identities and rechecks cleanliness;
it does not suppress arbitrary source changes. Managed and probe outputs occupy
separate fresh directories under the retained evidence root; the probe selects
the exact `work/simx-fp16` build and its matching managed report.

## Tool/cache identity and limits

The workflow provisions CPython 3.12.14, then verifies CPython/Linux, exact
version and the resolved PATH executable before restoring cache inputs. The
managed runner independently verifies the executing interpreter and the PATH
`python3` hash/size/resolved path. Its subprocess environment starts with that
interpreter's directory and fixed system directories, with explicit bytecode,
cache and worker controls. The probe uses the same workflow-selected `python3`
and independently resolves the host compiler in its clean PATH before comparing
its identity to the selected managed build.

Toolchain restoration is tied to the VERSION tag and resolved 40-character
commit. Preparation accepts only the matching lite/full cache keys. Dependency
cache restoration must match the exact Makefile/.gitmodules digest. Both actions
are `actions/cache/restore@v4`; no save action or whole-toolchain fallback exists.
Cache keys are not represented as fresh dependency compilation provenance:
initial job data keeps that claim false, preparation says actual hashes are
separate, and managed/probe contracts retain the explicit unresolved limitation.
Actual hosted cache availability and native output are not inferred here.

## Failure propagation and retained evidence

Preparation, managed execution and probe invocation use `set -euo pipefail`
and `2>&1 | tee` to retain combined output without replacing a producer's failure
with tee success. The probe is an ordinary subsequent step with no success
suppression or unconditional execution selector. Thus it runs only after
successful managed execution and cannot make a failed matrix pass. A failed
probe itself fails the job. Upload is the final `if: always()` step, includes
hidden retained source metadata, requires evidence to exist, and names the
artifact using source SHA, workflow run ID and attempt.

The initialization record is explicitly `record_stage=job-initialization`, with
native execution not run and result fields false. It is an initial observation,
not a final success receipt. Failed or absent downstream results cannot be
reinterpreted as successful execution from that record. Failure before the
evidence directory exists can make artifact upload fail too; it cannot create a
false pass or native result.

inputs and existing route sources. Governance filters also include the new
workflow, native probe directory and new contract. I found no newly introduced

The job requests only `contents: read`, uses a GitHub-hosted runner, checks out
with `persist-credentials: false`, names no secrets, and introduces neither
`pull_request_target` nor `workflow_run` escalation. No self-hosted runner is
reachable from a fork. The intended new exposure is execution of the reviewed
repository code on a disposable hosted runner with the same read-only cache
access and no shared-cache writes as its predecessor.
