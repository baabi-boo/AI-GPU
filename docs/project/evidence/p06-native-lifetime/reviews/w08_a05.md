## End-to-end findings

### Accessor and real execution

`Processor::pending_mem_reads() const` forwards directly to `ProcessorImpl` and returns the existing `perf_mem_pending_reads_`. That counter already increments for delivered read requests and decrements for delivered replies. The new path neither resets nor advances the model. The pending balance is measured separately from platform idle and core running state; neither is substituted for it.

The existing backend build wraps the real constructor, destructor, `run_checked`, and DCR symbols. The runtime invokes `run_checked()` through its asynchronous execution owner; this checked method returns **void** and lets execution exceptions propagate. The observed signed x3/gp value is architectural state, not a returned success code. Both compiled controls and the separate native probe cover successful gp values 7 and −1.

### Wrappers, failure retention, and terminal ownership

Lifetime mode is enabled once before construction. For each attempted run the wrapper reserves a bounded trace slot, records the actual before-state, and rejects a nonzero pending balance or non-quiescent model **before** the real reset-bearing call. It then requires one exact reset increment and a drained actual after-state. The capacity guard rejects a 34th attempted run before calling the real operation. Checked-counter and other failures remain sticky, and failure-side observation is contained so it cannot replace the original exception.

DCR/flush records capture both pending boundaries and preserve the inherited status/completion/error checks. A nonzero DCR status cannot be admitted merely because the runtime callback otherwise returns a value: the wrapper increments its error accounting and the application's final observation gate rejects it. A failed or null observation, missing operation, trace overflow, read failure, or disposal violation cannot produce an admitted successful process.

The unchanged queue destructor drains and joins its worker before unregistering/releasing its device ownership. The backend destructor joins its asynchronous run before processor member destruction. The application's terminal owner vector requires one remaining device reference, no queues or buffers, and successful command-processor retirement. The lifetime state at actual destructor entry must equal the final live snapshot. After real destruction only the still-live platform is queried; no processor storage is read after its lifetime ends.
