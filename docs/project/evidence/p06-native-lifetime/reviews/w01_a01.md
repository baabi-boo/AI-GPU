## Production route and exact boundaries

- `sim/simx/processor.cpp:201–213`: callbacks on memory-request/reply channels increment cumulative reads/writes, increment pending only for reads, and decrement pending for each reply. `perf_mem_pending_reads_` is a `PerfCounter` at `processor_impl.h:122`, so checked builds detect underflow/overflow already.
- `ProcessorImpl::run()` (`processor.cpp:310`) calls `launch_reset()` once before launch. It ticks until no core runs and the platform is idle; `perf_mem_latency_ += perf_mem_pending_reads_` occurs each run-loop iteration. VM fault early termination is excluded by the bound VM-off route.
- `launch_reset()` (`processor.cpp:382`) calls `reset()` once on the admitted direct-RAM route (`cp_llc_port_ == nullptr`). The LLC route instead calls `reset_launch()` and preserves some inflight work; it must remain excluded.
- `ProcessorImpl::reset()` (`processor.cpp:429`) invokes full `SimPlatform::reset()`, then clears pending balance. The platform (`sim/common/simobject.h:1224–1273`) deletes old events, resets objects, sets clock to zero, and increments `reset_gen_` once. Its existing comment explicitly requires quiescence. Therefore every run's pre-state must observe zero pending and idle before entering the real function, and post-state must show exactly one generation increment. Do not impose globally monotonic platform clocks across resets.
- `ProcessorImpl::flush_caches()` (`processor.cpp:243`) drains caches and may tick; each of the 33 output-download flushes requires before/after pending zero, stable generation, successful reply, and stable owner. Counters can legitimately change during flush. `dcr_read()` at 495 routes flush synchronously.
- `ProcessorImpl::~ProcessorImpl()` (`processor.cpp:231`) finalizes the platform; `Processor::~Processor()` at 565 deletes the implementation. `SimPlatform::finalize()` directly invokes cleanup (`simobject.h:239`), which stops workers, clears objects/events and inflight accounting, and resets clock to zero without incrementing reset generation (`simobject.h:1344`). A clean post-destruction platform is disposal evidence, never repair of an invalid pre-destruction lifetime.
- Backend `vx_device::~vx_device()` (`sw/runtime/simx/vortex.cpp:60`) first joins its `AsyncRun`, then frees host regions. Member destruction later destroys CP, completion owner, Processor and RAM in reverse declaration order. The witness must capture Processor state immediately before its real destructor and read only platform data afterward.

## Safe production API addition

A `uint64_t pending_mem_reads() const` (or similarly clear name) on `ProcessorImpl`, returning only `uint64_t(perf_mem_pending_reads_)`, plus a const delegation from `Processor`, is sufficient. Return by value, never a reference. Keep it independent of diagnostic seed/accessor code, no virtual methods, allocation, tick, reset, flush, source traversal or counter mutation. The `PerfCounter` conversion is const/noexcept (`sim/common/perf_counter.h:58`); ordinary builds use the same underlying uint64 value.

This host-owned observation does not make a SimObject communicate through a foreign object. The host wrapper observes its owned `Processor`; retain existing serialization and document that it is an observation at controlled boundaries, not a concurrent data-race-safe telemetry interface. There is no reason to change runtime completion APIs, timing loops, RTL, or counter arithmetic for this addition.

## Critical semantic constraint: gp is not status

`Processor::run_checked()` (`processor.cpp:622`) returns **void** and discards `ProcessorImpl::run()`'s integer. That integer comes from `Operands::get_exit_code()` (`operands.cpp:178`), which casts warp-0/thread-0 x3 (`gp`) to int. Legitimate startup can put a global-data address there; nonzero and even -1 are valid observations. Record it from post-state, but never require it to equal zero or call it a returned success status.

Actual execution failure is an exception propagated through the void checked call into `AsyncRun`'s future. `AsyncRun::collect()` retains terminal failure and rethrows; backend CP callbacks reject failed completion; public queue/event waits carry that error. Pair normal-return/exception observations with actual upstream wait/API success. Preserve the original exception if post-failure observation itself fails.
