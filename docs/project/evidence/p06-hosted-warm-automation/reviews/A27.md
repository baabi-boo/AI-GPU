# A27 — Composition cancellation boundary

## Change and scope

Added `!cancelled()` to the hosted composition step's existing
`always() && steps.checkout.outcome == 'success'` condition. Ordinary prior
failures still allow failure closeout; an observed cancellation prevents starting
composition and its acquisition/native work. Trusted repository/master, exact-SHA
checkout/governance, setup readiness and native gates are unchanged. Upload retains
its `always()` plus checkout-success and validated `encrypted_retention_ready`
condition, allowing an already validated encrypted artifact to remain eligible.

Extended the two existing parsed-YAML workflow regressions to enforce composition,
setup-readiness and upload boundaries; no new test or surrogate boolean evaluator.
No hosted helper, documentation, dispatch, native execution, commit or ref changes.

## Primary semantics

GitHub's [expression reference](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions#status-check-functions)
documents that status functions override implicit success gating, `always()` stays
true during cancellation, and `!cancelled()` allows ordinary success/failure paths.
The [cancellation reference](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-cancellation)
documents condition reevaluation and eventual forced process termination.
