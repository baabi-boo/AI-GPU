## Finding: exceptional teardown abandons live pooled traces

Confirmed source defect: allocation lifetime is not owned independently of normal pipeline retirement. `Scheduler::schedule()` allocates and placement-constructs a trace (`sim/simx/scheduler.cpp:229–230`); Core only records a raw pointer in `pending_instrs_` (`core.cpp:555–563,1403–1404`). Normal retirement explicitly calls the destructor and returns the allocation (`core.cpp:1215–1219`), as does macro completion (`952–954`). However, `Core::Impl` has no destructor owning outstanding traces, `Core::~Core()` only deletes its implementation (`1505–1506`), and reset merely clears raw-pointer pending tracking (`461`). C++ destruction of a raw-pointer list/channel cannot destroy its pointees.

Each `instr_trace_t` owns dynamically allocated operand vectors and a shared `Instr` (`instr_trace.h:40,47,50,55,92–96`). `PoolAllocator` has an immortal registry and parks per-thread pools after worker exit (`sw/common/mempool.h:139–175`); allocator object destruction neither destroys live traces nor returns their slots. After 64 occupied pool slots, additional allocations use standalone heap blocks (`58–60`), also orphaned unless explicitly deallocated.

The runtime's join is correct but insufficient to release these payloads: `sw/runtime/simx/vortex.cpp:56–62` joins before processor destruction; `ProcessorImpl::~ProcessorImpl()` finalizes the platform (`sim/simx/processor.cpp:231–233`). Platform cleanup clears object/event storage and resets packet accounting (`sim/common/simobject.h:1343–1374`), not raw trace ownership. This permits successful accounting reset/fresh execution while abandoned host allocations persist. Sticky failure and no live failed-context reuse remain valid; no arithmetic or cycle defect is claimed.

**A pending-list destructor alone is insufficient.** Sequencer micro-ops (`sequencer.cpp:108–124`), dispatcher split packets (`dispatcher.cpp:139–140`), LSU response beats (`lsu_unit.cpp:436–442`) and store copies (`495–499`) allocate additional traces outside `pending_instrs_`. Normal store-copy cleanup is separate (`833–834`). Constructor exceptions also require returning raw storage before ownership registration.
