## Confirmed cache/checkout defect and bounded repair

**High confidence; provider logs plus local reproducer.** Both successful regression jobs nevertheless produced this checkout post-cleanup warning:

`fatal: gitfile does not point to a valid repository: third_party/cocogfx/.git`

`git submodule foreach --recursive` returned 128. This is an ancillary cleanup failure, not a regression-test failure.

At the reviewed base, `.github/actions/setup-vortex/action.yml:47–52` caches the entire `third_party` working directory. Its submodule gitfiles point outside that directory into the checkout's root `.git/modules`. A consumer restoring only `third_party` therefore needs its own initialized submodule repositories. The main test checkout at `.github/workflows/ci.yml:260` omits recursive submodules; only P04 has a separate pre-cache initialization step. `.github/workflows/apptainer-ci.yml:76` has the same defective consumer topology.

A tiny **local-only** superproject/submodule fixture reproduced the exact provider error, without downloads, builds, or project edits:

- Fixture root: `/tmp/ai-gpu-b4f42b8a9d4b/a003-cache-repro-_2iorncy`.
- Cached gitfile: `gitdir: ../../.git/modules/third_party/cocogfx`.
- Ordinary clone, then cached working-tree overlay: `git submodule foreach --recursive true` exits **128**, with the exact warning above.
- Trying `git submodule update --init --recursive` **after** that restore also exits **128**.
- Recursive clone **before** the identical overlay: the same `foreach` exits **0**.

The existing fixture permits immediate reproduction with `git -C <fixture>/plain submodule foreach --recursive true` versus `git -C <fixture>/recursive submodule foreach --recursive true`.

**Minimal repair:** add `with: submodules: recursive` to those two consumer checkout steps. Preserve the existing P04 initialization, cache keys, expected-cache identity checks, and source admission. No shared cache-action rewrite is necessary for this defect. A004 owns implementation; A003 made no project-source edits.
