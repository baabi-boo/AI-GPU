## Finding and recommendation

No concrete F2/F3 defect was found in the inspected serial ownership and cleanup implementation. Context reservation precedes native open; operation ownership survives successful wait and is returned only after completed healthy close; the first execution and cleanup failures remain retained; failed cleanup poisons future managed work. A retained operation keeps its context and workspace alive after owner destruction. MLP rejects non-default workspace policy before opening a native context and closes each native operation before advancing. These findings are scoped to the documented single-caller managed interface, not raw runtime clients, separately linked instances or general concurrent native use.

The next harness must preserve that lifetime behavior and must not reuse the correctness observer unchanged:

1. **Observer capacity (high confidence, static proof).** `ai_workspace/observer.h` retains only 16 total buffer-history rows, sufficient for the frozen four-call correctness process. The proposed prime plus 32 calls needs 99 buffer allocations in the reference arm. Its existing overflow path increments observer errors. A new warm observer must freeze a sufficient bounded capacity or use a bounded three-live-buffer structure with separate cumulative accounting; changing correctness coverage is unnecessary.
2. **Policy-dependent observer overhead (high confidence, static proof).** The correctness observer performs before/after memory queries on allocation and release plus an address query at allocation. For each timed reference operation this adds 12 memory-info calls and three address queries, while the resident arm allocates outside the measured interval. This would contaminate an unqualified runtime-only speedup claim. Separate full resource qualification from minimally instrumented timing, or freeze and name the metric as inclusive of exactly this instrumentation. Do not subtract guessed overhead.
3. **Matched treatment (recommendation).** Both policies already coexist in the same compiled runtime. Use the same reviewed source revision and host/kernel binaries with only the policy argument differing; retain that single implementation identity in both arms. This is tighter matching than divergent commits, but needs explicit review of the older draft language before sampling.
4. **Timed interval discipline.** Keep fixture packing, competing-context/operation probes, memory/counter queries, resource checks, trace serialization and stdout outside timing. Use the same boundaries for both policies: immediately before submit through wait, exact output comparison and completed explicit close. Record setup/priming/owner-close separately. Check `ok()` and `complete` together because `ok()` alone intentionally does not mean finished.
5. **Failure handling.** Abort an entire attempt on any failed/incomplete prime or measured operation. Preserve operation ownership until established completion, and retain the first error. Never use a destructor drain or successful later call to turn a timed-out sample into a replacement success. A long-running destructor can need the existing process supervisor to terminate the process group.
6. **Counters.** Existing core and memory counters accumulate across launches in a live context. Use validated pre/post-batch snapshots after priming and after the final operation, with monotonicity and exact scope checks. Existing device-open/close snapshots include prime/setup traffic and cannot stand in for the proposed 32-call measured interval.

These are implementation constraints for the proposed benchmark, not claimed defects in the correctly bounded four-call correctness runner. No gate, tolerance, cold-baseline pin or numerical fixture needs to change.
