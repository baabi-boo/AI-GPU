## Decision

Use **one clean source commit and one executable/kernel/runtime build per format**, with `per_operation` and `reusable_single_tile` selected only through the runtime policy option. The existing runtime already contains both arms. Matching the entire compiled input is stricter than constructing two commits, which adds an unnecessary source/build difference. Bind both arms to identical source tree, build records, generated headers, dependency/tool identities and binary hashes; record the policy separately in every process and operation. The earlier separate-commit wording is in an unfrozen draft and should be revised explicitly before the new measurement contract is frozen.

## Concrete design finding

**F2, high confidence, static proof:** reusing `ai_workspace/observer.cpp` directly for primary timing introduces treatment-dependent native observation work. Each tensor creation and release calls memory-info before and after the real native call; creation additionally queries the buffer address. The default policy therefore receives 12 extra memory-info queries and three extra address queries in each timed operation, while resident buffer setup moves these probes outside operation timing. The existing observer also stores only 16 lifetime records; 33 default operations need 99. Its growing history scan during release would add another sample-order cost if enlarged naively.

Use a dedicated warm observer with three bounded live slots and a fixed 99-entry history (or separately accumulated scalar counts). Wrapper work must only forward the actual create/release and record handle, request bytes, flags, status and phase/sequence in fixed storage; no extra native queries, allocation, formatting, flushing, locks, or scanning over all historical operations in the timed region. Query native memory/capabilities/counters outside operation timing. Qualify allocation reclamation with the separate rich correctness packet. Native wrapper accounting remains included in the reported **instrumented host time**; it is not a clean uninstrumented runtime latency claim. Omission of wrappers would reduce perturbation further, but would leave actual per-process allocation counts inferred from another run, so minimal accounting is the recommended bounded compromise.

## Sampling and timing freeze

- Formats: FP16, then BF16; shape `(8,4,8)`; existing format-specific `single-dense_boundaries` independent fixture and expected FP32 words.
- Each format has paired indices 0 through 5. Index 0 is a fully retained excluded warm-up batch; indices 1–5 are the five independent measured batches.
- Alternate pair order by index, beginning reference-first at index 0. Run both policies serially on the same host/job and build. Do not parallelize arms or formats on shared measurement resources.
- Each process opens exactly one managed context, runs one excluded validated priming operation, captures the batch-begin counters, runs exactly 32 serial validated operations, captures batch-end counters, then closes the owner.
- Total: 24 processes, 792 launches, 25,344 exact FP32 word comparisons. The 20 measured batches contribute 640 measured operations, 20,480 measured word comparisons and 327,680 useful FLOPs.
- Each operation performs identical A/B writes (192 bytes), D poison write (128 bytes), one unchanged native kernel, D download (128 bytes), exact comparison and completed explicit close. Input packing/fixture loading and fixed record allocation happen before timing.
- Timestamp immediately before `submit`; include submit, bounded wait, actual 32-word exact comparison, completed close and successful-result checks. Timestamp immediately afterward. Preserve raw integer `steady_clock` nanoseconds; emit JSON and do heavy trace copying only after the timer. The operation object can be reset outside the timing only after completed close has performed cleanup; require no remaining native cleanup on reset.
- Owner creation/workspace setup, prime, owner teardown, counter-query spans and supervisor process duration are separate observations, never subtracted or added across overlapping intervals.
- Poison and operation order must be defined identically before execution; retain prime separately from operation indices 0–31. A failing prime, any timeout/error, missing result, failed comparison, incomplete close, observer overflow, failed final release, source drift or resource breach invalidates the attempt. No replaced batches or hidden retries.

## Record schema proposal

Use a new schema/contract ID and dedicated markers, never cold `P06_BEGIN/P06_END` parsing implicitly. Process identity binds contract hash, source commit/tree, qualification/build ID, format, policy, paired batch index, warm-up/measured role and sample ID.

A process record contains: 33 ordered operations (one prime +32); operation role/index, fixture ID/hash and poison; raw begin/end timestamps; actual FP32 bits and mismatch count; submit/wait/close status tuples; actual dispatch addresses/extents, 56 argument bytes and write/launch/read counts; minimal allocation-count snapshots; four cumulative native counter snapshots (`after_open`, `after_prime`, `after_batch`, `before_release`); actual owner-close/device-release results; requested live/peak payload counts and final zero-live accounting. Avoid accepting derived summary fields without recomputation.

Use strict exact JSON-key/type/range checks, reject booleans as integers, duplicate keys, nonfinite values, unknown markers, repeated/missing records and incorrect sequence. Bind every raw-log byte count/digest to its supervised command; verify recorded policy matches the exact argv and build binding. Each pair must share all source/tool/build/configuration identities. An analyzer requires every expected process exactly once before reporting a complete matrix.

## Counter feasibility and boundaries

The existing `ai_bench_common/counters.h` inventory can be reused unchanged: 45 descriptors, with 33 available and 12 L2/L3 unavailable entries under the frozen topology. A new benchmark-only observer can borrow the live device handle captured by a device-open wrapper and expose explicit snapshot calls; no installed runtime ABI change is needed.

Static inspection of `sim/simx/core.cpp` shows `perf_stats_` deliberately survives launch reset. `sim/simx/processor.cpp` similarly preserves `perf_mem_*` counters on launch/reset, while resetting transient pending state. Thus after-prime/after-batch cumulative differences are feasible for the inherited selected inventory. `sw/runtime/common/perf.cpp` queries two DCR halves per value; take snapshots only after completed operation close, while no managed operation is live, and retain query begin/end times and every status. Do not reset counters, extrapolate individual-kernel counts or silently infer wraps. Reject any decreasing available reading. This is source evidence; a fresh native multi-launch run still must validate actual monotonicity. Keep unavailable rows null and retain native units/scopes. Unselected cache-port counters known to reset per launch must remain excluded.

## Analysis and decision

Compute each measured batch's arithmetic mean of its 32 operation durations, then min/max/median/population-standard-deviation over five means per arm/format. Keep all individual operation and paired ratio diagnostics. Compute batch active-cycle delta from after-prime to after-batch, dividing by 16,384 useful FLOPs only when required counter queries pass. Freeze acceptance before data: candidate median mean <=95% of reference in both formats, no slower measured paired batch, no increase in each paired measured batch's active cycles, plus all correctness/resource/provenance checks. Five batches support descriptive findings, not a confidence or production-tail claim. A rejected hypothesis is a valid result and does not authorize threshold changes.

The experiment alone cannot close P06-A02/A03: native RTL/applicable inherited gate evidence and reviewed resource/timing obligations remain separate. P01 vendor emulation and the inherited DSP finding are unchanged.
