## Implemented behavior

The new `P06 Warm Workspace` workflow has one `experiment` job on the existing
qualified `ubuntu-22.04` host, with a 90-minute timeout. The coordinator explicitly
confirmed keeping that host version to preserve tool compatibility. There is no
matrix, policy arm job, or concurrent format execution. The job invokes the
full-matrix runner once; the runner owns the frozen FP16-then-BF16 order and all
24 processes on that single host.

The workflow triggers on `master` pushes and ordinary pull requests with the
same 30 positive path filters. They cover the workflow, `ci/project/**` helpers
and fixtures, the new warm application, existing workspace/matmul/TCU callers,
shared counters, runtime/kernel/simulator/RTL inputs, build scripts, dependency
inputs, the frozen profile, and relevant contracts. Manual dispatch exposes no
inputs. Governance gains only the new workflow, warm application directory and
warm contract paths, each in both its push and pull-request filters; its existing
`ci/project/**` trigger already covers the new Python tooling.

Preparation follows the existing workspace workflow: recursive shallow checkout
without persisted credentials; exact CPython 3.12.14 provisioning and retained
interpreter verification; pinned toolchain cache identity; restore-only toolchain
and third-party caches; existing bounded host-dependency installation; and the
unchanged `p04_ci_prepare.py` clean-source/cache/tool/resource checks. The
preparation selector is fixed to SimX and both formats. Missing caches receive
the existing fail-closed preparation behavior, with no toolchain installation
fallback or relaxed validation.

The execution command is fixed:

```bash
python3 ci/project/p06_warm_execute.py run \
  --source-dir "$PWD" --tools-dir "$P06_WARM_ROOT/tools" \
  --work-dir "$P06_WARM_ROOT/work" \
  --output "$P06_WARM_ROOT/evidence/warm-workspace" \
  --jobs 2 --timeout-seconds 1800 --run-timeout-seconds 180
```

`MAKEFLAGS`, `THREADS` and CMake parallelism remain two; ccache is disabled.
The existing preparation and new runner retain the 4 GiB polled process-group
RSS, 15 GiB disk reserve and 16 MiB per-command log limits. Shell pipelines use
`set -euo pipefail` so retaining output cannot mask a failed preparation or
execution. No analysis command is added before its implementation exists.

The artifact is named
`p06-warm-workspace-${sha}-run${run_id}-attempt${run_attempt}` and uploads the
entire evidence directory with `always()`, `include-hidden-files: true`,
30-day retention and missing-file errors. After initialization, this preserves
the raw workflow and its SHA-256, job identity, Python identity, dependency and
preparation logs, execution stdout/stderr, and the runner's full warm packet,
including hidden build stamps and partial/failed execution evidence. `job.json`
is explicitly labeled `record_stage: job-initialization`; its initial
`native_execution: not_run` does not represent the eventual runner outcome.

runner, ordinary `pull_request`, no secrets/OIDC access, no self-hosted labels,
no cache-save action, and no `continue-on-error`. Existing host-dependency
installation retains its `sudo` command inside the ephemeral hosted runner;
there is no new credential or external deployment capability. Cross-run
concurrency is serialized per event/ref without cancelling a running attempt.

policy, including use of the base revision's classifier because `.github/**`
changes make the changed workflow's own classification summary untrusted.
