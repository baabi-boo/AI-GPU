## Implemented behavior

The new runner creates fresh generated RV64 `p02-tfr` build trees for FP16 and
BF16, in that order. One executable/kernel/runtime set per format serves both
policies. A common build binding identifies source, profile, generated headers,
compiler records, tools, dependencies and binary hashes. Each policy process
adds its exact frozen plan row to that common binding; the resulting SHA-256 is
passed to the caller as its qualification ID.

All 24 processes run serially in the contract's alternating paired order, with
no backend/format/policy selection or dirty-source option. The expected result
is 792 launches and 25,344 exact output words; the 20 measured processes contain
640 measured operations. Counts include only fully verified passing processes.
Failures stop the attempt and preserve their command, source/build snapshots
and raw logs; there is no sample replacement or retry loop.

Native builds select `PERF=1` alongside the same format/configuration flags on
runtime and application. The new warm compiler validator checks original
runtime/backend/kernel/host/linker records. Expected backend header macros
explicitly include `PERF_ENABLE=1`; runtime, host and kernel macros do not.
Generated configuration headers are independently reproduced and compiler-role
headers are preprocessed with their retained flags and include paths.

The runner retains every raw log with its command receipt size/digest, source
and build bodies, source/tool/dependency before/after snapshots, common and
per-process bindings, and repeated stability observations. Finalization checks
retained evidence bytes and command logs again. The existing two-job, 4 GiB
polled RSS, 15 GiB free disk, 16 MiB command log, 1,800-second build and
180-second process limits are unchanged.

The process reader API is `verify_output(text, *, case, fmt, policy, binding_id,
sample_id, pair_index, phase, contract)`, returning `operations` and `summary`.
Its independently checked in-process owner lifetime must fit within the
supervised process duration plus the contract's explicit 1,000 ns observation
allowance. This is a containment check, never a correction to reported timing.
The runner records `hypothesis_evaluation: not_evaluated`: a successful complete
execution does not accept the speedup hypothesis or a project phase.
