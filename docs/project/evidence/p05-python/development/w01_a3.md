## Recommendation

Use the proposed CPython C++ extension to own an opaque `ManagedMlp` handle and construct its `MlpCase` exclusively from the already generated, immutable `p04::kFixtures`. Accept one of the ten exact case IDs; never accept expected arrays, arbitrary weights, a fixture path, or caller-set profile verification flags. Keep native C++ unchanged in this first slice.

Reuse `tests/regression/ai_mlp/p04_fixtures.h` and `tests/regression/ai_mlp/records.h` by adding their directory to the extension's build include paths. The built package must retain their source digests in its identity inventory. This avoids a new fixture parser or duplicate serializer. A source distribution can stage verified exact copies during its reviewed build; a built wheel need not import the repository's validation modules at runtime.

One architectural detail matters: `ManagedMlp::create` creates its own `ManagedMatmul` owner (`sw/runtime/ai/mlp_runtime.cpp:122`). It cannot share the existing Python matmul session's C++ owner without changing the native API. A Python session may provide trusted bundle configuration for model creation, but each model handle owns a separate native context. Do not describe this as session allocation reuse. The model itself then owns all three submissions and can survive release of the Python configuration/session object once creation finishes.

## Minimal serialization reuse

For an inspectable diagnostic snapshot, call `p04::records::trace(std::ostream&, const MlpTrace&)` into an `std::ostringstream`, then create an owned Python Unicode/bytes value. This covers every trace field, raw word, status, five-event dispatch profile and observed validity flag. If Python wants a dictionary, decode that owned JSON into a fresh object; no C++ memory view is needed.

For the complete model result envelope, use `p04::write_result` with backend/source/qualification identities from trusted package configuration. It already embeds the compiled model/fixture IDs and fixture SHA, the clock and timing scope. The C++ serializer validates array-prefix extents before reading them (`records.h:193–197`), and preserves uint64 width and JSON booleans. Its fixed hidden/bridge/final arrays can contain placeholders in incomplete traces: retain their validity flags and never present them as successful outputs.

Avoid hand-maintaining a second recursive C++→Python field mapper in the first slice. Keep any new P05 package/bundle/route identity outside the unchanged P04 object, because `p04_execution_records.verify_output` rejects unknown top-level fields. A P05 qualification runner can validate its own route metadata and then feed the unchanged completed model records to that existing strict consumer. Do not use the success-only consumer as a failure-state decoder.

The binding must not synthesize `P04_RESULT` or `PASSED!` for an incomplete or failed model. The serializer is not a success checker: the native application's success policy is separately implemented at `main.cpp:104–124` and `211–218`. Preserve all successful event-query observations, exact five-event order and statuses, profiling enablement, and restored resource baseline. Zeros without `event_profile_queried=true` are not measured timestamps.

`ci/project/p04_execution_records.py:188–257` independently checks the live bridge slices, original W1/W2 bytes, actual output blocks, row assembly, three launch descriptors, alignment/nonaliasing and reconstructed 56-byte arguments. `verify_output` additionally checks identity, two-poison iteration order, strict fields/types, bounded JSON/logs and final success framing. Reuse this independent check rather than weakening it for Python.

## Ownership and result API obligations

A suitable opaque object exposes `advance(timeout_ns)`, `close(timeout_ns)`, a structured result snapshot, and an owned trace snapshot. Creation itself does not launch; the first native submission occurs in `advance`. A convenience fixed-case runner can wrap that owner only after the low-level semantics are tested.

- `MlpResult.terminal` is not drained/completed ownership. Partial submission failure is terminal while `execution.complete` is false; the object must remain alive and available for explicit close.
- `ExecutionResult.ok()` checks codes but does not include completion. Always test `.complete` separately.
- `advance(timeout)` can traverse all three stages and applies the timeout to each wait/drain. Do not document it as a whole-model wall-clock deadline or cancellation.
- A timeout is retryable with the same owner and must not duplicate a launch. Calling `close` irreversibly stops future graph work; it drains, and subsequent `advance` does not resume the graph.
- `hidden_valid` and `logits_valid` mean actual values were observed, not that comparison or cleanup succeeded. `assemble()` sets `logits_valid` before resource checks; owner cleanup can also change an apparently successful result into failure later.
- Publish a successful tensor only after successful complete `close`, `trace.result.ok()`, `trace.owner_closed`, successful complete `trace.owner_cleanup`, and the declared profiling/resource checks. Return an independent 256-byte little-endian FP32-word copy or tuple of 64 uint32 values. That output must survive native close/destruction.
- On error, expose diagnostic actual data with its flags and all separate validation/primary/cleanup/model/bridge codes. A convenience exception must retain the native model owner when incomplete. Serialization/allocation errors must also leave the owner recoverable; do not destroy it while constructing an exception.
- Native destruction drains indefinitely (`mlp_runtime.cpp:96–99`). Explicit close and context-manager behavior must be documented; GC/interpreter teardown cannot promise bounded cancellation.
- Native objects are single-caller. If the extension releases the GIL during `advance`/`close`, keep strong Python references and serialize all owner operations, including trace/result copying. Do not return borrowed references to `model->trace()`.
