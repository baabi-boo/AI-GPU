## Decision

The architecture is compatible with the P05 handoff. The detailed interfaces
resolve most omissions in the initial coordination plan. Two concrete F2
findings were accepted and corrected in the design during this review:

1. Runtime qualification must not trust a mutable Python verification callback.
2. An operation retained after an exceptional submission must remain publicly
   retrievable for bounded recovery.

Implementation can proceed on those corrected interfaces. The accepted
corrections and the lifecycle conditions below must be checked against actual
code and tests before freezing the public API. This is an independent design
review, not a package acceptance, native execution result, maintainer approval,
or waiver.

## Findings and accepted corrections

### A5-F01 — mutable verification callback can manufacture provenance

**Severity F2; confidence high; evidence type reasoned-risk.**

The initial `interfaces.md` proposed that `_native.session_open()` call
`vortex_ai._bundle._verified_config(root, compiled_digest, source_digest)` and
trust the returned module bytes, library paths, format and qualification ID.
Passing an embedded expected digest to this callback does not authenticate its
return value. A caller can replace `_verified_config` with a function returning
an arbitrary dictionary, while the extension subsequently constructs the
attested `ExecutionBinding`. This defeats the intended restriction on
Python-supplied qualifications without requiring a modified native wheel.

Evidence: the qualified-session obligation in
`docs/project/p05-entry-handoff.md` at line 56; `ExecutionBinding` in
`sw/runtime/ai/runtime.h`; `ManagedMatmul::create` in
`sw/runtime/ai/runtime.cpp` at line 308. The native owner accepts attestation
flags and a syntactically valid hexadecimal qualification ID; it intentionally
does not replace the trusted producer's provenance verification.

**Accepted design correction from root:** setup generates a C++ configuration
header containing the immutable manifest digest, trusted metadata and six
artifact relative paths/digests/sizes derived from the validated receipt.
Native session opening reads and SHA-256-checks the manifest and each artifact
itself, with a small internal implementation, then derives backend, format,
source identity, qualification ID and module selection from that compiled
configuration. `_bundle.py` is a producer/build verifier and is not a runtime
authority. The generated pin/header survives the custom sdist stage.

Acceptance conditions:

- Changing `_bundle._verified_config`, Python hash helpers, environment-supplied
  qualification strings, or returned `build_info()` dictionaries cannot select
  a different native qualification.
- Missing, modified, wrong-sized, extra/escaped or disallowed symlink artifacts
  fail before the affected executable artifact is loaded; the runtime loader
  checks the actual loaded identities, as specified in `interfaces.md`.
- A wheel reconstructed from the sdist retains the same trust boundary and
  cannot silently become a bound production wheel through an unchecked flag.
- Keep the existing trusted-build scope. This is not a claim of protection from
  a malicious compiler, modified native extension, or arbitrary process-memory
  corruption.

Status: **resolved in design; implementation and tests not yet reviewed.**

### A5-F02 — retained exceptional submissions need a public recovery path

**Severity F2; confidence high; evidence type reasoned-risk.**

The detailed interfaces correctly preallocate the Python operation and capsule
and put the operation in a session registry before native submission. They also
retain the owner when Python status serialization fails. However, the initial
public API had no way to obtain that retained operation if `submit()` raised
`MemoryError` or was interrupted before returning it, and constructing an
exception with `.operation` also failed. `Session.close()` explicitly does not
drain arbitrary pending work. The session could therefore remain incomplete
with no public bounded way to retrieve and close the operation that keeps it
alive. Retention prevents premature release but does not by itself provide
recoverability.

Evidence: `interfaces.md` registry and serialization-failure rules;
`docs/project/p05-entry-handoff.md` at lines 61 and 82;
`ManagedMatmul::submit` at `sw/runtime/ai/runtime.cpp:361`, which can return an
owned operation even when its primary status is an error; and
`ManagedMatmul::close` at line 422, which returns incomplete while the context
is shared.

**Accepted design correction from root:** add
`Session.pending_operations()` returning an immutable tuple of the actual
pending operation/model owners. All owners enter the registry before native
submission, so a failed status/exception allocation does not hide them.

Acceptance conditions:

- Inject an allocation failure after a native partial submission and before the
  Python return/status is published. After memory pressure ends, the caller can
  retrieve the same owner from `pending_operations()`, wait/close it, and then
  close the session.
- Exercise the equivalent interruption window with SIGINT in a subprocess;
  retain the native operation and original first-error/cleanup information.
- The returned tuple does not expose the mutable registry. Taking a snapshot
  retains real owners; deleting the session does not invalidate them.
- Remove an entry only after completed explicit close. A failed close that is
  still incomplete must remain discoverable; a terminal cleanup failure must
  remain inspectable on the retrieved operation after removal.
- Include model owners, which have their own `ManagedMlp` context, in the same
  public recovery inventory.

Status: **resolved in design; implementation and tests not yet reviewed.**

## Remaining lifecycle decisions to make explicit during implementation

### A5-F03 — post-fork rejection must also cover destruction

**Severity F2; confidence high; evidence type reasoned-risk.**

`interfaces.md` says every native entry rejects use in a post-fork child, but
also says destructors retain the inherited infinite-drain behavior. A capsule
destructor is an additional native entry in practice. On Linux, fork a process
while an operation is pending, then drop its capsule or exit normally in the
child: invoking the unchanged native destructor can wait forever for work whose
runtime worker threads existed only in the parent. Rejecting `wait()` and
`close()` does not prevent this destruction path.

Evidence: `MatmulOperation::~MatmulOperation` at
`sw/runtime/ai/runtime.cpp:442`; `ManagedMlp::~ManagedMlp` at
`sw/runtime/ai/mlp_runtime.cpp:96`; the interface's post-fork restriction.

Required disposition: record the creating PID and make the guard apply before
**every** native touch, including capsule destruction, finalization and loader
cleanup. In an unsupported fork child, deliberately abandon inherited native
ownership until process teardown rather than calling its drain/release methods;
the parent's independent copy remains responsible for its own resources.
Document that child execution requires exec/spawn and a fresh session. A
subprocess test must prove both explicit calls and ordinary destruction reject
or finish without entering inherited waits. This changes Python wrapper
ownership policy, not the unchanged native destructors.

### A5-F04 — complete the public error and interruption mapping

**Severity F2; confidence high; evidence type reasoned-risk.**

The interfaces define `BindingError`, native status fields and bounded numeric
wait inputs, but do not yet freeze which public failures are Python type/value
errors, qualification errors, timeout outcomes, numerical failures or
`KeyboardInterrupt`. Without this table, identical invalid dtype/shape/length
requests can behave differently in `Tensor`, `Session.submit` and the directly
callable extension, and an interrupted call can conceal whether native work
advanced before control returned.

Required disposition:

- Publish one versioned table for wrong Python types, malformed metadata,
  unsupported dtype/shape/layout/profile, exact-extent failure, integer
  overflow, unavailable bundle/runtime, primary native error, incomplete work,
  model mismatch and terminal cleanup error. State which failures occur before
  any submission and preserve all available underlying native codes.
- State that `timeout_ns` is an exact non-bool integer in
  `0..1_000_000_000`, with zero polling and no implicit seconds conversion.
  The MLP timeout applies per native wait/drain, not to the entire `advance()`
  or host work. A one-second argument is not a one-second model deadline.
- State when pending Python signals are observed while the GIL remains held.
  Store native outcomes/ownership before any signal check or Python allocation
  that can abort publication. An interrupt is not cancellation and the pending
  registry is the recovery path when the call has not returned its owner.
- Test context exits both with and without an existing body exception,
  including `KeyboardInterrupt`: one bounded close, preserved incomplete owner,
  and the original body exception retained as the cause of any cleanup error.

Evidence: the error/release/timeout requirements at
`docs/project/p05-entry-handoff.md:83`; `ExecutionResult::ok` in
`sw/runtime/ai/runtime.h`; `ManagedMlp::advance` at
`sw/runtime/ai/mlp_runtime.cpp:341`.

### A5-F05 — GIL retention is not a complete reentrancy policy

**Severity F1; confidence medium; evidence type reasoned-risk.**

The GIL prevents ordinary concurrent Python threads from entering the native
methods simultaneously. It does not define same-thread reentrancy from an
accepted buffer exporter, metadata conversion or signal handler. The native
owners are single-caller objects. In particular, a callback that closes a
session while another entry is obtaining buffer storage must not invalidate a
cached owner pointer before submission.

Disposition: either apply exact built-in type restrictions at the extension
boundary as well as the Python facade, leaving no caller callbacks in an active
native critical section, or use per-owner nonblocking busy guards and reject
reentrant calls explicitly. Keep the owner and buffer exports strongly alive
through copying. Do not implement a blocking lock that deadlocks on same-thread
reentry. Revisit this policy if waits later release the GIL.

## Obligations already resolved by the detailed interface

These are acceptance assertions, not additional open findings.

| Boundary | Frozen behavior and essential check |
|---|---|
| Bytes | `Tensor` accepts bytes/bytearray/memoryview storage with one dimension, item size one, positive contiguous byte stride and exact length. Preserve an exporter reference/export until synchronous native copying finishes. Read-only input is valid. Never infer byte order from a host numeric dtype. |
| Logical rank versus storage rank | A flat byte exporter is storage for a logical rank-two tensor. Do not reject it because its buffer rank is one, and do not infer the matrix rank or layout from an arbitrary multidimensional exporter. |
| Shape/layout | A is `(M,K)` row-major with byte strides `(2*K,2)`; B is `(K,N)` column-major with strides `(2,2*K)`. Reject mixed dtypes, mismatched K, padding, noncompact strides, zero/negative/bool dimensions and unsupported tuples before dispatch. Raw bytes assert a layout; there is no way to detect a caller who has already packed the wrong mathematical order into otherwise valid bytes. |
| Addressing | Host buffer alignment/offset is not a device address or allocation identity. Native allocations own device alignment and disjointness. Host A/B storage overlap is harmless when each is copied into separate native allocation; do not confuse it with forbidden device-range aliasing. |
| Inputs after submit | The native owner copies A/B before submission returns. Later mutation, resize where permitted, release of exporters, or deletion of `Tensor` cannot change queued input. Revalidate actual extents at submission, since a bytearray can change after `Tensor` construction. |
| Partial failure | `Session.submit` returns an operation even for a native submission failure; validation/type failures before native work may raise. A native error is not evidence that no command was queued. |
| Status | `ExecutionStatus.ok` includes `complete`. Retain validation, primary and cleanup separately. Retryable timeout snapshots must not become a sticky primary error. Terminal cleanup errors must remain sticky even though a second native session close returns a default success after its context was reset. |
| Results | Return independent little-endian row-major FP32 bytes and unsigned raw-word tuples. Require successful completed native work, correct output count, and successful cleanup when the API requires it. Do not convert to host-native-endian memory or Python floats as a substitute for exact bits. Results survive close. |
| Model outcome | Preserve `MlpStatus`, `terminal`, execution status and trace validity separately. `ManagedMlp::close` can drain successfully while marking an unfinished model `closed`; `execution.complete && execution.ok()` alone does not establish model success. The specified model output gate also requires owner close and resource/cleanup success. |
| Context ownership | An operation may outlive its session. The loader's no-unloading process lifetime keeps forwarding pointers valid. One process remains permanently bound to its selected variant even after all sessions close; changing FP16/BF16 or backend requires a separate process. |
| Model trust | Select only the compiled frozen case IDs with matching bundle dtype. No caller reference arrays. Emit the actual three native stages and existing P04 record schema; a diagnostic valid array is not proof it matched its reference. |
| Framework scope | No NumPy dtype adapter, PyTorch route, autograd, generic model weights or broader P05 completion claim is part of this first slice. |

The exact size matrix for either accepted input format is:

| `(M,N,K)` | A bytes | B bytes | D bytes / FP32 words |
|---|---:|---:|---:|
| `(8,4,8)` | 128 | 64 | 128 / 32 |
| `(8,4,16)` | 256 | 128 | 128 / 32 |
| `(16,8,16)` | 512 | 256 | 512 / 128 |

These sizes follow the unchanged operator manifest and the explicit
little-endian representation. They do not broaden the six accepted signatures.
