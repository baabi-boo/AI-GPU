## Reviewed invariants

1. SimX Process initialization/finalization uses the global SimPlatform. A second live native device context must be rejected before vx_device_open.
2. ManagedMatmul and its MatmulOperations share RuntimeContext. A complete successful wait does not drop the operation's native reference; explicit close or destruction does.
3. A matmul operation may outlive its Python Session. Its independent shared lease must outlive the session too.
4. Creating a model first closes an idle session matmul owner, then gives a distinct model owner the lease. An incomplete matmul close must leave the original context and lease intact.
5. A suspended session may resume lazily only after the model releases its lease; another open session competes for that same processwide lease.
6. Native resources drain before the lease drops. The lease member is declared before the native unique_ptr, so C++ reverse member destruction preserves that order.
7. Both explicit and destructor-driven cleanup failures permanently block additional native contexts/work in that process. Existing owners can still close.
8. Failed native creation releases its temporary lease and preserves primary/cleanup status. A failed creation with cleanup failure poisons later work.
9. Python allocation failure after successful submit/model creation does not discard the preallocated native owner or its lease.
10. Post-fork capsule destruction must orphan native pointers and avoid native wait/release. The child's copied empty lease bookkeeping can safely destruct; supported_context rejects later inherited-runtime reuse.

Session.close during an independently owned model was reviewed explicitly. Returning success for the suspended session is consistent with closing only that session owner; it must not close the model. The model continues owning the process lease until its own close/destructor. This behavior passed and should be stated clearly in the public contract.

## Findings delivered and fixed by root

### F2, high confidence, static proof — destructor cleanup bypassed process poison

Initial lease patch called remember_cleanup only on explicit operations. Deleting an idle session with a failed kernel/module/device release, or deleting the last orphan operation/model with a release failure, allowed the global lease to expire without recording the failure. A later Session.open could then create a native context despite the intended fail-closed policy.

Root added owner-specific destruction:

- SessionOwner observes native.close before native member destruction.
- OperationOwner and ModelOwner drain using repeated native.close(VX_TIMEOUT_INFINITE), recording cleanup and retrying incomplete drains.
- Fork paths first release the native unique_ptr without destruction, so those wrapper destructors skip native calls.

Validation: destructor failures were injected for all session kernel/module/device releases; orphan operation event/queue/buffer/device releases; and model event/device releases. Every case rejected later native opening without an additional vx_device_open call, and no fake resources remained.

### F2, high confidence, static proof — failed lazy resume lost the primary memory_info error

session_memory_info lazily resumed a suspended session. When ManagedMatmul::create failed, it stored the actual creation result but returned VX_ERR_INVALID_HANDLE merely because owner.native was null. This replaced the real failure with a secondary symptom.

Root changed the null-native path to report the stored primary error, or cleanup error, before invalid-handle fallback.

Validation: a get_kernel failure with primary code 6 after a model closed propagated as code 6 from Session.memory_info; Session.close retained the same failure. A subsequent independent session could open when cleanup had succeeded.
