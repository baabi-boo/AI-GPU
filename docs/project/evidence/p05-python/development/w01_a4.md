A short `setup.py` should declare `Extension("vortex_ai._native", ...)` with relative source paths:

```python
sources = [
    "python/native/module.cpp",
    "python/native/vortex_shim.cpp",
    "sw/runtime/ai/contract.cpp",

    "sw/common", "tests/regression/ai_mlp",

```

Set `language="c++"`, compile with C++17 and `-pthread`, link with `-pthread` and `libraries=["dl"]`, and use hidden default symbol visibility (`-fvisibility=hidden`). List the actual headers, including `build_identity.h`, in `depends` so ordinary incremental builds notice identity/header changes. A new pin must not reuse old objects; release builds always use a clean staged source tree. GCC optimization/debug/warning choices should be recorded rather than inherited invisibly from an uncontrolled environment.

Do not link `vortex` or `vortex2`, specify repository/native `library_dirs`, set absolute native RPATHs, or expose existing C++ object layout as Python's ABI. Linux extensions intentionally leave CPython API symbols to the interpreter; blindly adding `-Wl,-z,defs` will reject those legitimate unresolved Python symbols. Hide shim `vx_*` definitions from the dynamic export table so they cannot interpose on the real library and recursively call themselves. `PyMODINIT_FUNC` supplies the required exported `PyInit__native`.

The wheel should contain Python files, the compiled extension, any narrowly declared package metadata, and `.dist-info` metadata including the Apache license. Native owner sources and fixtures are sdist build inputs, not necessary wheel data if compiled into the extension. Expected local tag is `cp312-cp312-linux_x86_64`, not `py3-none-any` or `abi3`. A wheel tagged merely `linux_x86_64` must retain the exact tested host runtime requirements in its compatibility record; no portability claim is earned by renaming it.

Never import `vortex_ai` from `setup.py` to obtain the version. Use static project metadata, standard-library path/hash operations for build assertions, and setuptools only. Do not invoke Git, make, configure, fixture producers, network clients, native `dlopen`, or GPU discovery during metadata generation or package build.

## Bundle pin and loader requirements relevant to packaging

1. **Freeze the pin as a build input.** Prefer a producer-written `build_identity.h` plus exact pinned manifest metadata in the staged source distribution. The sdist must retain everything needed to reproduce the same compiled pin. Ordinary `pip wheel` from the sdist must not need an external bundle directory, working Git checkout, or caller-provided digest environment variable. The producer can require external qualified artifacts when preparing a release, but that is a distinct operation from rebuilding an already prepared sdist.
2. **Digest bytes, then parse.** Pin the SHA-256 of the exact manifest bytes, not an unspecified JSON reserialization. Validate the pinned manifest, its relative artifact paths and every named native file's digest before constructing `ExecutionBinding`. An arbitrary caller string or boolean cannot override the pin.
3. **One manifest can cover several frozen variants.** If FP16 and BF16 share one release manifest, compile that one digest and allow only a declared variant key. If each variant has a separate manifest, each wheel needs a distinct identity; do not produce different wheels with identical name/version/tags and silently overwrite them. Exactly one selected variant remains process-wide, including after sessions close.
4. **Import remains independent.** `import vortex_ai`, metadata inspection, and importing the extension should succeed without an external bundle and must not load `libvortex.so`. Missing bundle errors belong to the explicit session/load operation. No compiler, make, installer, native backend, network, or filesystem writes during import.
5. **Absolute `libvortex.so` loading alone is insufficient.** `sw/runtime/stub/vortex.cpp` reads `VORTEX_DRIVER` and calls `dlopen("libvortex-" + driver + ".so", RTLD_LAZY)` on first device open; it caches the backend globally. `sw/runtime/stub/Makefile` gives `libvortex.so` an `$ORIGIN` search path. Runtime/backend identity therefore needs trusted launch configuration, absolute verified preloading and/or verification of actual loaded paths. Reject conflicting preload/search-path/native-library state. Changing `LD_LIBRARY_PATH` inside Python is not a robust selection mechanism.
6. **Respect existing backend symbol needs.** The stub Makefile states backends resolve VMManager/common symbols from `libvortex.so`. A simplistic `RTLD_LOCAL` plan may fail; loader qualification must determine the necessary visibility/order and verify identities. Do not claim that a manifest hash makes a writable bundle or a hostile process immutable. Keep library handles alive for the process, because managed operations can outlive session owners and native globals cache their backend.

The managed runtime currently references exactly these 20 C entry points, which bound the initial shim: `vx_buffer_address`, `vx_buffer_create`, `vx_buffer_release`, `vx_device_memory_info`, `vx_device_open`, `vx_device_query`, `vx_device_release`, `vx_enqueue_launch`, `vx_enqueue_read`, `vx_enqueue_write`, `vx_event_get_profiling`, `vx_event_get_value`, `vx_event_release`, `vx_event_wait_value`, `vx_kernel_release`, `vx_module_get_kernel`, `vx_module_load_bytes`, `vx_module_release`, `vx_queue_create`, `vx_queue_release`. Add only any further symbols explicitly required by binding error/diagnostic code. Resolve all required entries eagerly and report missing symbols before native owner creation.

## Practical offline artifact test

This is the recommended procedure, **not a test executed by this audit**. It uses the installed backend/frontend and needs neither the `build` module nor pytest. Packaging checks run in fresh staging directories, not by building in the source checkout. Native numerical executions still follow configured-build-tree rules and use external qualified artifacts.

1. Copy only the reviewed sdist allowlist into a fresh stage outside the checkout; record its file hashes. Include no `.git`, native bundle, previously built extension or `egg-info`. This prevents setuptools state from a previous build from masking missing inputs.
2. From that stage, invoke the public PEP 517 backend directly to build the sdist. The direct hook is useful because `python -m build` is unavailable:

```sh
python3.12 -c 'from setuptools.build_meta import build_sdist; print(build_sdist("/absolute/p05-package-test/dist"))'
```

3. Inspect the tar member list for the required files and forbidden paths; extract to a second empty directory and hide/remove the first staging directory from the test's reachable build inputs. Validate that the archive is self-contained. Build the wheel from the unpacked sdist using the already-installed build dependencies:

```sh
python3.12 -m pip --isolated wheel --no-index --no-deps \
  --no-build-isolation --no-cache-dir \
  --wheel-dir /absolute/p05-package-test/wheelhouse \
  /absolute/p05-package-test/unpacked/vortex_ai-0.1.0.dev0
```

`--no-build-isolation` deliberately uses the inventoried local backend versions; without it pip normally creates an isolated environment and attempts to install build requirements. `--no-index` blocks index access; the declared project must contain no direct-URL requirements or custom fetching hooks. Record the exact offline commands and output. A release claiming isolated offline *build-dependency provisioning* additionally needs local wheels for every locked build dependency; those wheel artifacts have not been located or provisioned in this audit.

4. Make a clean runtime venv with no global packages and no pip bootstrap, then use host pip's target-interpreter facility to install only the built wheel:

```sh
python3.12 -m venv --without-pip /absolute/p05-package-test/venv
python3.12 -m pip --isolated \
  --python /absolute/p05-package-test/venv/bin/python \
  install --no-index --no-deps --no-cache-dir \
  /absolute/p05-package-test/wheelhouse/EXACT_BUILT_WHEEL.whl
```

Use the actual generated wheel filename rather than a guessed tag. Run the install smoke script by absolute path from an empty working directory, with `PYTHONPATH`, `PYTHONHOME`, `LD_LIBRARY_PATH`, `LD_PRELOAD`, and native backend configuration absent, and interpreter `-I`. Assert that `vortex_ai.__file__` and `_native.__file__` resolve under the new venv; global NumPy/torch/pytest are unavailable; package metadata has no runtime `Requires-Dist`; the compiled pin and source identity match release records; import loads no native bundle library and spawns no process; and an explicit session call gives an actionable missing-bundle error. The clean import must succeed without native prerequisites.

5. Inspect the wheel zip and extension ELF with `zipfile`, `readelf -d`, `readelf --dyn-syms` or `nm -D`. Confirm no `DT_NEEDED` entry for libvortex, no checkout/native build RPATH/RUNPATH, no exported shim `vx_*`, expected CPython extension tag, Apache license inclusion, and only intended package files. Record dynamic libc/libstdc++/libgcc requirements as host prerequisites, not Python dependencies.
6. In fresh subprocesses, repeat with one relocated, verified real bundle variant at a time. Test correct load, wrong manifest, mutated module/library, missing backend/dependency, wrong profile/dtype, absent required symbol, and attempted variant switching. Full matched-run smoke must compare actual results and traces with the independent native path. Fault-injected local libraries can test loader/error behavior but cannot satisfy native numerical evidence.
7. Retain source/headers and fixture hashes, sdist/wheel SHA-256, tar/zip membership, build logs, exact dependency/compiler inventory, installed metadata, isolated smoke output, and native loaded-path records. These are separate from future PyTorch P05-A02 evidence.

## Remaining decisions / risks for root

- Decide whether one pin covers FP16/BF16 variants or each gets a uniquely identified wheel; the proposed one-manifest/multiple-variant approach avoids package collision while enforcing process-level selection.
- Ensure the bundle producer and sdist builder are distinct. Requiring external manifest input every time `setup.py` runs makes the advertised sdist non-self-contained.
- Explicitly test import on a machine/environment without native artifacts. Directly linking libvortex makes missing native dependencies break import and bypasses lazy validation.
- Keep fake loader/test artifacts outside the production pin and production distribution.
- No PyTorch dependency or framework compatibility claim is justified by the current environment. A plain-Python package smoke does not close all P05 gates.
