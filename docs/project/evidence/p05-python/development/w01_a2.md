# W01 A02 — Executable provenance and Python package boundary audit

## Scope and recommendation

Read-only audit of `AI-GPU` at `6aac9c421180805a5621156e3d914c685fc6f4a5` (initial working tree clean). Read `AGENTS.md`, current status/roadmap/backlog/acceptance, P05 entry handoff/phase, P03/P04 execution runners, compiler/source inventory helpers, managed runtime creation, dispatcher and relevant Makefiles. No source edits, native builds, commits, pushes, or delegated agents. This report is the only written artifact.

**Recommended bounded implementation:** Linux CPython C-API C++17 extension, copying native owners, no new binding library; an external qualified native bundle paired with the wheel by a **compile-time SHA-256 of the complete canonical bundle receipt**; a small `dlopen`/function-table shim; fresh sanitized process, one complete backend/format/bundle variant per process. Public constructors select the installed/pinned bundle (or its relocated directory), never accept verification flags, qualification IDs, a user-chosen expected digest, or arbitrary module bytes. Frozen P04 cases remain internal. This is an implementation slice, not full P05 acceptance or PyTorch support.

The compile-time receipt pin is necessary: a JSON receipt whose only checks are internally consistent hashes and plausible source/profile strings can be fabricated alongside arbitrary executable bytes. The reviewed producer plus installed extension's immutable pin establishes the trust boundary. This is integrity/provenance binding under the existing trusted-package/trusted-builder threat model, not cryptographic authentication of hostile hardware or of a Python process controlled through arbitrary native code.

## Findings grounded in current source

### The native API trusts the runner

- `sw/runtime/ai/contract.h`, `ProfileBinding`, contains `verified_kernel_profile` and `verified_device_profile`; neither is an observation of a binary.
- `sw/runtime/ai/runtime.h`, `ExecutionBinding`, explicitly delegates image/backend/compiler verification to a trusted runner.
- `sw/runtime/ai/runtime.cpp`, `qualified_id` and `ManagedMatmul::create`, check only a 64-character hexadecimal ID, minimum image size, the two booleans and selected enum, then query runtime geometry and load the supplied image. Geometry/ISA capability queries cannot distinguish TFR/STD arithmetic from a different implementation with matching advertised capabilities.
- `tests/regression/ai_matmul/main.cpp` and `tests/regression/ai_mlp/main.cpp` set `{p02_tfr_wmma_v1, true, true}` based on the trusted-runner convention. These executables are independent comparison paths, not standalone provenance authenticators.
- `sw/common/ai_matmul_profile.h` enforces accepted compile-time geometry/arithmetic/feature exclusions and input/output type selectors. Preserve it in the extension build validation; do not replace it with a runtime enum check.

**Consequence:** exposing the native fields through Python, making `_create(module, qualification_id)` merely private, or validating a plausible SHA string does not meet the handoff. Construct `ExecutionBinding` only after the extension's verification boundary succeeds. Even direct use of the low-level extension must not bypass verification.

### Existing runners provide the producer pattern

`ci/project/p03_execute.py` and `ci/project/p04_execute.py` perform these independent checks:

1. Source/helper inventory at import and before execution; clean checkout and initialized pinned submodules for formal runs.
2. Exact frozen profile SHA; fixture loader and, for P04, regeneration of the checked fixture header.
3. Tool and dependency byte inventories, fresh generated build, configure identity, copied recipe identity and regenerated C++/Verilog headers.
4. Separate runtime, backend, kernel, host and linker records via `p03_execution_records.validate_records`; backend effective-header preprocessing.
5. SHA/size inventories of executable/module/runtime/backend artifacts; `qualification_id = SHA256(canonical binding JSON)`.
6. Hash stability immediately before/after launches and source/tool/dependency stability at the end.

`p04_execute.artifacts` identifies the relevant generated files, native app, ELF/VXBIN, kernel archive and three Vortex libraries. `p04_execute.execute` adds the frozen fixture hash/model ID to its binding and calls the independent output consumer. The new package producer should reuse these checks, not invent a reduced parallel interpretation of profile flags.

`ci/project/compiler_records.py` deliberately parses inert text, rejects shell expansion and unknown operands, preserves record boundaries and checks direct kernel ISA/ABI. `ci/project/p02_matrix_records.py::_record` applies frozen profile requirements independently to each role; `p03_execution_records.validate_records` enforces the exact native linker binding. The generic `compiler_records.validate_records` is the P01 vendor contract, **not** the complete P03/P04 profile validator.

`ci/project/baseline_inventory.py::_digest` checks regular-file identity and read-time size/mtime/ctime stability. `hash_artifacts` checks relative unique contained paths and file hashes. It allows symlinks whose resolved targets remain inside the root; a new bundle contract must explicitly choose whether to allow these, rather than assume it rejects every symlink. `collect_source` observes Git commit/tree, dirty state, pin inventory and submodules. `p03_execute.source_snapshot` adds dependency headers missed by the older broad source suffix selection. Retain that expanded source/helper closure in producer evidence.

The compiler-record documentation expressly limits hashes: they detect drift but do not prove stamp honesty, binary derivation, interpreter integrity or loaded Python bytecode. A source tree and matching stamps adjacent to a binary are insufficient without a trusted build observation.

### Loader behavior constrains the public contract

`sw/runtime/stub/vortex.cpp::dispatcher_get_callbacks` caches `g_backend_lib` and `g_backend_cb` process-wide, chooses `VORTEX_DRIVER` only on first open (default `simx`), then `dlopen`s the basename `libvortex-<driver>.so`. Later environment changes do not switch it. `libvortex.so` has SONAME `libvortex.so` and `$ORIGIN` runtime search; backend wrappers also search `$ORIGIN` for simulator DSOs.

Therefore a fresh process with one complete bundle variant is the minimal safe supported model. Do not advertise simultaneous SimX/RTL, FP16/BF16 native-build variants, or arbitrary replacement bundles in one interpreter. The lock must remain after sessions close because the native dispatcher's global backend persists. Repeated sessions using the identical bundle may remain supported.

The extension should not link directly to `-lvortex` for this first slice: that loads a runtime during Python import before the binding can verify its identity and produces uncontrolled dynamic-loader errors when native dependencies are absent. A shim lets ordinary package import succeed without native prerequisites and session creation issue actionable errors after explicit checks.

The shim needs exactly these 20 currently used API functions from `sw/runtime/ai/runtime.cpp` (MLP adds no direct `vx_*` calls):

`vx_device_open`, `vx_device_query`, `vx_device_release`, `vx_device_memory_info`, `vx_module_load_bytes`, `vx_module_get_kernel`, `vx_module_release`, `vx_kernel_release`, `vx_queue_create`, `vx_queue_release`, `vx_buffer_create`, `vx_buffer_address`, `vx_buffer_release`, `vx_enqueue_write`, `vx_enqueue_launch`, `vx_enqueue_read`, `vx_event_get_value`, `vx_event_wait_value`, `vx_event_get_profiling`, `vx_event_release`.

Use exact public C signatures from `sw/runtime/include/vortex2.h`, eager symbol resolution and a retained library handle. Keep wrapper symbols hidden to avoid interposition with the actual runtime. Native backend symbol resolution can depend on symbols exported by `libvortex.so`; the hosted integration must exercise the selected `RTLD_*` policy, rather than assuming `RTLD_LOCAL` is sufficient. Avoid unloading while any session/operation or dispatcher state can retain library code.

## Minimum practical receipt and verification design

### Build producer

A new `ci/project/p05_*` producer, operating in a fresh generated tree, should:

- Validate clean source and the actual native builds with the existing P03/P04 helper contracts.
- Verify the extension's AI C++ sources and public headers come from that same source inventory; compile the real managed sources, not a second arithmetic implementation.
- Preserve the native executable and its exact invocation for independent comparison.
- Construct a versioned canonical receipt, write its exact bytes, compute its SHA-256 and embed that SHA as a generated C++ constant in the extension. A user setting a build variable is a trusted local build, not automatically a qualified release.
- Build the wheel from that pinned extension; record the wheel and extension hashes in an **outer execution/package receipt** to avoid a digest cycle. The inner receipt must not include the digest of an extension that embeds its own receipt hash.
- Keep the complete reviewed producer/helper/source/build/tool evidence in the qualification packet. The small install-time receipt is a binding index, not a replacement for the packet.

Suggested inner fields:

| Field | Required content |
|---|---|
| `schema_version`, `contract_id` | Exact supported versions, unknown/extra fields rejected |
| `source` | Observed clean source revision/tree, pin/submodule identity and relevant source inventory hash |
| `binding_source` | Hashes of extension sources and reused managed C++/headers (before generated receipt-pin header) |
| `variant` | `backend` in `{simx, rtlsim}`, `format` in `{fp16, bf16}`, RV64 and exact accepted profile ID/hash |
| `fixture` | Frozen P04 fixture SHA, model ID and generated adapter identity |
| `compiler_records` | Raw role stamps by hash plus independently validated role/configuration results; include extension compile/link record separately |
| `generated` | `.config.stamp`, `config.mk`, C++/Verilog config/types headers, copied recipes and effective-header/reproduction observations |
| `artifacts` | Unique canonical relative path, SHA-256 and byte size for every executable/module/DSO used |
| `dependencies` | Project dependency hashes and declared external runtime prerequisites; static archives separately from load-time DSOs |
| `toolchain` | Actual Python, compiler, linker, build tool and native tool identities/version records |
| `qualification` | Producer packet/report identity and explicit scope; passing native baseline alone does not claim Python execution |

Do not allow arbitrary extra artifacts to satisfy required roles; exact role membership matters. Binding/receipt ID should be recomputed from canonical data or exact pinned bytes, not accepted from caller text. Reject duplicate JSON keys, booleans-as-integers, unexpected fields, unsafe paths, missing records and malformed digests.

### Session creation

1. Resolve the installed extension and declared bundle directory. Read bounded receipt bytes, compare their SHA-256 with the compile-time expected digest, then parse the strict schema. The caller may relocate the bundle, but cannot choose its identity.
2. Verify exact role inventory, backend/dtype/profile/source/fixture consistency and every required regular file's SHA/size. Read and retain the module bytes once; pass that checked copy to `ManagedMatmul`.
3. Confirm no incompatible Vortex runtime/backend has already been loaded and no different bundle was previously selected. Fail closed on missing prerequisites or mismatch; do not change backend after lock acquisition.
4. Use a fresh launcher with explicit `VORTEX_DRIVER` and only intended library directories in its startup environment. Sanitize loader injection/search variables rather than mutate `LD_LIBRARY_PATH` inside an already running Python interpreter.
5. Load the verified absolute runtime path and required symbols. Verify the actual loaded object's path/identity (e.g. symbol-origin `dladdr`) and the backend/simulator/project-dependency objects actually selected, so library search and already-loaded same-name DSOs cannot silently defeat file verification. A launcher-controlled environment is useful but is not itself an observation of loaded objects.
6. Only then construct the native `ExecutionBinding`, deriving dtype/profile/ID internally. Native geometry queries remain a second check. Retain the bundle/process identity and return it in read-only session metadata/traces.
7. During qualification, rehash and retain before/after observations as the existing runners do. State the existing non-adversarial-filesystem limitation; this slice does not solve a malicious concurrent replacement attack.

The shim still uses the existing dispatcher, whose backend load is by basename. Validate and test the exact search/preload strategy in hosted integration; an absolute path for only `libvortex.so` does not guarantee the backend/simulator/dependencies came from the verified bundle.

## Exact project artifacts and portability limits

For a SimX bundle, at least these load-time native objects must be bound:

- `sw/runtime/libvortex.so`
- `sw/runtime/libvortex-simx.so`
- `sw/runtime/libsimx.so`
- `third_party/ramulator/libramulator.so`
- `third_party/ramulator_ext/libramulator-vortex.so`

For processor RTL substitute `libvortex-rtlsim.so` and `librtlsim.so`; the dispatcher and Ramulator DSOs remain. The matmul module is the exact validated `tests/regression/ai_matmul/kernel.vxbin` or `tests/regression/ai_mlp/kernel.vxbin`, with the associated ELF and build records bound. Preserve the matching native app independently. `sw/kernel/libvortex2.a` and `third_party/softfloat/build/Linux-x86_64-GCC/softfloat.a` are build inputs, not additional load-time DSOs.

`sim/simx/Makefile` and `sim/rtlsim/Makefile` currently link simulator DSOs with **absolute source-checkout RPATHs** to Ramulator and Ramulator extension directories. Copying only the three Vortex DSOs to a wheel is therefore not a proven portable installation. For the first external-bundle slice, declare and verify all five project DSOs and confirm the actual loaded paths in a relocated clean-process test. If relocation needs relinking/RPATH editing, retain the changed binary hashes and requalify; do not pretend original binary hashes still apply. System libstdc++/libgcc/glibc and any transitive system DSOs need a declared platform compatibility boundary. Full ELF dependency closure cannot be established locally because no native binaries exist here.

Required negative provenance tests:

- Direct low-level extension construction cannot accept `verified_*`, arbitrary module bytes, arbitrary ID or an expected hash supplied by Python.
- A caller-created internally consistent manifest with a plausible source hash/profile fails against the compiled receipt pin; changing receipt and artifact together still fails.
- Wrong backend/format/profile/source/fixture, dropped/duplicated role, swapped runtime/kernel/host record, contradictory macros, altered generated header, stale copied recipe and malformed stamp all fail before native dispatch.
- Changed module/runtime/backend/simulator/Ramulator bytes, wrong size, missing file, escaped path, unsafe symlink and replacement during hashing fail closed.
- Preloaded foreign `libvortex.so`, foreign backend with same basename, wrong startup search directory, stale `VORTEX_DRIVER` and a second bundle request fail explicitly.
- Missing DSO or any one missing `vx_*` symbol produces an actionable dependency/ABI error; constructor/submit must not run afterward.
- Ordinary import with absent bundle succeeds or gives the documented package-level behavior without a toolchain install/build; native session creation fails clearly.

Required positive/qualification tests:

- Build wheel, install in fresh venv outside checkout, clear source `PYTHONPATH`, run import, create, supported submit/wait/result/explicit close and named frozen model case; prove source checkout is not resolving imports.
- Match exact actual output bits to the unchanged native executable and independent fixture; preserve traces and provenance. Native results from P04 are baseline only, never relabelled Python runs.
- Run all three signatures for the selected dtype and all frozen cases in each declared format, separate processes/variants as necessary. A first FP16 checkpoint may be reported as bounded scope, not the full six-signature matrix.
- A relocated matched bundle still works under the declared dependency policy; a changed or absent dependency fails.
- Record actual Python minor/patch, wheel ABI/platform tag, C++ compiler, build backend versions, package/extension/native artifact hashes and complete native invocation.

Integration locations: new package/build files under a dedicated Python package directory; new producer/consumer/tests under `ci/project`; reuse managed sources under `sw/runtime/ai`; native comparison remains `tests/regression/ai_matmul` / `ai_mlp`. The existing `.github/workflows/p04-model.yml` demonstrates isolated per-backend/per-format jobs, pinned cache checks, `p04_ci_prepare`, two jobs, bounded commands and hidden stamp retention.
