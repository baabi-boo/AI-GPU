## Findings and required binding behavior

1. **Status success is not completion.** `ExecutionResult::ok()` (`runtime.h:32`) checks three codes but deliberately does not check `complete`. Successful `submit` has `ok=true, complete=false`; the native harness asserts this. Publish a successful Python tensor only with terminal successful status and the expected native output count. Return owned output bytes/words, not a memoryview of the vector. `output_words()` is empty until actual successful readback (`runtime.cpp:449–510`). The output remains stored after `close`, including if a later release reports a cleanup error: preserve the separate status and make any diagnostic access explicit rather than calling it success.

2. **Native submission failure may still own live work.** `runtime.cpp:227–299,361–413` creates an operation before queue/buffer creation and returns it after partial enqueue failure. After any successful write it is incomplete until drain. Early validation rejects without an operation; native queue/buffer/address/enqueue errors normally return an operation even when already closed. Preallocate the Python operation wrapper before entering submit, install the native pointer immediately, and return that object for all native results. A convenience exception must retain the operation. Avoid a post-submission Python tuple/result allocation that drops the only owner on `MemoryError`. The native C++ allocation catch path currently runs before enqueue because the enqueue helper is `noexcept`; do not generalize it to Python allocations after submission.

3. **Timeout is retryable and not sticky cancellation.** `wait` leaves internal status/resources unchanged on timeout (`449–473`), returning a transient timeout only if no earlier primary error exists. A prior submission error remains primary even when the current drain times out; `complete=false` is decisive. A non-timeout wait whose completion value cannot be established also retains all resources. `close` frees only after terminal completion. Retain the same operation after timed-out close, preserve prior primary/cleanup independently, and expose timeout units/range explicitly. `ManagedMatmul::close()` has no deadline: it returns `VX_ERR_TIMEOUT, complete=false` while any operation retains the context, even if that operation was successfully waited but not closed (`422–434`).

4. **Garbage collection can block indefinitely.** The operation destructor repeatedly calls `close(VX_TIMEOUT_INFINITE)` with 1 ms backoff (`442–446`), so dropping an incomplete object is not bounded cancellation. A Python finalizer/context exit policy must state that exact limit. Never reset the native pointer after an incomplete bounded close. Interruptible Python waits should use bounded native waits, retain self/native ownership across signal checking, and leave the operation reusable on `KeyboardInterrupt`. Do not call Python APIs while the GIL is released. Explicit close is necessary to observe cleanup failure; native destructors discard cleanup codes.

5. **Single-caller scope requires explicit serialization.** Native owners contain no mutex, and traces/state are modified in wait/close. Each operation shares `RuntimeContext`; context cleanup uses `shared_ptr::use_count()` (`104–125,422–434`). Releasing the GIL without a lock permits `wait`, `close`, `trace`, submission and session close to race. Use one shared session/context mutex retained by every Python operation (or initially keep the GIL during all native calls and disclose blocking behavior). If releasing the GIL, acquire shared locking without holding the GIL while waiting for the lock, and retain the Python/native owner until reacquisition. Snapshot traces/output under that same lock. Reject unsupported free-threaded/subinterpreter use unless separately qualified. Serialize context cleanup to preserve cleanup-error attribution.

6. **Qualification inputs are assertions, not verification.** `create` only checks that the qualification ID is 64 hexadecimal characters and both verified flags are true (`27–30,308–343`), then checks runtime capabilities. It copies module bytes and loads `main`; it does not verify module/runtime hashes or compiler records. The public Python constructor must use a trusted package/launcher manifest and derived identity. Do not expose a constructor accepting arbitrary module bytes plus `verified_*` booleans or user-supplied qualification strings as qualified execution.

7. **Explicit byte representations are necessary.** Native submit validates only the three supported tuples and exact byte lengths (`365–395`); it has no knowledge of a Python exporter's dtype, rank, byte order, strides, or layout. Validate Python metadata before submit: FP16/BF16 little-endian 16-bit words; A row-major `(M,K)` and B column-major `(K,N)`; packed exact extents; no implicit conversion, transpose, broadcast, padding or noncontiguous view. Keep buffer-export references through the synchronous native copy. Contract planning subsequently checks native addresses, allocation identity, four-byte alignment, disjoint ranges, capabilities and exact wire bytes; Python must not manufacture device addresses from host pointers.

8. **Close-result persistence differs by object.** Native operation repeated close returns its stored primary/cleanup status. Native session close resets its context and a second call returns fresh success, even after first-close cleanup failure (`422–434`). Python should cache and expose terminal session close status so retries cannot erase the observed failure. Session destruction while an operation exists is supported: the operation keeps module/device/image alive and final operation close performs their release. Avoid retaining the Python session itself unnecessarily if it would change the documented native lifetime behavior; a shared context lock is sufficient.

9. **Trace arrays need observation context.** `event_results` initially contains success codes before any observations; profile results initially mean not-supported and have explicit queried flags. Expose command counts, completion, profiling enabled/queried flags and exact statuses together, not an unqualified claim that all five events ran. Return immutable snapshots. Profiling-query failure is diagnostic and deliberately does not invalidate otherwise successful numerical output (`476–494`).

No demonstrated native lifecycle defect was found in the exercised supported path. Items above are concrete requirements at the new binding boundary; they do not justify weakening the accepted native contract.

## Recommended minimal extension surface

Use a reviewed, version-pinned C++ CPython extension owning `unique_ptr<ManagedMatmul>` and `unique_ptr<MatmulOperation>` directly; do not expose C++ layout through ctypes. Suggested shape:

- `open_session(qualified_configuration)` produces an opaque session after manifest/module/runtime checks.
- `session.submit(a_bytes, b_bytes, *, shape, a_layout, b_layout)` returns an opaque operation with immutable submission status, including partial-failure operations. Session fixes input dtype/profile.
- `operation.wait(timeout_ns)` and `operation.close(timeout_ns)` return explicit `{validation, primary, cleanup, complete}` snapshots; they never consume an incomplete owner.
- `operation.result_bytes()` returns an independently owned little-endian FP32 byte string only after complete success; `trace()` returns a copied snapshot. Expose raw words directly or make numeric unpacking an explicit adapter.
- `session.close()` preserves its terminal cleanup result; session and operation support documented explicit context-manager behavior. Strong references, shared locking and no-Python-API GIL-release scopes are part of the implementation contract.

A named fixed MLP case API should be separately backed by the pinned fixture and existing `ManagedMlp`; no arbitrary caller-provided expected arrays should be treated as correctness evidence.

## Missing boundary tests to add

Existing host tests cover all six shapes/dtypes, native input copying, early validation, device/module/kernel setup failure, every native buffer/address/enqueue failure, timeout retention/session destruction, asynchronous event+cleanup errors, destructor drain, repeated resources and profiling. Add Python-specific tests for:

- Native submission failure followed by timeout/retry while the same Python operation remains reachable.
- Python allocation failure immediately around submission/result wrapping, and `KeyboardInterrupt` during an incomplete wait.
- Read-only exporters, mutation/release after synchronous copy, buffer acquisition failure, noncontiguous/itemsize/endian/rank/stride errors, and negative/overflowing integer metadata.
- Session destruction while operations remain; output copies surviving operation close/destruction; session close cleanup-error persistence; successful readback followed by cleanup-only error.
- Concurrent wait/close/trace/session-close access if GIL release is supported; bounded subprocess check for unbounded-finalization behavior rather than a test that can hang the full suite.
- Native completion-value query failure and a non-timeout wait error with completion still unestablished. Current fake `vx_event_get_value` always succeeds and the fake waiter only injects timeout or terminal asynchronous failure, so these retention branches are not exercised by current P03 tests.
