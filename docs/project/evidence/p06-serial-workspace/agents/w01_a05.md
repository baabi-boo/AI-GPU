## Exact boundaries and additional traps

1. **Host exceptions currently precede dispatch.** `create` catches context,
   qualification/image copy and owner-allocation failures. `submit` catches
   operation/state, trace-string and A/B/download/output allocation failures;
   those allocations precede its `noexcept` submission helper. Acquire each new
   reservation with rollback that also covers failure before the context or
   operation object exists. Do not add throwing bookkeeping after the first
   enqueue without fixing the catch path: assigning a default `ExecutionResult`
   back to `state.result` currently resets `complete=true`, which would permit
   premature release if an exception could occur after partial dispatch.

2. **Partial submission has a precise ownership split.** The first accepted
   write changes `complete` to false. Failure at enqueue 1 has no accepted work;
   failures at 2–5 retain respectively 1–4 events and drain that accepted tail.
   Planner/address/allocation failures likewise have no queued work. Preserve
   today's completed automatic rollback for no-work failures; a published
   partial operation must retain staging, queue, events, context and lease.
   Borrowed resident handles must never enter the per-operation release loop.

3. **Primary error ordering must precede completion observation.** In baseline
   `wait`, a non-timeout wait error is recorded only after a successful value
   query. Query failure or value below one returns a modified temporary result;
   a later successful observation can erase the failure and expose output.
   Remember the first non-timeout wait error before querying, then remember a
   query error or inconsistent below-target value without replacing that first
   error. Completion remains false until a successful value query establishes
   the target. A timeout alone stays retryable.

4. **Cleanup-only failure can leave output visible.** Baseline release never
   clears `output_valid`; successful completion followed by an event/queue/
   buffer or last-context cleanup error therefore leaves `output_words()`
   nonempty. Root explicitly selected suppression of subsequent output access
   after observed cleanup failure. Previously copied output cannot be revoked;
   the final result still records failure. Existing combined async/cleanup
   tests miss this because the primary async error already suppresses output.

5. **Publish poison before making a reservation available.** Record cleanup
   failures from rollback, explicit close and destruction before releasing
   shared ownership. A new create must never race through a temporarily free
   slot before poison becomes visible. Continue all release attempts, preserve
   the first cleanup error, and never retry a possibly consumed handle. Final
   operation teardown after owner destruction must report context teardown
   failures as well. Repeated owner close needs durable status after reset.

## Missing regression cases

| Boundary | Required added checks |
|---|---|
| Host allocation | Inject failure before context/operation construction, during qualification/image/staging copies, and at owner publication. Assert empty output owner where appropriate, no stranded context/operation reservation, and clean retry only after clean rollback. |
| Setup | Fail each capability query (existing test only fails query 1), each resident buffer allocation/address query, and workspace validation; include rollback release failure. The buffer whose address query fails is already owned and must be released. |
| Partial enqueue | At each of 2–5, combine submit failure with a bounded wait timeout, attempted second submit/context, owner destruction and eventual drain. Preserve original primary; never expose output or return the lease before completed close. |
| Completion observation | Script wait error plus query error, wait error plus value zero, successful wait plus query error/zero, repeated observation failures, then successful drain. Also verify ordinary timeout then success remains successful. |
| Cleanup | Target every event release, queue release, A/B/D release and kernel/module/device release individually; exercise success plus cleanup-only failure, rollback, explicit close, destructor close and final operation-owned context destruction. Verify first error, remaining releases, no double release, output suppression and new-work rejection. |
| Lease isolation | Reject invalid and valid second submits while the first is queued, timed out, partial, or successfully waited but unclosed. A rejected call must not clear the first lease. Keeping an already closed operation object alive must not prevent clean serial reuse. |

The existing fixture's `cleanup_failure` fails only the next release and still
destroys that handle. Its event-value query always succeeds, and its launch
writes fixed values independent of inputs. Extend the fixture with independent
scripted wait/query and targeted release controls; changed-input tests need a
separate meaningful data-lineage oracle. Do not throw C++ exceptions through
fake C entry points to simulate a returned API error: managed helpers are
`noexcept`, while production create/enqueue entry points translate exceptions.

Permanent poison cases need separate process invocations. `reset()` only
resets fake backend state and must not clear production poison. Use finite
observation-failure scripts for eventual-drain tests; destruction intentionally
waits indefinitely when completion cannot be established.

The common buffer destructor ignores `mem_free` errors, and ordinary handle
release returns do not prove physical reclamation. Keep poisoning explicitly
limited to observed cleanup failures. The selected 320-byte workspace denotes
128/64/128 logical payload bytes, not allocator/RSS usage. This audit adds no
P06-A02/A03, native arithmetic, recovery or performance evidence.
