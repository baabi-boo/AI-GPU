### Reservation and ownership

The single atomic distinguishes available, reserved and positive cleanup-error
states. All declared `vx_result_t` failures are positive and distinct from the
reserved sentinel. A compare/exchange reserves before any native open; successful
rollback/teardown returns availability only after native handles have been
consumed. Cleanup poisoning changes the reserved state before any release can
publish availability, and a positive error cannot be overwritten by later
release or create attempts. Acquire/release ordering covers handoff between
otherwise separate managed creates. No claim is made that the non-atomic owner
or operation fields support concurrent methods on one object.

`RuntimeContext` is retained by a live operation. A successful wait does not
drop that reference or the operation lease. Healthy completed close releases
events, then the queue, then owned default buffers before returning the lease;
resident handles are borrowed and remain context-owned. Last-operation close
after owner destruction also releases the context and propagates its cleanup
status. Explicit owner close detects retained operation ownership and returns
incomplete without setting a closing latch. Closed operation objects do not
hold a lease or a context reference.

Context cleanup attempts all remaining buffers/kernel/module/device releases,
consumes each handle once even when a release reports failure, retains the first
observed error, and prevents new work. Repeated owner close returns the saved
result. Native buffer/module/queue/event release functions generally return
success after reference release, and buffer destruction ignores the underlying
`mem_free` return. The implementation correctly promises poisoning only for
**observed** release failures; wrapper-injected release errors do not establish
physical deallocation observability or physical device recovery.

### Allocation, dispatch and exceptions

The resident policy creates A128/B64/D128 during context setup with existing
read/read/write permissions, queries every address and invokes the unchanged
planner before publication. Submission accepts only `(8,4,8)` for that policy;
the default's three shapes in both formats remain unchanged. Invalid arguments
and unsupported resident shapes return before operation allocation or enqueue.
Every successful call still creates host staging, queue/events, rewrites all
inputs and poison, launches the same kernel and downloads the complete output.
The request uses the actual queried addresses and the known requested extents.

Create reserves before `make_shared` and covers failure before a context exists,
string/image copying and final owner allocation. A context that exists has its
reservation flag before subsequent throwing work. Submit acquires its lease
before object/state/trace/staging allocation; construction failure without an
operation clears the lease, while an existing no-work operation closes cleanly.
An incomplete operation is retained instead of overwriting its completion state
and freeing an accepted prefix. The C API's allocation/enqueue entry points
translate their own exceptions to statuses; the no-throw wrapper helpers rely
on that established C boundary. This review does not qualify an arbitrary C API
implementation that lets C++ exceptions escape those entry points.

Actual `Queue::enqueue` publishes an output event only after successful FIFO
insertion. Deferred writes/reads retain buffers and still reference host staging;
launch captures its argument bytes and retains the kernel. The worker runs FIFO,
retains dependencies, clears command-owned work before signaling completion and
propagates dependency/async failures. These semantics support waiting on the
last accepted event while retaining the full prefix, then releasing the queue
before the tensor handles. Raw clients or independently linked managed copies
remain outside the context guard, as documented.

### Completion and consumers

A non-timeout tail-wait failure is stored before the completion-value query.
Non-timeout query failure or a value below target remains sticky through later
drain. Tail, query and prefix-poll timeouts retain incomplete ownership and do
not replace an earlier primary error. All prefix observations finish before
completion is marked true; profiling-query results remain separate from the
operation's arithmetic/error status. Output becomes valid only after a fully
submitted successful operation and is suppressed by that operation's primary
or cleanup failure.

The Python extension constructs a default `ExecutionBinding`, closes the native
matmul owner before creating a model, and reacquires on lazy resume. Native and
Python cleanup poisoning are compatible. Real MLP stages explicitly close each
operation before advancing. A terminal model may have `complete=true` while its
owner context remains live; explicit model close/destruction is still required
for context handoff. Reviewed new combined-model tests use real model/runtime
code over a fake C API; scripted zero outputs establish control flow only.

## Finding and resolution

**F1 — output-suppression wording exceeded the detached-result boundary.**
Confidence: **high**. Evidence type: **static-proof**, supplemented by the
bounded fake-backend probe below.

Before clarification, §3 broadly stated that output access is empty after an
observed cleanup failure. A healthy closed operation has already detached its
context and owns independent host output. If a subsequent owner teardown reports
a kernel-release failure, that old operation retains its successful output and
healthy close result, while the shared instance rejects new work. This is a
reachable documentation ambiguity, not an observed runtime ownership defect.

The root confirmed the intended operation-local boundary and revised §3 to say
that suppression applies to failures observed by the operation, including
last-owner context teardown performed during its close. A later owner teardown
failure does not retroactively revoke a previously healthy closed operation's
host result. I re-read that paragraph and confirmed its agreement with code and
the probe. **Resolved before publication; no runtime behavior or test threshold
was weakened.** Final contract digest is recorded below.
