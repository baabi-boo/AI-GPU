## Implemented behavior

The runner's `run` CLI matches the workflow's `--source-dir`, `--tools-dir`,
`--work-dir`, `--output`, `--backend`, `--format`, `--jobs`,
`--timeout-seconds`, and `--run-timeout-seconds` arguments. It also accepts
existing host-tool and Verilator locations. Backend/format selections can be
repeated without changing canonical matrix order. Duplicate, empty or unsupported
selections are rejected. No iteration, case, policy or dirty-source override is
provided: each chosen variant always runs both policies and the frozen four-call
sequence. Fresh source-external work/output directories and a clean source
checkout are required.

The four calls use the unchanged independent P02 fixture words, in manifest
order including the repeated dense case. The independent producers must
reproduce the full P02 fixture corpus and exported header before a build. The
existing P02 profile SHA-256 and the unchanged native matmul kernel SHA-256 are
checked. Each backend/format has a fresh configured tree; generated C++ and RTL
configuration headers must reproduce independently.

Compiler-record validation uses the new workspace validator API without changing
its signature. Each original runtime, backend, kernel and host compiler record
is checked separately, and the original host link must contain exactly the four
approved observer wrappers and qualified runtime path. Every returned role is
also probed through its original include search order. The processor RTL C++
shim is explicitly treated as a nonselecting shim; the independent Verilator
record must carry the native arithmetic selection. Exact effective hardware
macro maps must agree with the independently generated profile, and execution
mode, tracing and performance instrumentation macros are rejected.

Each policy gets a separate direct application process and a distinct canonical
binding containing its policy, backend, format, sequence, full fixture words,
fixture hashes, exact source revision/tree and file inventory, profile/kernel
identities, compiler records, generated configuration, actual binary hashes,
tool hashes and existing dependency hashes. The caller receives only its policy,
module path and qualification ID. The agreed records API receives the ordered
four-case list, format, policy, binding ID and frozen contract.

All source bodies in the expanded P03 inventory are retained, including loaded
transitive Python helpers and workspace-specific sources. This includes
`p06_workspace_compiler_records.py`, `p06_compiler_records.py`, the shared
compiler/stamp parsers and the three independent fixture producers. Original
stamps, copied Makefiles/helpers, generated headers, configuration records,
raw command logs and successful or failed process attempts remain inspectable.
Failed builds retain available generated records. Log sizes and SHA-256 values
must match the bounded-process receipts, and the final packet checks retained
source/build/snapshot bodies again. Source, tools, dependencies and built
artifacts are checked for stability before and after execution.

The unchanged hard maxima are two jobs, 4 GiB polled process-group RSS,
15 GiB free-disk reserve, 16 MiB per-command logs, 1,800 seconds per build and
180 seconds per application process. Smaller job/time selections are permitted;
larger selections are rejected in both CLI parsing and execution. Existing
bounded-process limitations remain explicit. The root's workflow supplies the
90-minute hosted job deadline and was not edited.

Completion counts derive from the verified operation records. A successful
single backend/format reports two processes, eight launches and 256 checked
words, with `full_matrix_completed: false`. Only all four variants may report
the full eight processes, 32 launches and 1,024 checked words, after final
stability verification. Performance acceptance, phase acceptance and phase
completion remain false. Failed-process logs do not become invented passing
launch/word totals.
