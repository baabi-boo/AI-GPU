## Conclusion for the proposed boundary

The current model and Python/PyTorch success paths already serialize work through completed operation close. A native reservation covering every `ManagedMatmul::create` also covers a model's underlying owner, provided that the reservation remains held until actual context teardown. The proposed default-off workspace policy preserves the current shipped consumers: Python constructs a default `ExecutionBinding`, and `ManagedMlp` uses the existing per-operation path for its three differently sized stages.

Two details require explicit coverage in the implementation: terminal model inference must continue to occupy the context until model close, and a successfully waited matmul must continue to occupy its operation until explicit completed close. The existing binding enforces both before many calls reach the native runtime; a binding pass therefore cannot establish the new native guard by itself.

The root's stated candidate scope is one optional fixed `(8,4,8)` A/B/D workspace, 320 payload bytes, allocated at context setup; model and binding callers keep the default per-operation policy. No model workspace, Python policy switch, concurrency support, or new numerical/performance claim is proposed by this audit.

## Findings and compatibility observations

### A02-F01 — native model ownership must be guarded below the binding

**Severity:** F2 for leaving this prerequisite unresolved before reuse. **Confidence:** high. **Evidence:** static-proof.

`ManagedMlp::create` calls `ManagedMatmul::create` directly (`sw/runtime/ai/mlp_runtime.cpp`, create). At the inspected base, `ManagedMatmul::create` opens a device without a process reservation, and `submit` permits another operation whenever its separate output pointer is empty (`sw/runtime/ai/runtime.cpp`, create/submit). The Python lease in `python/native/module.cpp` does not protect direct C++ calls.

A concrete unsafe sequence is to create an idle model and then create a separate matmul owner, or to finish `model.advance()` and create another owner before `model.close()`. The model still owns its native context in both cases. Direct model/model creation has the same issue. Similarly, a raw native caller can submit twice with two empty operation pointers, including after the first successful wait. These are the known prerequisite defects the root intends to fix; this report does not claim they were newly discovered execution failures.

Required behavior: reject a conflicting managed context before a second `vx_device_open`; reject a conflicting operation before queue/buffer creation or enqueue. Preserve these exclusions while draining partial work, while a close times out, and after owner destruction if an operation retains the context. A successful wait or terminal model status must not return either reservation.

### A02-F02 — fixed workspace policy must not silently enter the fixed model

**Severity:** F1 conditional integration risk. **Confidence:** high. **Evidence:** static-proof of the consumer shape and accounting requirements.

`ManagedMlp::create` forwards its supplied `ExecutionBinding` unchanged to `ManagedMatmul::create`. `submit_stage` uses `(16,8,16)` for hidden output and `(8,4,8)` for each output half. The hidden stage transfers 512 A bytes and 256 B bytes and produces 512 D bytes. These extents exceed the proposed fixed workspace's 128/64/128 byte capacities. All model stages need their original accepted shape support under the default policy.

`ManagedMlp::check_resources` queries memory after operation close but before owner close and requires exact equality with the observation taken immediately after owner creation. `python/native/module.cpp::model_output_ready` independently requires the same equality. Lazy retained allocation would fail this check if accidentally enabled for a model. Allocating at context creation can make the comparison stable, but it does not make the hidden shape fit and does not establish final workspace release.

Keep current shipped model/binding construction default-off. If a native caller can pass the new opt-in policy to `ManagedMlp::create`, define and test its disposition explicitly: reject it at model creation or apply a documented model-specific default policy. Do not silently resize the fixed workspace, weaken the model resource check, or alter the accepted graph to fit the experiment.

### A02-F03 — sticky native poison changes a legacy host test's process assumptions

**Severity:** F2 conditional test integration obligation. **Confidence:** high. **Evidence:** static-proof.

`ci/project/fixtures/p03_managed_runtime_test.cpp::asynchronous_errors` loops over five asynchronous fault ordinals in a single process. Each iteration injects `cleanup_failure`, closes the operation, closes the owner, calls the fake-runtime `reset()`, and creates another owner. Once native cleanup poison is process-sticky, the next iteration must be rejected even though the fake counters were reset.

Preserve coverage of all five event ordinals by running them in separate child processes or separate executable invocations. Do not add a production poison-reset hook to preserve this test's old loop. The P05 compiled suite already runs each scenario in a fresh child expressly because cleanup poison cannot be reset, and its error tests already require rejection of future work.

Changing the owner close result itself would also affect existing tests: P05's operation-cleanup cases expect the operation to retain `cleanup == 10`, block new work, and allow a separately successful context teardown to report `session.close().ok`. Keep the distinction between a process-wide poisoned submission state and the actual result of a later teardown, or deliberately update the contract and all affected assertions together. A later clean teardown must not clear the poison.

### A02-F04 — the isolated P04 test does not exercise the production guard

**Severity:** F2 if it is used as the sole native-model guard evidence. **Confidence:** high. **Evidence:** missing-test, supported by the test's link command.

`ci/project/test_p04_mlp_runtime.py` compiles `p04_mlp_runtime_test.cpp`, `mlp_runtime.cpp`, and `mlp_host.cpp`. Its fixture supplies replacement `ManagedMatmul`, `MatmulOperation`, and `RuntimeContext` implementations; it does not link `runtime.cpp`. Its passing control-flow tests cannot establish native process/operation reservation behavior.

Add a test linking the real `ManagedMlp` and real `ManagedMatmul` against the host fault-runtime VX boundary. Cover matmul/model and model/model creation in both relevant orders, idle models, terminal models before explicit close, incomplete model close, and successful create after complete clean close. Assert no second device open and no leaked reservation after failed setup. Keep the fake arithmetic scope explicit.

## Existing consumers that are compatible without behavior changes

| Consumer | Observed behavior at the base | Compatibility condition |
|---|---|---|
| `ManagedMlp::advance` | Waits, compares/copies output, calls `release_operation`, resets the operation only after complete close, then increments the stage | Return the native operation reservation only from completed close; preserve all existing default-policy shapes |
| `ManagedMlp::close` | Stops future graph advancement, drains the current operation, checks resources, closes the native owner, and retains incomplete ownership for retry | Keep context reservation until owner teardown, including terminal inference and incomplete close |
| `tests/regression/ai_mlp/main.cpp` | Creates one model per iteration, advances to terminal, drains close to completion, validates the record, then resets the model | A clean model close must permit the next serial model creation |
| Python `SessionOwner` / `OperationOwner` | One binding lease; operation shares that lease until completed explicit close; orphaned operations retain it | Preserve copied output/trace after close and keep failed/incomplete work drainable |
| Python model handoff | Closes/resets the idle session matmul owner, releases its lease, acquires the model lease; resumes matmul with a fresh owner after model close | Complete native close must release the reservation before model creation/resume; no double reservation acquired independently for the same owner |
| Python `_api.Session` | Registers an operation before native submission; native state refusal can leave an empty recoverable owner in `pending_operations()` | Do not remove this recovery behavior when adding native state rejection |
| PyTorch eager matmul | `_ready` rejects pending owners; `_wait_matmul` completes, `_close_operation` explicitly closes, then output is copied | Preserve successful serial calls and retained owners on timeout/partial failure |
| PyTorch eager fixed model | Advances the model, closes it, then copies output; returned CPU tensor is independent | Preserve profiling/resource checks and complete close before output publication |

The binding's `execution_binding` function explicitly enables profiling but otherwise uses default construction. It does not need a workspace option for this bounded native experiment. PyTorch borrows that existing session and does not directly construct a native binding.

## Existing coverage to preserve

`ci/project/test_p05_native_binding.py` already covers overlapping contexts, second submission before and after successful wait, pending-owner retention through GC, orphaned operation drain, model suspension/resume, close of a suspended session, terminal model context retention, incomplete model close, and cleanup poison. Its `ChildChecks.done()` checks `max_live_devices <= 1`, and the rejection probes check that device-open or queue-create counts do not increase.

The same suite has stage/occurrence-level setup, partial-enqueue, event, profile and release failures. `ci/project/p05_test_runtime.py` compiles the actual `runtime.cpp`, `mlp_runtime.cpp`, and extension with a fake VX DSO; this is useful integration evidence once rerun on the candidate. Conflict cases often stop at the extension's own lease, so they supplement the proposed direct C++ guard tests rather than replacing them.

`ci/project/p05_torch_native_host_tests.py` uses real PyTorch plus the compiled extension/fake VX boundary. Its scenarios cover all accepted matmul shapes, fixed models, transient and deadline timeouts, partial submit, asynchronous failure, cleanup failure and model mismatch. It tests recovery after clean drain and refusal after cleanup poison, and verifies that earlier returned tensors remain unchanged. Its orchestration unittest tests retained result handling; passing orchestration alone does not mean these real-PyTorch child scenarios ran.

For the optional workspace, add direct native assertions that:

1. Default bindings still cover all six shape/format signatures and the model graph.
2. Workspace opt-in accepts only its declared shape, with validation before dispatch for incompatible requests.
3. Context creation owns exactly three fixed buffers; operation close releases queues/events while retaining those buffers; final context teardown releases them once.
4. Changing A, B and D poison across serial submissions changes the transferred bytes and output appropriately; successful wait alone still blocks the next submit.
5. Saved operation output and trace remain independent after later operations reuse device buffers.
6. Partial enqueue, close timeout, owner destruction and every cleanup failure preserve the required workspace/context lifetime and sticky poisoned state.

These are coverage recommendations, not tests run by this assignment. They do not replace independent numerical comparisons, the matched experiment, native RTL evidence, or applicable P06 gates.
