### Allocation-injection boundary

The fixture replaces ordinary C++ `new`/`delete` locally, counts current wrapper
allocations, and tracks successful injected-scope pointers in a fixed-size array.
It observes four create allocation sites and seven submit allocation sites, then
visits every ordinal for `std::bad_alloc` and a distinct non-allocation exception.
The four create sites cover shared context, qualification string, module image,
and public owner. The seven submit sites cover operation object/state, trace
identity and four staging/result vectors.

Every fake C API entry establishes a thread-local exclusion scope. Its own
container/event allocations cannot consume the injected ordinal or throw the
scripted exception across the C ABI. Successful calibration asserts that such
excluded allocations actually occurred. Recorded wrapper pointers must all be
released after rollback/close, including constructor unwinding before an owner
object is published. This is deterministic failure injection, not global OOM,
an exhaustive host-heap leak proof, or a test of native library allocation failure.

### Race and polling boundaries

Only create calls run simultaneously. The first fake-open entry waits for the
competing create to return, so setup completion cannot accidentally hide the
reservation overlap. An unexpected second open is counted and rejected before
touching the fake's ordinary containers; a broken reservation therefore produces
a deterministic assertion instead of introducing a fake-backend data race.
No individual managed owner is used concurrently. The test establishes the
shared atomic reservation behavior, not general runtime thread safety or native
backend concurrency.

Polling failures are injected at the wrapper observation boundary. The deferred
fake can have completed its work while a later prefix/status poll reports a
timeout; the wrapper must still retain ownership until it establishes completion.
Busy probes compare the fake native-call map and native-open count before/after.
Completion and close assertions also check hidden failed output, exact wait and
timeout counts, no premature resource release, and healthy subsequent reuse.
