The following are existing source observations, not proposed behavior:

1. `ManagedMatmul::create` in `sw/runtime/ai/runtime.cpp` validates a qualified
   binding, copies its module bytes, opens device zero, queries capabilities,
   loads the module and resolves `main`. It has no native process reservation.
2. `submit` validates shape and exact input lengths, allocates fresh host staging,
   creates a fresh queue, and creates A/B/D buffers on every call. It validates
   the actual buffer addresses through `plan_matmul` before three writes, one
   launch and one read. There is no live-operation exclusion.
3. `wait` preserves ownership after completion. The context is shared by the
   operation, and owner `close` returns timeout/incomplete while that ownership
   exists. This does not prevent another `submit` today.
4. `OperationState::release` releases events, queue and operation buffers, then
   its context reference. Destruction drains indefinitely. A no-work submission
   error is already closed internally before its operation is returned; a
   partial enqueue retains its returned operation for drain.
5. `ExecutionResult::ok()` does not test `complete`; callers must inspect both.
   `ManagedMatmul::close` currently forgets its cleanup result after resetting
   the context, so a later close returns success. The proposed sticky failure
   contract therefore requires an actual implementation change.
6. Python has a separate `NativeLease`/cleanup-poison guard in
   `python/native/module.cpp`. The MLP creates a managed matmul and explicitly
   closes each stage. Neither fact qualifies a new native guard by itself.

The operator contract remains exactly three tuples `(8,4,8)`, `(8,4,16)` and
`(16,8,16)` in each of FP16/BF16, compact A row-major, B column-major, FP32 D
row-major, positive-zero initial accumulation and the accepted RV64 `p02-tfr`
profile. Shape support is a tuple set, not independent ranges. The 56-byte
argument schema, grid/block calculations, poison values, WMMA order and exact
expected words must remain unchanged.

## Concrete minimal API and treatment

The integration owner selected an enum in the existing internal binding. Freeze
this additive shape before implementation:

```cpp
enum class WorkspacePolicy : uint32_t {
  per_operation = 0,
  reusable_single_tile = 1,
};

// Add to internal ExecutionBinding:
WorkspacePolicy workspace_policy = WorkspacePolicy::per_operation;
```

The existing `create(binding, &owner)` and `submit(m,n,k,...,&operation)` call
shapes remain intact. This does not add a pool to the locked `vortex2.h` API or
create an installed/stable C++ interface. Unknown enum values must fail validation
before opening a device or allocating resources. Record the selected policy in
the new experiment records; never infer it solely from an address repeating.

For `reusable_single_tile`, create exactly three context-owned buffers during
context setup: A=128 bytes with `VX_MEM_READ`, B=64 bytes with `VX_MEM_READ`, and
D=128 bytes with `VX_MEM_WRITE`. Obtain and validate their actual addresses and
full tracked extents before publishing a usable owner. Allocation/address/plan
failure must roll back all successfully created resources. A partially built
workspace cannot become dispatchable. Initialization time is outside the measured
operation interval and must be reported separately.

Only `(8,4,8)` submissions are accepted by this policy; reject other tuples,
including the otherwise supported `(8,4,16)` and `(16,8,16)`, before acquiring
resources or enqueuing work. Do not reallocate, resize, pad, convert or silently
fall back to per-operation mode. The default policy continues supporting all six
signatures and the MLP's mixed-shape sequence. Do not opt the MLP or Python
interface into the fixed workspace implicitly.

Every successful operation still gets its own queue, events, input copy, output
staging and result storage. Rewrite all A/B input bytes and all D poison bytes on
every call, including after a previous successful read. Run the same planner,
argument encoder, native launch and read/comparison path. Changing inputs and
poison across calls must not expose retained prior output. Do not add queue/event
reuse, cached host staging, precomputed arithmetic, weight caching, launch
batching or reduced transfer traffic to this treatment.

## Required fail-closed ownership contract

The same ownership implementation must exist in both reference and candidate.
Only the buffer lifetime differs. Root's selected enforcement scope is **one
linked managed runtime instance**: all direct `ManagedMatmul`, MLP and Python
paths reaching that instance share its guard. Arbitrary raw `vx_device_open`
clients, duplicated runtime implementations in multiple DSOs and coexistence
with such clients are unsupported and are not guarded by this design. A local
C++ static must not be described as enforcing universal process-wide exclusion.

| Boundary | Required behavior |
|---|---|
| Context creation | Atomically reserve the shared managed-context slot before device open; publish only after successful complete setup. Clean no-work rollback returns the reservation. |
| Operation creation | Validate arguments and reserve one operation lease before resource/enqueue work. A second call must perform no allocations, enqueues or mutation of the first operation. |
| Queued or partially queued operation | Return/retain an operation owning every required staging object, event, queue, buffer access and shared context. A submit error is not permission to discard it. |
| Successful wait | Output may become available, but the operation lease remains held. A wait is not an operation close. |
| Incomplete wait/close | Retain context, workspace, staging, events and queue. Timeout is retryable observation, not cancellation or terminal completion. |
| Completed operation close | Release events and queue first; release default-policy buffers; only then return a reusable lease after successful cleanup. Resident buffers remain context-owned. |
| Owner close/destruction while operation retained | Owner close stays incomplete. Owner destruction transfers lifetime responsibility to the shared context held by the operation; its final close performs last-owner cleanup. |
| Cleanup error | Latch the first cleanup failure for the context and shared managed instance. Reject new submissions and contexts; allow only draining existing owners. Repeated close must preserve the error and avoid double release. |
| Final context teardown | Release resident buffers before module/kernel/device teardown; relinquish the context reservation only after complete successful cleanup. |

Keep validation, primary runtime failure, cleanup failure and completion separate.
Preserve the first primary failure when later drain succeeds. Unestablished
completion (failed event-value query or value below target) cannot release
resources. Classify terminal device loss conservatively as preventing further
work until a fresh process; successful draining is not device recovery evidence.

Two contract details still need exact frozen status assertions in implementation
review: the error returned by busy/poisoned create/submit, and whether an
incomplete owner close latches a closing state. Preserve today's no-work rollback
behavior as the minimal option: no accepted command plus verified successful
cleanup may return an already-closed operation. A nonempty operation pointer
alone must not be treated as a held lease. A partially submitted operation must
never take that shortcut. Use scoped acquisition rollback so host allocation
failure cannot strand the reservation before an operation is published.

The guard does not make these single-caller objects thread-safe. Its reservation
must nevertheless prevent simultaneous managed creates from both opening a
context. Reentrant/concurrent method use remains explicitly unsupported.

## Resource accounting and final-release caveat

These are exact logical A/B/D extents derived from the existing signature, not
measurements of device allocation or process memory:

| Shape | A bytes | B bytes | D bytes | A+B+D bytes |
|---|---:|---:|---:|---:|
| `(8,4,8)` | 128 | 64 | 128 | 320 |
| `(8,4,16)` | 256 | 128 | 128 | 512 |
| `(16,8,16)` | 512 | 256 | 512 | 1,280 |

At the small-tile shape, each call still uploads 192 input bytes and 128 poison
bytes, downloads 128 D bytes, and performs 512 useful FLOPs. The 56 argument bytes,
module traffic and runtime/control transfers remain separately accounted.
Across a successful 32-operation measured batch this is 6,144 input bytes,
4,096 poison bytes, 4,096 D bytes and 16,384 useful FLOPs in either arm.

Count A/B/D `vx_buffer_create` attempts/successes separately from all runtime
allocations. The reference should have 96 successful A/B/D allocations during
the 32 measured calls and three additional allocations in its excluded prime.
The candidate should have three successful context-setup allocations and zero
new A/B/D allocations during prime or measured calls. Both still create 33
operation queues and, for fully successful work, 165 events across prime plus
batch. Partial attempts must retain their actual prefix counts.

`Device::mem_alloc` rounds to cache-block or VM-page granularity. Its
`memory_info` reports combined paged/pinned allocator totals. Therefore 320
logical payload bytes are not automatically the same quantity as a device-wide
usage delta; account for alignment, argument scratch, module/runtime allocation
and the priming boundary. Keep logical resident bytes, tracked allocation bytes,
observed allocator used/free bytes and host RSS distinct. A snapshot is not a
measured peak; a peak requires instrumentation observing allocations/retirements.

**Material source limitation:** `sw/runtime/common/buffer.cpp` ignores
`device_->mem_free(dev_addr_)` errors in `Buffer::~Buffer`, while
`vx_buffer_release` returns success after reference release. Thus a successful
buffer-release return or fake-runtime handle count alone cannot establish actual
allocator reclamation. A release error injected at the wrapper seam tests that
seam's error handling, not the behavior of every underlying free.

Capture native memory while the device is live: before workspace creation,
after workspace creation, after prime, after operation 32, and **after workspace
release but before device release**. The final observation requires explicit
internal teardown instrumentation or an independently reviewed observer; calling
public `memory_info` after owner close is invalid. Retain statuses, raw values
and resource release order. To demonstrate complete final allocator release,
reconcile all context-owned resources against the corresponding baseline before
device teardown, with retained runtime scratch explicitly identified. A final
snapshot failure is unavailable evidence, never zero usage. No such native final
accounting was performed by this audit.

## Validation required before performance claims

1. Exercise both policies and both formats against supported/unsupported tuples,
   exact span lengths, unknown policy values, wrong profile, poisoned addresses,
   aliasing, owner publication failure and partial workspace initialization.
2. Test competing matmul/model contexts in both orders, second operation while
   queued/failed/timed-out/waited-but-open, owner destruction before and after
   completed wait, explicit/repeated close, and reservation rollback.
3. Inject each enqueue/event/query/cleanup boundary. Verify no early release,
   dependency-skipped work, no valid output on failed execution, preserved first
   errors, sticky poison and independent fresh-process recovery. Existing
   `asynchronous_errors` loops reset the fake backend and reopen in the same
   process; poison tests must isolate failure cases in separate processes rather
   than adding a production reset switch to clear the latch.
4. Execute changed-input/unchanged-poison and changed-poison sequences through
   reuse, preserving exact independent FP32 fixture words. Verify default-policy
   correctness for all six signatures and the existing MLP lifecycle. Host stubs
   cannot prove these numerical or dispatch results.
5. Retain actual addresses, sizes, binding IDs, argument bytes, policy,
   allocation/release counts, memory observations and status transitions. A
   repeated address alone does not prove reuse: a normal allocator can return a
   freed address again.
6. Freeze a distinct warm-batch manifest/schema, then execute matched clean
   reference/candidate revisions with identical tools/profile/observer and
   reviewed source diff. Preserve the accepted cold benchmark and raw evidence.
   The proposal's 24 processes/792 launches and its proposed thresholds remain
   design inputs until formally frozen and executed.

The minimal next implementation can establish reviewed source and host ownership
evidence, followed by bounded native SimX execution in a qualified environment.
Host CI passes do not establish native numerical correctness, modeled-cycle
