## Prioritized findings

### F2 / high / static-proof — native exclusivity is absent

`ManagedMatmul::create` opens a new device without a process reservation. `submit` creates a new queue and three buffers without checking for another live operation. A single caller can therefore create two live contexts or call submit twice sequentially while the first queue is active. The `shared_ptr` count only prevents owner teardown; it does not prevent submission.

This is a concrete prerequisite blocker for shared resident buffers. The common queue serializes each launch's DCR setup with that queue's `enqueue_mu_`, while `Device::cp_submit_cl_` releases `cp_mu_` between individual commands. Distinct queues can interleave launch setup. Separate SimX processors also initialize/finalize the process-wide `SimPlatform` (`sim/simx/processor.cpp`), so one context's destruction can affect another. No concurrency qualification follows from the present single-caller contract.

`ManagedMlp::create` delegates to `ManagedMatmul::create`; one guard there covers direct matmul and the model's underlying managed context, including idle models and terminal models whose owner is still open. A guard in `runtime.cpp` does not intercept raw `vx_device_open` callers or independently linked copies of the managed runtime. Keep coexistence with those paths unsupported and explicitly scoped; do not claim to change the raw API.

### F2 / high / static-proof — cleanup does not prevent future native work

`OperationState::release` records the first cleanup error in that operation, nulls handles and drops its context. The still-live owner can immediately submit again. `RuntimeContext::release` has no durable cleanup field, its destructor ignores the result, and `ManagedMatmul::close` resets the context even when cleanup failed. Repeating owner close then returns a default successful result. Thus explicit operation cleanup failure, owner cleanup failure, and destructor cleanup failure can all be followed by apparently healthy native work today.

Preserve reported cleanup failures in a process poison state, the affected context, and the owner's retained close result. Poison must reject new creation/submission while allowing existing owners to wait/close. Repeated close must not release handles twice or replace an earlier failure with success. The existing P03 `asynchronous_errors` fixture explicitly expects owner close success after an operation cleanup error; that expectation must change with the new contract.

### F2 / high / static-proof — an unestablished completion error can disappear

In `MatmulOperation::wait`, a failing `vx_event_get_value` or a completion value below one produces an error in a temporary copy of `state.result` (`runtime.cpp`, current lines 465–472). A later successful wait can expose output and return success, losing the earlier non-timeout error. A non-timeout wait error is also lost when the subsequent value check fails.

Remember the first non-timeout wait/query failure in persistent primary status while retaining `complete=false` until completion is established. A timeout alone remains retryable and does not become a sticky primary failure. Later drain can make `complete=true`, but cannot turn the failed operation into a successful sample or valid output.

### F2 / high / missing-test — current fixtures do not exercise the proposed guard

The 24 passing tests cover existing six signatures, invalid inputs, setup/allocation/address/enqueue errors, timeout ownership, async errors, profiling, destructor drain, model stages and model cleanup. They do not prove native context exclusion, waited-but-unclosed operation exclusion, sticky process poison, failed owner-close persistence, or serial resident-buffer reuse. P04's fake `ManagedMatmul` cannot test the guard added to the real native implementation.

Add a combined host fixture using actual `runtime.cpp` and `mlp_runtime.cpp` with fake C entry points, plus targeted direct runtime groups. Fault cases that permanently poison the process need separate invocations; a fake-state reset must not reset the production poison as a test shortcut.

### F1 / high / static-proof — cleanup observation is bounded by the common API

Common `vx_event_release`, `vx_queue_release`, `vx_buffer_release`, `vx_kernel_release` and `vx_module_release` normally return success after dropping a reference. `Buffer::~Buffer` ignores `mem_free` errors; `CallbacksAdapter::~CallbacksAdapter` ignores the backend `dev_close` result. `vx_device_release` has an exception translation boundary, but this does not expose ordinary ignored teardown return codes. A valid release return therefore does not establish that every backend cleanup step succeeded.

The bounded implementation should poison on **observed release errors**, and document that scope. Broad common-runtime release/ABI changes are unnecessary for this slice. Fault-injected release errors establish wrapper behavior only; do not relabel them as observed backend faults or physical recovery evidence.

## Exact lease and cleanup invariants to preserve

1. Reserve one managed process context before any `vx_device_open`; publish the owner only after setup succeeds. Clean, complete rollback returns the reservation. An observed rollback cleanup error poisons future work.
2. Validate submit arguments before taking the context's single operation lease. Acquire the lease before allocation/enqueue, with exception-safe rollback. A published partial submission owns its accepted prefix, staging, events, queue and context until drain.
3. Successful `wait` establishes completion only. It does not return the lease, free buffers or permit another submit. Incomplete wait/close retains every resource and both reservations.
4. A completed operation close releases events and queue before returning its lease. The queue destructor joins the worker, and the worker destroys command captures before signaling completion, including skipped commands. Preserve this order when buffers become context-owned.
5. Owner close while an operation retains the context reports incomplete. Owner destruction may drop its own reference; the operation then retains the context and performs final teardown on its completed close. Last-owner teardown failures must be included in the operation's returned cleanup and poison the process.
6. Cleanup errors are sticky and orthogonal to primary failure. Release calls happen at most once per handle; don't retry a possibly consumed handle after a failing release. Continue releasing remaining resources and preserve the first error.
7. No-work setup failures may retain today's already-closed returned operation. Return the acquired lease only after their rollback is complete and cleanup succeeded. Validation rejection before acquisition never changes another operation's lease.
8. `ExecutionResult::ok()` does not include `complete`. Tests and callers must inspect both. Destructor drain remains unbounded; it is not cancellation or a bounded-close guarantee.

## Minimal implementation recommendation

- Put the shared managed process reservation and persistent poison in the native managed layer; make acquisition/poison publication thread-safe even though individual owners remain single-caller. Keep current binding checks as a compatible outer guard, not the source of native safety.
- Add explicit context fields for operation ownership and sticky cleanup. Have the operation own a lease token/flag and return it exactly once after successful complete release. Do not infer lease availability only from `shared_ptr::use_count`.
- Retain the owner's close result after resetting `context_`; the last operation reports teardown when it is the final context owner. A requested close should latch a closing state if the frozen API contract adopts that rule; otherwise explicitly preserve today's retryable close semantics. Do not leave this implicit.
- Preserve per-operation allocation as the default/reference policy. Add an explicit opt-in policy for exactly `(8,4,8)` with context-owned A/B/D extents **128/64/128 bytes**, totaling **320 payload bytes**. Do not resize or silently grow it for another shape. Keep all existing six signatures and the MLP's `(16,8,16)` stage on the default path.
- Initialize all three resident buffers atomically with respect to publication, or roll back the partial workspace. Each call still creates its queue/events, copies owned inputs, rewrites A/B and all D poison, validates actual addresses/extents, launches the unchanged kernel, downloads and explicitly closes. A live operation borrows buffers while retaining the context.
- Add focused tests for competing direct/model contexts; queued/timed-out/partial/waited-but-unclosed operations; staging/allocation rollback; sticky non-timeout query failures; every observable release boundary; repeated close; owner destruction with retained operation; 32 serial changed-input calls; unchanged default signatures; and new-work rejection after poison with clean recovery only in a fresh process.
- Treat this as an external managed-contract change requiring independent review. Host tests alone cannot grant P06-A02/A03 or a speedup claim. Keep the accepted cold baseline unchanged and freeze the matched warm experiment before evaluation.

Findings about interleaving and shared simulator state are source proofs, not measured corruption.
