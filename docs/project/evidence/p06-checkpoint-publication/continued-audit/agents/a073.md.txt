## How main CI selects work

The `change-impact` job is advisory: it reads the classifier and policy from the
base revision, writes a summary, tolerates errors, and is not a dependency of
other jobs. R1 is therefore a review classification, not a test-selection switch
(`.github/workflows/ci.yml`, `change-impact` job).

The separate `plan` job chooses catalog cells according to the event and
toolchain-cache observation:

| Condition | Initial or expanded selection |
|---|---|
| Push with a toolchain cache hit | SimX / smoke cells |
| Pull request with a cache hit | SimX and processor rtlsim / smoke and full cells |
| Push or PR with a toolchain cache miss | All ordinary catalog drivers and tiers |
| Indeterminate push/PR diff with a restricted driver list | All ordinary drivers; existing tier choice remains |
| Scheduled run | All ordinary drivers and tiers |
| Manual dispatch | Explicit driver/tier inputs; the cache-miss override is not applied |

Changed RTL/config paths can add matching rtlsim/xrtsim/opaesim drivers. Static
inspection found zero intersections between the actual 97-path diff and
`ci/testcase.py::_DRIVER_PATHS`. The actual cache-hit result was not queried, so
this review does not assert which of the possible matrices this run selected.

Tier filtering selects which cells exist. A selected cell subsequently runs its
complete category/driver/XLEN marker group, not just the tier entries that caused
the planner to select that cell. The planner computes dependencies and shards
from those same complete groups. Thus “push defaults to smoke” does not mean
every executed test is a smoke-tier case (`ci/testcase.py::cmd_matrix`,
`cell_expr`; workflow `Plan matrix` and `Run cell` steps).

“All” is bounded: the explicitly opt-in `fpga`, `asic` and `timing_gpu` tiers are
excluded from ordinary matrix expansion. Their separate hardware/licensed/large
resource workflows are not implicitly qualified by a main-CI success.

## Execution and result interpretation

The workflow creates separate 32-bit and 64-bit build trees, runs `configure`,
builds software/tests, and transfers each build artifact to its selected cells.
Cells execute generated build-tree scripts with the matching `VX_XLEN`, strict
markers and any planned shard. Performance/model-parity shards cap independent
Verilator C++ build jobs at two; that cap does not change simulated parameters
or golden data. JUnit is retained even on failure. P04 model catalog cells add
source-matched preparation and their own retained packet
(`.github/workflows/ci.yml`, `build` and `tests` jobs).

A green job cannot establish absent coverage. The `complete` job rejects a
dependency result of `failure`; its condition alone does not reject `skipped`
or `cancelled`, and it prints the actual tests result. An empty planned matrix
intentionally skips setup/build/tests. Consequently, a successful `complete`
job alone is not evidence that every catalog cell or test body ran. Whole-run
job results and retained JUnit populations must support any concrete coverage
claim. The existing harness also preserves explicit opt-in skips and non-strict
`known_issue` expected failures, including tolerated XPASS; a green main-CI
workflow is not a zero-skip, zero-expected-failure certificate
(`ci/conftest.py::pytest_generate_tests`).

The separate Project Governance workflow remains responsible for the complete,
unfiltered, uninterrupted, zero-skip governance qualification and original
replay required before native admission. Main CI does not substitute for that
requirement, grant new phase acceptance, or establish physical FPGA/vendor
integration/performance results (`AGENTS.md`; `docs/continuous_integration.md`).
