# A053 — platform contract audit

**Verdict: no concrete blocker for the documented, named supported routes.**

Read-only inspection at code commit
`d31e8879e7c248b1a72615128882533ccdd0b3b4`. The repository contains concurrent
documentation/evidence work; this review did not modify it. The scope was the
Linux directory-path handle used by the checkpoint writer and the Linux pidfd

## Directory access remains write/search compatible

`ci/project/p02_matrix.py:97` opens the parent with `O_PATH | O_DIRECTORY`, not
`O_RDONLY`. The parent descriptor is used only to anchor create, stat, replace
and unlink operations and is then closed. `fstat`, buffered output and `fsync`
operate on the separately created ordinary file descriptor. The implementation
does not enumerate directory entries, open the directory for reading, change
its mode or add a permissions fallback.

The two unconditional regressions in
`ci/project/test_checkpoint_directory_access.py:27–60` keep the directory at
mode `0300` through actual initial publication/replacement and the P04
preparation consumer. They assert preserved mode and restore it in `finally`
before temporary-directory cleanup. The prior independent review retained at
`docs/project/evidence/p06-checkpoint-publication/reviews/directory-access.md`
records successful real checks under UID 1000, including rejection of the old
read-only open and continued denial when write/search permissions are absent.
This audit inspected that evidence; it did not rerun those probes. As already
recorded there, DAC-bypass privileges can weaken a mode-based negative control.

## pidfd use and skip behavior

The new `os.pidfd_open` and `signal.pidfd_send_signal` calls are confined to
`ci/project/test_p05_launcher_signals.py:109,118`. They retain an exact-child
handle for test cleanup. The installed production launcher does not acquire
pidfds; its new imports are standard-library `signal` and `threading`.

Neither that test module nor the directory-access test contains a skip
decorator, `skipTest`, `SkipTest`, a capability-based fallback, or a platform
guard that suppresses the assertions. Source/AST inspection found no skip
calls. The strict runner also treats skips as unsuccessful qualification
(`ci/project/governance_run.py:175–178,217–221`). Missing or denied pidfd
capability therefore fails the test; it cannot silently become a qualifying
pass.

A local attribute inventory observed Linux x86_64 CPython 3.12.14 with
`os.O_PATH`, `os.O_DIRECTORY`, `os.pidfd_open` and
`signal.pidfd_send_signal` present. This was an inventory, not a fresh syscall
or lifecycle test. The current source still requires its own hosted strict
qualification; workflow configuration alone is not execution evidence.

## Scope limit

The governance preparer's platform check does not currently probe O_PATH or
pidfd operation explicitly. An older or syscall-restricted Linux host may
therefore pass the initial platform screen and later fail the full suite.
This review found no demonstrated failure on a named supported route and does
not claim arbitrary Linux kernel/container compatibility. Extending readiness
diagnostics would be a separate task; adding skips or weakening the strict
suite would not establish compatibility. No non-Linux package, test, or
governance qualification follows from this audit.
