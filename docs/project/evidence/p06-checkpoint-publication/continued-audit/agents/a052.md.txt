1. Finish and commit the intended evidence/reference changes, check the remote
   head and preserve concurrent work, then publish the exact final candidate.
   The presently dirty checkout cannot supply strict revision qualification.
2. Observe that candidate's own complete governance job, including every required
   step, succeeds. Use that invocation's manifest as the authoritative population;
   5,547 is the current discovery count, not a hard-coded acceptance threshold.
   The 258-method development run and the base revision's 15 passing workflows
   do not qualify a later commit.
3. Let the final candidate finish uninterrupted. Governance concurrency is keyed
   by event/ref with `cancel-in-progress: true`; a later push on the same ref can
   cancel it. Even a later documentation/evidence commit changes the revision
   being admitted.
4. Obtain the unchanged original ZIP for the selected successful run and exact
   attempt. Select its expected digest from authenticated provider metadata,
   verify the downloaded bytes, and independently replay it using reviewed
   reader code and a clean trusted checkout of that exact final revision.
   Retain the reader identity, invocation, result and provider/run/attempt binding
   outside the trusted source checkout. Do not repair/repack the original or
   calculate its expected identity solely from the download.
5. Before native admission, the existing hosted checks additionally require the
   same repository, `master`, selected SHA, successful run/job/steps, exact
   artifact identity and unchanged reobserved provider/source state. A local
   replay alone does not authenticate the provider or grant native acceptance.
   Private control delivery, the public age recipient and actual resource
   admission remain separate prerequisites.

These are outstanding execution obligations already required by `AGENTS.md`,

## Separate audit-branch publication

The root subsequently proposed keeping the selected implementation and current
evidence on `master`, then publishing the remaining read-only agent ledger and
final provider/replay receipts on a separate audit branch. This preserves the
selected master commit's source identity when those later changes contain only
audit metadata. Any subsequently required production correction would still
need its own new master revision and complete qualification.

The branch filtering was inspected in every workflow using a non-executing YAML
parser, then the main CI planner was read directly:

| Workflow population | Push branch/path behavior | Effect of a docs/project-only audit-branch push |
| --- | --- | --- |
| Project Governance | No branch filter; includes `docs/project/**` | Runs on the audit branch. |
| Main CI | No branch or path filter | Runs on the audit branch. |
| P04 Native Model, two P05 installed workflows, ten P06 automatic workflows | Push branch filter is exactly `master`, with their existing path filters | Do not run on the audit branch. |
| Apptainer CI | No branch filter; only Apptainer/dependency-install/version paths | Not selected by a docs/project-only change. |
| P06 Qualified Warm | Manual dispatch only | Does not run automatically. |
| ASIC, FPGA and timing gates | Schedule/manual or manual only | No automatic audit-branch push execution. |

Governance concurrency is
`project-governance-${github.event_name}-${github.ref}` with cancellation enabled.
The audit ref therefore has a different group and does not cancel the master
invocation. Main CI has no workflow concurrency group; it starts separately.

This separation does **not** make audit-branch delivery CI-free. In `ci.yml`, a
push normally selects SimX/smoke. A toolchain-cache miss expands drivers and
tiers. An indeterminate base, including the zero `PUSH_BEFORE` on a first branch
push, expands driver coverage even with a cache hit. The audit branch can
therefore consume substantial CI resources despite containing only records.
No workflow change or gate relaxation was proposed or made by this review.

Hosted native admission remains restricted to a successful governance run whose
provider `head_branch` is `master`; a successful audit-branch governance run is
not a substitute for the selected master source's original.
