## Finding requiring correction

**F2 / high confidence / static-proof — ordinary cache-flush DCR reads make
the new preflight fail after the prime operation.**

The DCR wrapper in `hooks.cpp` records every `Processor::dcr_read` in its
single `reads` array and increments `read_count`. The application consumes
that array as exactly 264 MPM halves and requires `read_count == 2 * queries`
before each public counter query. These two contracts disagree with the
unchanged managed execution path.

The concrete source chain is:

1. `sw/runtime/ai/runtime.cpp` enqueues one launch followed by a 128-byte
   output read for every operation, including the prime.
2. `sw/runtime/common/queue.cpp::Queue::enqueue_read` routes that read to
   `Device::cp_submit_mem_read`.
3. `sw/runtime/common/device.cpp::Device::cp_ring_append_` marks the caches
   dirty on each launch and inserts one full `CMD_CACHE_FLUSH` before the
   following device-memory read. The flush clears those dirty flags.
4. `sim/common/cmd_processor.cpp::CommandProcessor::flush_cores_` issues one
   `vortex_dcr_read(VX_DCR_BASE_CACHE_FLUSH, cid)` per core.
5. `sw/runtime/simx/vortex.cpp::make_cp_hooks` forwards that call through
   `AsyncRun::invoke` to the same wrapped `Processor::dcr_read`.

The frozen configuration has one core and disables L2, L3 and VM. Thus the
first snapshot contains 66 MPM reads; the prime adds a cache-flush read, and
the next public query sees `read_count == 67` instead of 66. This is a valid
workload failure, not malformed evidence or a numerical mismatch.

There are **33 expected cache-flush reads per complete process**, in addition
to **264 MPM reads**, for **297 total DCR read entries**. Each output read
clears the dirty state, so the next operation's input writes and launch do
not introduce another boundary flush. The console drain uses the uncached
IO aperture. `Device::check_mmu_fault` skips its additional DCR reads because
VM is disabled in this contract. Unknown extra DCR routes must still fail.

The required correction is to retain and validate a separate complete
cache-flush trace, while preserving the exact 264 MPM halves and the unchanged
runtime workload. Do not disable flushing, silently ignore unknown reads,
or weaken the counter route/order checks.

Recommended exact observations were sent to root and the separately assigned
fix owner:

- Cache flush: address `0x000`, core tag 0, successful value 0; MPM address is
  `0x001` (`VX_types.toml`).
- Retain a global DCR sequence and completed-run count in both traces.
- Expected global flush positions: 67, then 134 through 165. Corresponding
  completed-run counts are 1 through 33.
- MPM global groups: 1–66, 68–133, 166–231, and 232–297.
- Snapshot cache-flush counts: 0, 1, 33, 33.
- Flushes may advance model ticks: `ProcessorImpl::flush_caches` calls
  `SimPlatform::tick` while draining. Require nondecreasing ticks, unchanged
  reset generation and selected class, and idle/not-running endpoints;
  preserve actual observations rather than requiring unchanged ticks.

The existing `AsyncRun` ordering ensures the kernel has finished before the
flush callback. The primitive DCR flush read starts and drains its work inside
the real call. The wrapper's surrounding observations should remain read-only.

scope.

  out of the app-facing interface. The fixed read array is bounded; the
  original wrapper rejects a full trace before indexing outside it.
- Compile-time guards require checked counters, timing mode, RV64 and one
  simulation worker. They do not substitute for validation of the separately
  built production model, which remains another review scope.

  `Processor::~Processor` deletes `ProcessorImpl`, whose destructor finalizes

  It serializes observation with the asynchronous run. The reviewed real
