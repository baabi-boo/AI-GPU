## Corrected cache-flush obligation

The actual managed operation enqueues one kernel followed by one output DMA.
`Device::cp_ring_append_` marks L1/LLC state dirty at launch and inserts the
full cache flush before the output transfer. The frozen profile has one core,
L2/L3 disabled and VM disabled; `CommandProcessor::flush_cores_` consequently
produces one additional DCR read at address zero and core tag zero per launch.
The subsequent transfer sees clean cache state. The console drain uses the
uncached aperture; VM fault DCR reads are excluded by the frozen configuration.

The reviewed correction retains these reads rather than changing the workload
or ignoring them. `hooks.cpp` separates MPM and cache-flush arrays while
retaining global `dcr_read_entries` and `completed_runs`. Unknown DCR addresses
increment violations and fail. Both arrays are bounded before indexing.

`main.cpp` checks all 264 MPM half replies and all 33 flush replies. The four
MPM sequence groups are 1–66, 68–133, 166–231 and 232–297. Flushes occupy 67
and 134–165, with completed-run counts 1–33. The snapshot flush counts are
0, 1, 33 and 33; each public query must add precisely two MPM replies and no
flush. Final entry/completion counts are 297, including both trace classes.

The flush endpoint checks agree with `ProcessorImpl::flush_caches`: its real
call can advance platform time while draining, so ticks must not decrease;
reset generation and selected MPM class must agree across the call, and both
ends must be idle/not running. The stricter MPM checks retain unchanged
ticks/reset/class and exact low/high tag routing. No reset, seed, diagnostic
replacement translation unit, cache bypass or workload reduction was added.

## Documentation finding resolved during review

**F1 / high confidence / static-proof — literal storage-immutable wording
overstated the public performance getter.** `Core::perf_stats() const` delegates
to `CoreImpl::perf_stats()`, which refreshes the derived `opds_stalls` aggregate
before returning the statistics. The hook reads cycles and instructions through
that public accessor. Ordinary MPM reads already use the same refresh; this
does not reset their event storage or establish a new numerical failure in the
fixed profile. It does mean that an assertion that no counter storage can be
written by any getter would be inaccurate.

Root corrected the design text while this review was active. The reviewed
design paragraph explicitly names the derived refresh, disclaims immutable
counter-storage observation, and preserves the unresolved complete backing
lifetime proof. The checked design file SHA-256 was
`7d627a9e5fd8f2bdd8ca855309cd59a8b312f7a3360c3c810629912d09f2f6d8`.
No implementation workaround or production-model change was requested.
