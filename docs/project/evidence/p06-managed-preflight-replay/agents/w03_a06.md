## Guard design and controls

The file guard uses an independently enumerated allowlist of 45 current reader
source paths, required current data files, the externally supplied archive and
source identities, and the pinned current archive parser. It permits directory
traversal only through those files' ancestors and tracks directory descriptors
so relative `os.open` and `os.stat` calls cannot escape the same allowlist.
It rejects write-capable opens, enumeration, and unrelated current source
reads. Wrapping `os.open` and `os.stat` preserves their actual platform
capability memberships; it does not bypass the production no-follow checks.

The original archive's recorded tool paths are read as data before installing
the guard. The test requires that at least one such tool file really exists on
the host, proves that reads of each collocated tool are blocked, and then runs
the unchanged complete replay successfully. Existing checkout source files and
directory-relative attempts provide additional controls. This avoids depending
on the absence of the producer files, or blocking the interpreter merely
because an unrelated trusted module happens to live nearby.

The full positive replay guards subprocess entry points, shell/process launch
APIs, `ctypes.CDLL`/`PyDLL`, and both ZIP extraction methods. Module loading is
restricted to the pinned current archive parser. An execution guard compares
its code object, filename, nested code, stack size, and qualified name against
an independent compilation of its pinned source. A forged loader result with
the same filename is rejected by that guard without executing its sentinel.
This is a control for the test guard, not a claim that arbitrary changes to
the running Python interpreter are inside the production threat boundary.

The current generated-header helper intentionally imports and executes the
hash-pinned **current** `ci/gen_config.py` before these replay guards are
installed. Its rendering uses pinned current configuration inputs. That trusted
initialization and the renderer's configuration-expression evaluation are
distinct from archived Python execution. The test does not prohibit those
trusted operations or claim to sandbox the interpreter itself.
