## Findings and handoff

### F1: inherited archive-loader source pin did not bind cached bytecode

Confidence: **high**. Evidence type: **static-proof**, with a disposable-tree
reproduction.

At the tested snapshot, the core called `p06_replay._archive_api`. That helper
hashed the pinned current `archive_reader.py` source, then used
`SourceFileLoader.exec_module`. Python could use a different cached code object
whose header matched the source's timestamp and size. A stale or poisoned
current-host cache was therefore outside the source-hash check.

The reproduction copied the real pinned reader into a temporary tree, created
its conventional bytecode-cache file with the interpreter's magic number and a
timestamp/size header matching that source, and marshalled a harmless code
object containing only `PYC_SENTINEL = True`. It patched the inherited helper's
root to the disposable tree and called `_archive_api`. The result was:

```text
pinned_source_matches: True
different_cached_code_executed: True
expected_archive_api_present: False
```

The cache header was constructed as:

```python
header = importlib.util.MAGIC_NUMBER + struct.pack(
    "<III", 0, int(status.st_mtime) & 0xffffffff,
    status.st_size & 0xffffffff)
cache.write_bytes(header + marshal.dumps(
    compile("PYC_SENTINEL = True\n", str(source), "exec")))
```

No production source or actual cache file was changed by the reproduction.
This requires a stale or poisoned current-host cache; it is not an injection
through a retained ZIP member. The narrow trigger supports F1 rather than a
claim that the archive itself can execute code.

I reported the defect before any edits and proposed direct compilation of the
same current byte string whose hash was verified. Root then implemented a
managed-only `_archive_api` with this behavior, left the inherited loader
unchanged, and updated the managed isolation expectation to require that the
file loader is never reached. Root assigned the repair and a matching-cache
regression to a subsequent independent reviewer. **The test passes in this
report precede that repair and do not claim to validate it.**

### F1: relative archive path in the initial CLI documentation example

Confidence: **high**. Evidence type: **static-proof**.

The initial design-document CLI example supplied a relative `--archive` path.
The CLI passed that `Path` unchanged to the pinned archive reader, which
requires an absolute canonical archive path. Following the example would
therefore reject the otherwise valid original before replay. I sent this to
root and the wave-5 documentation owner for correction. The assigned tests use
absolute paths, and this discrepancy cannot bypass validation.
