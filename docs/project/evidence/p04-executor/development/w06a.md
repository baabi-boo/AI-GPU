## Timestamp meanings

The following are F0 observations, high confidence, supported by static proof in
`queue.cpp`, `device.cpp`, `event.cpp` and `mlp_runtime.cpp`.

| Interval | What the implementation measures |
|---|---|
| `submit_ns - queued_ns` | Host interval from command timestamp capture until the worker has dequeued it and finished its external dependency waits. It includes enqueue/worker scheduling and preceding work, rather than isolating a hardware queue. |
| Transfer `start_ns - submit_ns` | Host worker bookkeeping before the transfer work body samples start. |
| Transfer `end_ns - start_ns` | Starts before acquiring the queue enqueue mutex. Includes any mutex wait, host staging allocation/copies, backend push/pull, command-processor submission/polling and staging cleanup performed by the transfer call. |
| Launch `start_ns - submit_ns` | Includes capability/descriptor work, device argument staging, acquisition of the enqueue mutex and explicit KMU DCR programming before start is sampled. |
| Launch `end_ns - start_ns` | The host-observed `cp_submit_launch()` call, including applicable MMU setup/fault checks, command retirement and console draining. It is not accelerator-only kernel latency. |

Launch end is sampled before the argument-slot scope guard releases its slot,
before destruction of captured work ownership, and before event profile/completion
publication. Consequently end is a command-body boundary, not an exhaustive
operation-release or event-observation endpoint. Successful operation and owner
cleanup are checked separately.

`vx::now_ns()` and the model's private `now_ns()` both use
`duration_cast<nanoseconds>(std::chrono::steady_clock::now().time_since_epoch())`.
The public API stores all four values as `uint64_t`; the model uses the same
host clock and representation. The qualified process therefore has one usable
ordering domain. Absolute steady-clock timestamps from different hosted machines
must not be aligned into a global timeline; the verifier compares dependent
stages and repetitions within the same application invocation.

## Ordering and observation predicates

- The worker waits dependencies before sampling submit. The consumer correctly
  requires the previous event's end to precede the next event's submit. It does
  not incorrectly require the next event's queued timestamp to follow completion:
  dependent commands can be enqueued while earlier work is active.
- All event enqueue timestamps must fall inside the corresponding model
  `submit_begin_ns`/`submit_end_ns` interval. Native event completion may occur
  after that host submission returns; the consumer does not impose a false upper
  bound on event end.
- The model waits and closes an operation before submitting its dependent stage.
  The consumer checks the prior final-read end against the next stage's submission
  begin, and checks the prior repetition's final-read end against the following
  repetition's create begin.
- The worker publishes profiling under the event mutex before marking the event
  complete. The managed wrapper only reads profiles after completion is established,
  preserves explicit query statuses and queried flags, and retains copied values
  before releasing events. A failed query does not turn default zeros into an
  observed profile.
- Equal timestamps and zero-duration intervals are legitimate. The app and consumer
  use non-strict timestamp comparisons and separately require successful event
  outcomes and successful observed queries. Failed or skipped work can have a
  valid profile, so query success alone never qualifies native success.
- The consumer checks exact unsigned types and bounds before time comparisons.
  Existing tests explicitly cover zero intervals, missing observations, reversed
  timestamps, out-of-submission enqueue values and dependency/repetition inversions.
  Those tests were inspected, not rerun as another broad suite.

## Host-duration and byte-accounting boundaries

`advance_ns` accumulates complete calls to `ManagedMlp::advance()`. It contains
nested submission, waiting, comparisons, bridge work, output assembly and
operation-close time. It is not exclusive CPU orchestration overhead. The stage
wait duration includes runtime completion/profile/output decoding; stage close
can itself wait. Model close accumulates explicit close calls. The RAII duration
updates complete before the caller reads the final trace.

The duration fields are observations with overlapping scopes, not a disjoint
partition of total process time. In particular, do not sum `advance_ns`, its
nested stage/bridge durations and event service intervals. Host waits overlap
worker/event service. Initial application fixture copying, module-file reading,
record serialization and all incidental runtime overhead are not individually
itemized by these model fields.

The reported 1,920 H2D and 768 D2H bytes per model run are the sizes of the nine
explicit tensor-buffer writes and three reads. They include destination poison
but exclude the argument upload, control/ring descriptors, console traffic,
module/setup traffic and physical transaction amplification. Output assembly
copies 256 host bytes. This matches the explicit-tensor scope of the runner and
record contract; these byte totals are not physical bandwidth measurements.
