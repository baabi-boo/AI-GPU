## State transitions and ownership

| Boundary | Reviewed behavior |
|---|---|
| Creation | Case identity, dtype agreement and output ownership are checked; input and reference arrays are copied before native work. Setup allocation failures return without publishing a partial model. |
| Submission | The operation is stored directly in the model's member. Partial failed submissions remain owned; absence of an operation after a nominally successful submission fails explicitly. |
| Incomplete wait | The same operation is retained, no output is consumed and no dependent stage is submitted. A normal timeout can resume without changing the stored first terminal error. |
| Partial submission plus timeout | Retention depends on `complete`, not on whether the primary error equals `VX_ERR_TIMEOUT`; the original allocation/enqueue error survives draining. |
| Completed stage | Actual output extent is checked before fixed-array copying; comparison and cleanup occur before the next native stage. Cleanup failure terminates inference even when arithmetic matched. |
| Trace-copy exception | `save_trace` catches allocation/other exceptions, invalidates the observation, records a terminal failure and leaves the active operation owned for explicit drain. |
| Terminal inference | Repeated `advance` cannot resubmit. A later cleanup failure remains separate from the original numerical/runtime status and cannot turn the result into successful inference. |
| Explicit close | Close sets the closing/terminal state before draining. It cannot run missing dependent work. Incomplete operation or owner close remains observable through `execution.complete=false`. |
| Resource accounting | The initial query follows owner setup; final counters are checked after operations release and before owner close. Query errors or changed counters prevent a successful result. |

`MlpResult::terminal` and `ExecutionResult::complete` intentionally describe
different facts. A failed inference may still own pending work. Conversely,
successful draining does not prove successful inference. The explicit
`MlpResult::ok()` predicate includes terminal success, execution statuses and
completion; consumers must use it rather than only the execution result.

The production `ManagedMatmul::submit` boundary is `noexcept`; its allocations
occur before its internal enqueue helper. Review did not identify a reachable
post-enqueue exception escaping that boundary. A mock that throws through a
`noexcept` API would not establish a production executor defect.

The per-call timeout is documented as a bound on each wait/drain, not a total
model-call deadline. Destruction drains indefinitely. The native application's
outer process deadline and retained-owner behavior are separate obligations;
this review does not claim bounded cancellation or physical-device recovery.

## Numerical lineage and observed data

Source inspection confirms that the hidden projection receives explicitly
little-endian X/W1 bytes. Actual hidden words are copied and compared before
`prepare_mlp_hidden` is invoked. Both output projections receive slices of
`trace_.bridge_bytes`, which are the actual helper result; their expected
arrays are used only for comparisons. Output assembly copies the two observed
row blocks in order and performs the final exact comparison.

Observed-data flags are set only after successful extent/bridge processing;
they deliberately do not mean the numerical comparison passed. A mismatching
actual hidden value remains retained for diagnosis. Native sequences are
`0,1,2`; row ranges and shapes match the agreed record contract. There is no
CPU matmul fallback or conditional reference substitution in the executor.
