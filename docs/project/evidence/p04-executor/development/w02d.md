## Reviewed behavior

- The new internal binding flag defaults to false. That path still passes a
  null queue-info pointer and makes no profiling API calls. Opt-in queue creation
  uses the existing structure size, null extension pointer, normal priority and
  `VX_QUEUE_PROFILING_ENABLE`; no installed header or API changes.
- The context owns the flag, and each operation copies it into its trace.
  The extension adds no new allocations during completion or profile capture.
- `Queue::worker_loop` publishes the event's profile before marking completion.
  Managed waiting first confirms the final event's counter, and the queue is
  FIFO. Profile retrieval therefore occurs after actual completion and before
  any event handle is released.
- Only indices below the actual event count are queried. Timeout returns before
  that loop. Uncreated, disabled and incomplete slots retain `queried=false`,
  `VX_ERR_NOT_SUPPORTED` and zero timestamps. Repeated waits and closes do not
  re-query completed work.
- A failed query retains its status and discards any payload written by the
  API. It cannot turn a default or garbage timestamp into a successful profile.
  The original primary and cleanup outcomes remain independent.
- Failed or skipped commands can legitimately have profiles. Their event
  failures remain visible, so consumers must check event outcomes as well as
  successful profile-query status. Profiling alone is not a launch-success
  predicate.
- The discovered test group exercises default-disabled operation, both formats,
  timeout/resume, every profile-query failure, partial enqueue boundaries,
  asynchronous failure propagation, persistence after release and idempotence.
  The added mock symbol covers the only existing source-level harness linking
  the production managed wrapper directly.

## Timing interpretation observation

F0, high confidence, static proof: the existing runtime obtains timestamps from
`std::chrono::steady_clock`. In `Queue::enqueue_write` and `enqueue_read`,
`start_ns` is sampled before acquiring `enqueue_mu_`; those command intervals
include any mutex wait and host-observed command-processor transfer service.
For launch, argument staging, control programming and lock acquisition precede
`start_ns`, while `end_ns` follows launch retirement. The separate
`submit_ns` → `start_ns` interval retains preparation time.

The consumer must describe these as host-runtime observations and preserve all
four timestamps. Zero-duration intervals can be valid. These values do not
establish physical DMA duration, GPU cycles or physical-board latency, and
overlapping host wait intervals must not be summed with command profiles.
