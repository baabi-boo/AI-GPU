## Scope and implementation

Implemented `ci/project/p04_execution_records.py` and its independent synthetic
corruption suite in `ci/project/test_p04_execution_records.py`. The consumer
implements the agreed `mlp_execution_records_v1.md` schema and matches the live
native serializer's public trace/stage/dispatch fields.

`verify_output(text, case, iterations, binding_id, *, backend, source_revision,
fixture_sha256)` returns the verified JSON records. It assumes that the caller
has independently validated the frozen case and bound source/compiler/binary
identities; parsing an arbitrary supplied record never authenticates execution.

The consumer checks:

- Exact field inventories, canonical word/byte encodings, bounded JSON/logs,
  duplicate keys, strict integers/booleans, failure text and success framing.
- Expected model/fixture/source/backend/binding identities, one or two ordered
  repetitions and distinct poison values.
- Every actual hidden, bridge, native output-block and assembled output word.
  Hidden errors that ReLU would hide and signed-zero changes remain failures.
- Actual submitted X/W1 and actual bridge-slice/W2 bytes; graph shapes, row ranges,
  order, byte counts, launch/write/read counts and independently reconstructed
  56-byte arguments with aligned, disjoint and nonwrapping allocation ranges.
- Separate successful submission, observed completion, operation cleanup,
  model result and owner cleanup. Successful asynchronous submission may remain
  incomplete; completion and cleanup may not.
- All five actual event outcomes and observed successful profiling queries per
  launch, monotonic profile values, enqueue timestamps within submission,
  predecessor-event/stage/model-repetition ordering, and restored resources.

Zero-duration intervals remain legal. Queued timestamps may overlap preceding
execution; a dependent event's submission must follow predecessor completion.
The profile domain remains host `steady_clock`, not physical device latency.
