## Conclusion

The proposed owning state machine is a sound fit for the current API if it
separates inference progress, terminal inference failure and resource draining.
Retaining one active `MatmulOperation` inside the model owner permits bounded
returns without destroying live work. The existing runtime's destructor drains
indefinitely; a local temporary owner cannot implement bounded cancellation.

## Required state-machine invariants

- Copy case inputs, weights and reference arrays before the first submission.
  References are comparison-only; actual H and bridge bytes own subsequent data.
- Check both `result.ok()` and `result.complete` before consuming output. A
  successful submission normally has `complete=false` and no available output.
- Retain every returned operation, including partial failed submissions. A
  partial enqueue failure can remain the primary error while a later drain
  times out. Therefore retention depends on `complete`, not on comparing the
  primary status to `VX_ERR_TIMEOUT`.
- A transient timeout leaves the stage pending. A subsequent `advance` resumes
  the same operation without a second submission, reference comparison or host
  transformation. Record the timeout without turning a later successful wait
  into a fabricated first-attempt success.
- Preserve the first terminal inference error independently from cleanup
  results. A successful `close` cannot overwrite a hidden-value mismatch,
  bridge rejection, failed event or failed output-row comparison.
- Explicit `close` prevents further dependent launches. It may drain the active
  operation, but it must not finish the graph as a side effect. After close,
  `advance` cannot restart the case. Repeated success/failure/close calls are
  idempotent and cannot replay a completed stage.
- Copy actual outputs and trace while the operation exists, close it, inspect
  cleanup, and release it before launching the next stage. A cleanup error
  terminates the case even if that operation's numerical output matched.
- Query the final device-memory counters after all case operations release but
  before the managed owner closes. Compare to the baseline captured after
  owner/module setup. Keep the memory-query status explicit.
- Document whether an `advance(timeout)` bounds the entire call or each wait.
  A whole-call contract should use a monotonic remaining-time budget, including
  saturating handling of the infinite timeout; blindly applying the same finite
  timeout to three waits can exceed the advertised bound.

## Exception and result-storage paths

`MatmulTrace` includes a `std::string`, so copying it may allocate. Copying output
vectors and growing a vector of stage records may allocate too. A `noexcept`
executor must not allow these failures to terminate the process or destroy a
local in-flight owner. Prefer fixed-size model outputs and three preallocated
stage records, initialize strings and identifiers before dispatch, and catch
`std::bad_alloc` separately from other exceptions. Preserve any owned operation
for explicit draining on a copy/reporting exception.

The existing `ManagedMatmul::submit` allocates/copies inputs before its internal
noexcept enqueue helper. The proposed executor should preserve this ordering;
the audit did not establish an existing post-enqueue C++ exception bug in that
runtime. Throwing through a runtime C API mock is not a substitute for a
reachable production failure scenario.

Model completion and resource completion need distinct meaning. A failed model
can still have an incomplete drain; a drained operation is not proof that the
model produced valid logits. Actual arrays need validity flags or stage states,
because default zero arrays must never masquerade as observed zero-case output.

## Minimal adversarial harness additions

Extend model-level mocks while retaining the existing P03 runtime tests. These
tests demonstrate host ownership/control flow only, never GPU arithmetic.

| Group | Injection and required observation |
|---|---|
| Happy graph and copied ownership | Both formats; mutate caller inputs and references after create; observe exactly three launch shapes, actual bridge slices, distinct row blocks and unchanged copied inputs |
| Timeout at every stage | Delay each of the three native operations; return promptly with live resources; resume the same operation once; no duplicate launch or bridge; output validity appears only after completion |
| Partial submission plus timeout | Fail an enqueue after at least one event exists, then time out draining it; retain ownership even when primary reports the enqueue failure; no dependent launch; later drain restores counters |
| Asynchronous dependency failure | Fail each write, launch and read event at each stage; preserve first primary status, suppress dependent stages and logits validity, and restore resources |
| Comparison and bridge stops | Corrupt a negative hidden word that ReLU would erase; corrupt bridge comparison; corrupt first output block; each stops before the next native submission and retains actual bad data |
| Late failure | Fail the third matmul or its read after two successful native calls; retain earlier records, report no valid final inference, release every operation |
| Cleanup and memory queries | Inject release failure and baseline/final memory-query errors; record cleanup separately, never turn them into success through later idempotent close |
| Close and repeated calls | Close before advance, while pending, after failure and after success; close never launches a missing stage, repeated advance/close never replays work, no premature buffer release |
| Host allocation failure | Fail model allocation/owned-input setup before dispatch; where reporting copy can allocate, inject that reachable failure after completion and verify retained ownership and drain |
| Repetition | Recreate and run enough cases to expose a per-case resource leak; check memory before owner close and complete handle counts after owner release |

The existing fake runtime already supplies queue/event ownership, delayed work,
enqueue failure ordinals, asynchronous failure ordinals, cleanup failure and
resource counters. Its current launch callback writes synthetic incrementing
words, so the model harness needs stage-specific response data and explicit
captured A/B byte observations. Expected hidden/bridge arrays must not themselves
be accepted as proof that the executor passed actual prior output onward.
