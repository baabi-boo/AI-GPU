## Finding and implementation direction

P04-T02 is the next bounded development step. Existing P03 supplies the exact
native kernel, managed runtime, compiler-record validator and bounded execution
runner needed for the fixed network. Reuse that kernel and its accepted
`p02-tfr` profile. Add a model executor, a small native regression host, a strict
model-record verifier and a dedicated trusted runner; no new hardware arithmetic,
installed ABI or kernel argument layout is required.

Do not call `p02_matrix.select_cases` for P04: it requires 88 P02 cases, a
44/44 format split and the old matrix counts. Similarly, P03's `verify_output`
only validates one matmul per result and does not establish graph dependency,
bridge lineage, row-slice placement or full-model coverage. Both need small
P04-specific counterparts; historical P02/P03 parsers should stay unchanged.

## Build/configuration obligations

Create separate fresh build trees for `simx-fp16`, `simx-bf16`, `rtlsim-fp16`
and `rtlsim-bf16`. Configure RV64 with `--profile=p02-tfr`; the current runner's
generated identity contract also fixes `--osversion=ubuntu/focal`. Application
and backend builds must receive identical format flags:
`-DITYPE=fp16` or `bf16`, `-DOTYPE=fp32`, `-DKUNROLL=1`.

`sw/common/ai_matmul_profile.h` checks one cluster/core, four warps of four
threads, issue width one, 16 KiB local memory, TFR/STD native arithmetic, PE
ratio one, TCU latency four, DSP usage disabled and ordinary dense 16-bit WMMA.
All other format/scaling/sparse/WGMMA banks and matrix load/store remain off.
Keep the original profile bytes and their frozen digest unchanged.

The generated app `config.stamp` consists of three independent records: kernel,
host and linker. Runtime and arithmetic backend stamps are separate. Native
RTL additionally has distinct Verilator and host-shim records. Preserve the
accepted record parser's treatment of those roles; never pool macro flags
across them. Reproduce both generated C++ and Verilog headers, then compare
their exact bytes before execution.

`configure` already discovers new test directories through its `tests*` pattern
and copies their `Makefile`, `*.mk` and `*.in` files. A new
`tests/regression/ai_mlp/Makefile` therefore needs no configure surgery. C++
sources remain in the source tree and the generated Makefile points to them
through `VORTEX_HOME`. List every new header as an explicit prerequisite so
editing the fixture adapter or executor header rebuilds the host binary.
Do not add this strict-profile app to the generic default regression list,
which builds apps with default macros.

## Smallest native app and trusted-runner boundary

The app should accept a frozen case ID, module path, qualified binding ID and
one/two iterations. Generate a compact C++ fixture adapter deterministically
from the validated JSON. Verify adapter bytes against the canonical fixture in
host tests and bind them to the native runner's source inventory. Keep expected
H/R/Y arrays solely on comparison paths.

The trusted runner should:

1. Validate the unchanged P04 fixture contract and the new adapter's identity.
2. Freeze all ten case IDs and the selected backend/format/repetition matrix.
3. Configure/build current trees and validate separate compiler records.
4. Bind the actual module, host executable, runtime/backend libraries, source,
   profile, fixtures and dependencies into a SHA-256 qualification ID.
5. Set the exact driver and runtime-library search directory, run each selected
   case with bounded commands, and parse its actual model records.
6. Verify binary/source/tool identities before and after execution; preserve
   interrupted or failed records separately from later attempts.

A user-supplied 64-digit identifier is not qualification. The C++ wrapper's
capability queries cannot prove native arithmetic selection or binary identity.
Actual evidence must retain the runner's validated binding and the matching
record body, not only a plausible-looking ID in stdout.

## Catalog gap

No `ai_matmul`/P03 native case is currently registered under `ci/testcases`.
P04 should add a dedicated category rather than assuming the governance unit
suite invokes native execution. The catalog supports `via: script` with a
`run:` command, so a thin generated-build script can invoke the trusted runner
and propagate failures without adding a new CI mechanism. A direct blackbox
case with a static qualification ID is insufficient for formal evidence.

The category should explicitly declare RV64, both relevant drivers, format
coverage and touched paths. Include the executor, host bridge, fixture adapter,
runner, record verifier, model fixture/manifest, managed kernel/runtime and
profile/config dependencies. Expand governance workflow paths to cover the new
app and catalog entry if those paths are otherwise absent. Add source tests
that check this trigger coverage. Keep existing cases and thresholds intact.

## Timing/accounting gap

`ManagedMatmul` currently calls `vx_queue_create(..., nullptr, ...)`, so queue
profiling is disabled. `MatmulTrace` has no timestamps. Submit/wait wall time
alone cannot separate transfer work from native launch work.

The existing public runtime already exposes `VX_QUEUE_PROFILING_ENABLE` and
`vx_event_get_profiling`; no installed API change is necessary. A small opt-in
internal binding option plus per-event profile records can capture the three
writes, launch and read before events are released. Inspect profiling-call
statuses and monotonic timestamp ordering. Default behavior can remain
unchanged for P03 consumers.

These timestamps are host monotonic queue-command intervals. In
`sw/runtime/common/queue.cpp`, write/read intervals wrap synchronous CP memory
operations; the launch interval includes launch argument/control work. Report
that scope explicitly. They are not device-only execution time, physical DMA
time, hardware bandwidth or FPGA latency. Separately record bridge,
comparison, assembly and overall host durations without pretending overlapping
intervals are additive. Explicit tensor traffic is 1,920 H2D and 768 D2H bytes
per completed case, excluding argument/control/module traffic.

## Validation performed and limits

app/Makefile, generated build rules, fixed profile, catalog schema and runtime
event-profiling implementation. Inspections used bounded `sed`, `rg` and Git

`ci/testcases/runtime.yaml` and `ci/testcases/sw.yaml`; subsequent catalog
inspection used discovered paths. No source code was edited, no build or GPU
execution was attempted, and no acceptance gate is claimed.

The inherited runner requires a 15 GiB disk reserve and 6 GiB available-memory
budget, fresh nonoverlapping work/output roots, prepared pinned toolchains and
identified softfloat/Ramulator dependency libraries. Resource adjustments, if
needed for a new bounded runner, must be declared before execution and never
be presented as proof that missing tools or hardware exist. Native processor
RTL remains distinct from AFU/vendor integration and physical hardware.
