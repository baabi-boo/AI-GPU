committed source.** This is source review of the model/app boundary against the
actual managed operator contract. It does not establish native execution,

obligation 5 of `mlp_execution_records_v1.md` says that an incomplete result

## State and lifetime review

| Boundary | Reviewed behavior |
|---|---|
| Creation | Model/case allocations and qualification-ID copies precede native owner creation. Setup errors do not publish a partial model. The actual owner-create implementation publishes only success with no pending operation. |
| Partial submission | Submission writes directly into the model's operation member. An enqueue error after earlier accepted work returns that operation and leaves `complete=false`; model failure is terminal but ownership survives for explicit draining. |
| Immediate submission failure | The actual operator may return an already closed operation even when no event was enqueued. The model still retains and closes it safely; a null returned operation cannot be treated as a successful submission. |
| Transient timeout | Timeout is merged into the returned observation, not the persistent model error. The same stage/operation resumes, without consuming output or resubmitting. The original primary error of a failed partial submission takes precedence over a later drain timeout. |
| Unestablished completion | The operator checks the event value before declaring completion. A non-timeout error without established completion remains owned. The model stops inference and the app proceeds only to draining. |
| Trace-copy exception | A copy failure invalidates the trace and records a terminal host error. It does not release the pending operation. A later successful trace copy cannot erase that earlier model failure. |
| Comparison and cleanup | Actual output extent is checked before copying. Hidden/bridge/output comparison failure stops dependent work. A cleanup error after numerically successful output also terminates inference; primary and cleanup errors remain separate. |
| Explicit close | Close marks the model as closing before draining and cannot run the remaining graph. Operation ownership is reset only after complete draining. Owner-close incompleteness remains visible in subsequent results. |
| Late resource/owner error | Resource-query failure or changed allocator counters overrides an otherwise successful model result. An owner-release error after `advance()` success is retained in the trace and prevents application success. |
| Stage bounds | The stage advances only after operation release. At stage 3 there is no active operation, so close's early return avoids indexing beyond the three native records. |

The actual managed operator performs potentially throwing host allocations before
its internal enqueue helper. Its enqueue path is `noexcept`; review did not find
a reachable C++ exception after enqueue that would bypass the ordinary returned
operation. A mock throwing through that `noexcept` boundary would not reproduce
a supported production transition.

`terminal` describes inference state, while `complete` describes outstanding
ownership/drain state. Numerical mismatch can have successful execution-status
fields and successful draining; callers must still check `MlpResult::ok()` or
the model's final result. The native application checks both its inference
result and the post-close trace, along with owner closure and profiling.

## Application failure and deadline boundary

The app uses one-second waits and retains the model across retries. After a
terminal failure it records diagnostics and drains; it never calls `advance`
to finish a failed graph. A `P04_RESULT` is emitted only after inference,
operation cleanup, owner cleanup and profiling predicates pass. The final
`PASSED!` follows all required repetitions. A failed later repetition therefore
cannot turn earlier successful records into a complete passing process.

A serializer or output-stream exception before explicit cleanup unwinds through
the model destructor. That destructor deliberately drains indefinitely. Likewise,
the app's repeated finite-wait loop has no standalone aggregate deadline. The
trusted runner supplies the external per-command deadline and process cleanup;
neither the app nor the model claims bounded cancellation of a stalled physical
device. These limitations are already stated in the API and executor evidence.

Memory counters bracket tensor operations after owner/module creation and before
owner destruction. Successful owner cleanup is required separately. The counters
do not prove post-owner memory balance or exhaustive host-heap leak freedom.
