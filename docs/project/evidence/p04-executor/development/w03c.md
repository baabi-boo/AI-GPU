## Implemented scope

- Added `.github/workflows/p04-model.yml`: four variants (`simx`, `rtlsim`
  crossed with `fp16`, `bf16`), at most two concurrent jobs, two build jobs,
  two execution iterations, and a 90-minute hosted-job timeout. The runner's
  complete format-specific case set supplies all five fixture families.
- Triggered qualification for relevant implementation, workflow, fixture,
  contract, and pinned-input changes on pushes to `master` and pull requests,
  plus explicit dispatch. Permissions are `contents: read`; checkout does not
  retain credentials. There is no privileged pull-request trigger, secret use,
  shared-cache write, or allowed-failure qualification step.
- Added `ci/project/p04_ci_prepare.py`, reusable once per native catalog cell
  with `--format both`, or once per dedicated format variant. The helper emits
  `evidence/preparation.json` before formal execution can begin.
- Restored existing pinned toolchain and dependency caches with read-only
  restore actions. Accepted toolchain identities are the resolved `VERSION`
  revision and either the existing `lite` or `full` profile. Dependency identity
  must exactly match the `third_party/Makefile` and `.gitmodules` cache key.
- Checked out recursive submodules before restoring dependencies, then checked
  their provenance after restoration. The helper relocates untracked cached
  `tools` to a fresh outside-source destination before requiring a clean source
  tree at exactly the workflow SHA. It does not add source exclusions or hide
  dirty files.
- Enforced the preparation resource prerequisites: 15 GiB free disk reserve,
  4 GiB available memory, two build jobs, and the runner's 16 MiB command-log
  cap. The helper inventories actual tool and dependency hashes separately from
  cache identities. Formal execution uses fresh sibling work and evidence
  destinations outside the source and never selects development mode.
- Retained job identity, preparation results, and all available native evidence
  with an artifact-upload step that runs on failure as well as success.

The shared setup action, general CI workflow, and catalog belong to separate

## Failure behavior and limits

A missing pinned cache fails qualification with an explicit remedy: warm the
existing CI setup job with the same pinned inputs, then rerun qualification.
This dedicated job does not build a complete toolchain or cached dependencies.
It installs only the existing baseline host dependencies when both caches were
restored.

Before relocation, the helper verifies that `tools` contains no tracked source
files, that HEAD equals the requested workflow SHA, that the destination is
fresh, and that source and destination share a filesystem. Relocation is an
atomic rename. A different filesystem produces a retained blocker requesting
a fresh outside-checkout sibling on the source filesystem; the helper does
not perform a potentially large unmonitored copy. A provenance failure after
relocation retains the relocated tools for inspection and blocks execution.

Preparation success is explicitly `native_execution: not_run` and
`acceptance_claimed: false`. These files do not establish numerical execution,
model acceptance, vendor hardware results, or resolution of unrelated DSP
area-gate failures.

## Focused validation

Performed against the shared, uncommitted development checkout; these checks
are development evidence and are not a clean-source native packet.

1. Parsed the workflow using PyYAML `BaseLoader` and asserted the four-variant
   matrix, matching push/PR path filters, `master` push branch, hosted runner,
   90-minute timeout, two-job concurrency, read-only permissions, two read-only
   cache restores, absence of cache saves, and unconditional artifact upload.
2. Checked all five embedded shell blocks with `bash -n` and parsed the embedded
   initialization Python with `ast.parse`. Parsed the preparation helper with
   `ast.parse`; earlier `python3 -m py_compile` checks also passed.
3. Ran eight isolated preparation guard probes using disposable Git checkouts
   and controlled mocked resource/tool inventories. The positive relocation
   case passed. Dirty provenance, insufficient RAM, insufficient disk, tracked
   tools, a wrong expected SHA, an occupied destination, and symlinked cache
   tools all blocked. The probes checked relocation timing, preserved marker
   content, exact retained JSON, both-format selection, and the absence of any
   native-execution or acceptance claim. They did not invoke simulator tools.
4. Exercised a real missing-cache invocation: it returned failure and retained
   a blocked receipt with the cache remedy, without relocating tools. A second
   invocation refused to overwrite that receipt.
5. Checked both authored implementation files for trailing whitespace. All
   focused checks passed.

During validation, the workflow root was moved from job-level `runner` context
to runtime `RUNNER_TEMP` initialization through `GITHUB_ENV`, because the
GitHub context availability table excludes `runner` from job-level `env`.
Reference: <https://docs.github.com/en/actions/reference/workflows-and-actions/contexts>.
