## F2-01: impossible nested durations pass

In actual `simx-fp16`, `fp16-seeded_dense`, iteration 0, the recorded
`advance_ns` is 40,608,744 and the first native stage's `wait_ns` is 20,034,865.
Changing only `advance_ns` to zero is accepted. A second mutation sets each of
the three stage wait durations to `advance_ns // 2`. Each individual duration is
less than the parent, but their sum, 60,913,116 ns, exceeds the enclosing
40,608,744 ns. That also passes.

`ManagedMlp::advance()` creates its outer `Duration` before submission, waiting,
comparison, operation release, bridge and assembly work. Those host work
intervals are sequential and nested inside the successful call or accumulated
calls. The RAII duration destructor updates `advance_ns` before the caller can
serialize the trace. Thus both mutated observations contradict the producer.
This conclusion does not require a physical clock rate or minimum nonzero
duration.

Recommended correction: for a successful completed record, require the
saturating sum of the three submission elapsed times, stage waits, stage
comparisons, stage operation closes, bridge, bridge comparison, assembly and
output comparison to be no greater than `advance_ns`. The producer uses
saturating uint64 accumulation. Exclude model creation and owner/model close,
which have separate scopes; also exclude all event intervals, which overlap
host waits. Preserve valid equal timestamps and observed zero durations.

## F2-02: sequential enqueue timestamps can reverse

The same actual record begins with A/B enqueue timestamps
`[171226149934, 171226152609]`. Swapping them to
`[171226152609, 171226149934]` passes the auditor, including its full packet
path. Both remain inside the stage submission interval and each event's own
queued/submit/start/end ordering remains valid, so the existing predicates do
not detect the contradiction.

`runtime.cpp` enqueues A, B, destination poison, launch and read in that order
from the single model caller. Each queue API records `queued_ns` from the same
host steady clock before returning to that caller. These five enqueue timestamps
must therefore be nondecreasing. The queue worker may execute an earlier command
while the caller enqueues a later command, so the correct additional condition
is adjacent **enqueue-to-enqueue** monotonicity; requiring the earlier event to
finish before the next enqueue would reject valid asynchronous execution.

its matching mutated log hash is
`5b96d4f8a2600adee2f7aec8d66c681dc3bf476a8969e81279af56ce5aa9cdfc`.
