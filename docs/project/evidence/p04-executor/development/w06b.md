## Observed resource contract

| Boundary | Observed behavior and limits |
|---|---|
| Preparation | Requires at least 4 GiB available RAM and 15 GiB free on source/workspace before moving restored tools. Unknown available RAM blocks. |
| Runner preflight | Checks source/tools/work/output free disk and at least 4 GiB available RAM before native commands. |
| Each monitored command | Receives a 4 GiB process-group RSS budget, 15 GiB disk reserve, 16 MiB retained-output cap, and its explicit deadline. Source/work/output are supplied as monitored resource paths; working/log directories are included by the monitor. |
| Build concurrency | CLI accepts one or two jobs. The clean environment and make arguments consistently set `MAKEFLAGS`, `THREADS`, `CMAKE_BUILD_PARALLEL_LEVEL` and `-j` to the selected value. Hosted/catalog invocations select two. This is requested build concurrency, not an OS-wide process-count quota. |
| Command deadlines | Configure is 120 seconds; compiler-version/header probes are 30 seconds; native builds use the selected maximum-1,800-second value. Both hosted/catalog commands explicitly select 180 seconds per case invocation, which contains two model repetitions. |
| Workflow bounds | Dedicated workflow uses two concurrent matrix jobs and a 90-minute limit per job; general-CI test jobs retain their existing 180-minute limit. These are distinct from each command's resource monitor. |

**Deadline precision:** the inherited CLI parser accepts
`--run-timeout-seconds` from 1 through 1,800 seconds, with default 180. Therefore
180 seconds is the frozen hosted/catalog invocation and documented reproduction
setting, not the public CLI's absolute maximum. Qualification review must check
actual command receipts against that selected budget. No successful packet
automatically accepts a phase.

RSS and disk limits are **polled budgets**, not cgroup, address-space or filesystem
quotas. The default polling interval is 0.1 seconds; transient peaks can be missed
and a child may cross a threshold before it is terminated. RSS sums readable
non-zombie processes in the command's process group, may count shared pages more
than once, and excludes page cache. Descendants deliberately leaving that group
are outside containment. The runner preserves these limitations in every report
and the process helper preserves them in every command receipt.

The parent Python process's inventory/hash/checkpoint work and workflow cache,
checkout and apt steps are outside this command RSS monitor. No claim is made
that an entire CI job is restricted to 4 GiB. The retained log cap is enforced
when bytes are written: excess output is discarded, the command fails with
`log_limit`, and the retained prefix is hashed. This bounds each command's raw log,
not all workflow logs or the complete evidence directory. JSON checkpoints have
a separate 16 MiB serialization bound.

## Deadline and cleanup path

Commands start in a new POSIX session/process group with stdin closed. Their
combined output is drained without blocking the watchdog. A timeout, polled
resource breach, output overflow, interrupt or monitor failure stops the group.
The stop sequence sends SIGTERM, allows a one-second grace, sends SIGKILL, waits
up to two seconds to reap the leader, and allows a quarter-second drain grace.
These grace periods and monitoring overhead are additional to the requested
command deadline; the implementation does not claim an exact wall-clock cutoff.

A leader returning zero while descendants remain alive is a failure. A nonzero
exit, missing process completion or incomplete cleanup cannot pass the P04
command guard, even if the log contains valid-looking model success records.
Per-command outcome, exit code, reason, sampled peak RSS, cleanup flag and retained
log identity are checked and checkpointed before output verification.

The app's individual waits are finite, but its retry/drain loops and model
destructor can wait indefinitely for a backend. Retained ownership is correct;
it is not bounded device cancellation. `run_bounded` supplies the native command
deadline and group termination. An uninterruptible kernel task, process-group
escape, hard runner termination or host loss remains outside a guaranteed
cleanup/evidence-retention promise.

## Mutation and evidence boundaries

Preparation validates safe outside-source roots, exact cache identities, source
revision, resources, untracked tool ownership, a fresh destination and the same
filesystem before atomic tool relocation. It does not copy/rebuild tools on an
EXDEV failure. Dirty-source, recursive-submodule, tool or dependency validation
can subsequently block; in that case relocated tools remain in the outside
workspace and `tools_relocated` identifies the action. There is no rollback that
would obscure the failed attempt. Source/fixtures/dependency binaries are not
rewritten by this helper.

Fresh work/output roots and exclusive log creation prevent overwriting an older
packet. Preparation refuses an existing receipt. The native runner records a
command before starting it, retains monitor failures, and changes its report to
failure/blocked on validation errors. Dedicated and catalog workflow uploads use
`always()` and distinct run-attempt artifact names. This preserves available
evidence on ordinary failures; it cannot guarantee an upload after fatal host
loss or exhaustion of the outer workflow deadline. The initial job receipt is
created before cache preparation to distinguish unstarted native execution.

The dedicated workflow restores caches without saving them. The general model
cell uses the unchanged shared setup action with its default `prepare=false`;
only the existing separate setup job warms missing caches. Cache restoration and
host dependency installation precede the model monitor and have their own CI
scope. The runner itself installs no dependency and checks identified tools and
dependencies for drift before/after native work.
