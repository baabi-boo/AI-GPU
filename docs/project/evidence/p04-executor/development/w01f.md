## Timing interpretation correction

`sw/runtime/common/vortex2_internal.h::now_ns` uses `steady_clock`.
`Queue::worker_loop` assigns `submit_ns` after waiting for dependencies.
In `Queue::enqueue_launch`, arguments are staged and KMU/DCR configuration is
written before `start_ns` is assigned; `end_ns` follows
`device_->cp_submit_launch()` retirement.

Consequently, launch `end_ns - start_ns` is host-observed launch-command
execution/retirement. Launch `start_ns - submit_ns` includes host preparation,
argument staging, control writes and any intervening lock wait. Preserve both
intervals. Describing only `end - start` as including argument/control setup
would be incorrect. Write/read `start` is recorded before the queue mutex and
the CP transfer call, so those service intervals can include lock waiting.
These measurements are not device-cycle timestamps, physical DMA bandwidth,
FPGA latency or hardware speed. Model wall time and event intervals overlap;
do not sum nested durations into a throughput claim. Zero-duration intervals
can be valid clock observations when query validity and event success are
established; timestamp ordering is the relevant structural check.

## Failure and hosted qualification requirements

Host fault-injection tests should cover a changed negative H word before ReLU,
bridge/reference mismatch, exchanged output row blocks, partial submission,
timeout then successful resume, timeout then explicit drain, late output-stage
failure, cleanup failure and repeated resource restoration. These tests prove
host control-flow behavior only. Their mock arithmetic must not appear in the
native application's execution path or count toward A02/A03.

The current local prerequisite screen cannot support the trusted runner's
unchanged six-GiB memory entry rule or absent native tools. Hosted CI is a
reasonable execution route, conditional on its own prerequisite checks. Retain
the existing bounded runner rules: fresh directories, explicit one/two-job cap,
six-GiB process RSS limit, fifteen-GiB disk reserve, sixteen-MiB command logs
and finite per-command timeouts. Check available memory and disk on the runner
after setup. A cache hit alone does not establish source, tool or dependency
identity; preserve the identities actually used.

Keep the new workflow on hosted runners with read-only repository permissions,
no secrets or `pull_request_target` exposure, and failure-propagating commands.
Upload failed-attempt logs as well as successes. Preserve existing test cases
and gates. Independently inspect all changed runtime/build/CI hunks and rerun
the base revision's impact classifier if `.github` changes. A new workflow's
trust boundary needs explicit independent review. This receipt supplies
architecture advice, not a review of unwritten implementation or an approval
waiver.
