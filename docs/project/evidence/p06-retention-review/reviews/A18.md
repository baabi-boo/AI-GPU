## Findings and evidence

### 1. Direct and hosted layouts preserve the selected tree without relabelling the attempt

The producer enumerates the whole selected directory, including hidden paths and empty directories, and places it under `private/` after the exact manifest (`ci/project/p06_qualified_warm_encrypt.py`, `_inventory` at line 287 and `_tar_members` at line 368). The reader validates that exact format, bytes, inventory and revision (`ci/project/p06_qualified_warm_retention.py`, `_validate_archive` at line 329); it does not require the selected tree to be a successful packet layout or inspect inner ZIP semantics. The restorer writes those validated entries beneath its own fresh `private/` directory (`ci/project/p06_qualified_warm_restore.py`, `restore_archive` at line 302).

This means a direct packet restores to `output/private/<packet files>`, while a hosted retention selection restores to `output/private/packet/<packet files>` alongside the original packaging log, hosted closeout and any hidden failure paths. There is no invented missing native subtree, normalization of a failed report, inner-ZIP extraction, or attempt-success inference.

The four existing integration tests passed. They round-trip actual `package_partial` output and preserve the incomplete native report, hidden lock, arbitrary byte values, partial ZIP bytes, hosted failure receipt, hidden failure log and empty directory. They also reject changed inner-ZIP bytes and an undeclared tar member before output creation. Two selected packer tests independently passed for malformed/unfinished/failed-cleanup records and acquisition-only retention before the workspace exists.

### 2. Retention pass stays distinct from packaging, orchestration and acceptance

`RetentionArchive.report` (line 404) fixes `native_execution="not_run"`, `retained_code_executed=false`, `origin_authenticated=false`, and all three native/performance/phase acceptance fields to false. It does not expose `complete_replay_original_created`, `packaging_passed`, or `orchestration_passed` as conclusions. Its `outcome="pass"` and `retention_verified=true` describe the selected archive's integrity only. `restoration_completed=true` means this copy operation completed, including when the copied evidence says the attempt failed.

Only the outer manifest and optional public summary are decoded by the reader. Inner receipts, executable-looking source files, failed reports and inner archives are opaque hashed payloads. The optional summary compares revision/count metadata; it does not verify ciphertext or authenticate origin. The report now states that limitation explicitly. No optional-summary behavior was changed by A18.

Four independent scratch round-trips used the real packer and real producer plaintext helpers: (a) a complete synthetic direct packet, (b) a real interrupted direct partial packaging, (c) interrupted hosted packaging with hidden binary failure output and an empty directory, and (d) publication failure with both a surviving pass receipt and an explicit failure receipt. Every raw file and directory set matched, the original archive and source selection stayed unchanged, and the restored manifest matched its original bytes. Fixed false acceptance fields remained false in all four cases. No forbidden subprocess/process/network audit events were observed during these `inspect`/`restore` calls. This is bounded synthetic evidence, not a general process-containment proof.

### 4. Surviving contradictory packaging receipts remain evidence, not authority

The existing packer deliberately preserves referenced final archive names when withdrawal of its published pass receipt cannot be observed (`ci/project/p06_qualified_warm_pack.py`, failure cleanup following line 480). It also writes `packaging-failure.PRIVATE.json` with `packaging_passed=false`, `partial_attempt=true`, `complete_replay_original_created=false`, and `published_receipt_withdrawal_unresolved=true` (line 530). A directory can therefore legitimately retain both a pass receipt and a failure receipt after interruption.

The independent publication-failure probe exercised that exact state and then restored it. Both receipts and all archive bytes were unchanged; the reader did not prefer the pass receipt, classify the attempt as complete, or claim acceptance. A downstream independent replay still has to evaluate the original attempt evidence. The retention report is not an authority for choosing one of the retained receipts.

There is one explicit usability limit, not a newly found laundering defect: if failed withdrawal leaves two hard links to the same receipt inode, the existing encryption producer rejects that selection with `link-or-special-input`. The fifth scratch probe confirmed this fail-closed result. Those bytes remain local and the failed attempt is not deliverable through the producer until a separately reviewed valid selection exists. Neither the reader nor this review weakens the no-link policy or fabricates an encrypted success. Interruption/storage/cleanup limitations already apply to the packer and producer.

### 5. Incomplete restoration is reported conservatively and retains owned output

The restorer validates the entire input before creating its exclusive destination. Once it owns an output directory, it writes `.restore-incomplete.PRIVATE.json` before restoring the manifest and tree, verifies the complete result, removes the marker only as part of final checks, and returns success only after the retained-input context closes successfully. The marker is a diagnostic with `outcome="incomplete"`, `restoration_completed=false`, `native_execution="not_run"`, and fixed false claim fields.

Post-creation failures call `_retain_incomplete` (line 281) through the owned directory descriptor and raise a fixed `RestoreError`; they do not recursively delete evidence. The CLI emits a fixed failure report with both `retention_verified=false` and `restoration_completed=false`, and returns status 1 (`_failure_report` at line 60; `main` at line 401). Source paths/raw bytes are not included in that report. Re-creation of the marker is best effort; its presence or absence alone is explicitly not a success receipt or atomic crash guarantee.

Four targeted restore tests passed for exact hidden/empty/raw payloads and private modes, copy failure/interrupt, failure after marker removal, and sanitized CLI copy failure preserving incomplete output. No further testing was needed to resolve the assigned semantic integration questions.
