## Recommendation

Support the producer's deterministic **PAX-format uncompressed tar**, not arbitrary tar. After strictly validating the first manifest, construct the expected ordered headers using fresh trusted `TarInfo` objects with the producer's metadata, serialize with `PAX_FORMAT`, UTF-8 and strict errors, and compare those bytes to the archive. Stream/hash the declared payloads and check zero padding. This is simpler and less permissive than accepting a general tar parser's normalized inventory: it accepts the producer's Unicode/long-name fallback headers while excluding hidden global PAX state, sparse metadata, alternate names, duplicate records, and ignored trailing archives.

If implementing a separate parser, the following grammar and bounds are required.

## Manifest contract

The exact top-level key set is `schema_version`, `contract_id`, `expected_revision`, `directories`, `files`.

- `schema_version`: integer `1`, rejecting Boolean `true`.
- `contract_id`: `p06-qualified-warm-encrypted-retention-v1`.
- `expected_revision`: lowercase 40-hex string **or JSON null in valid producer output**. The producer's argument is optional. Requiring an exact caller-selected revision deliberately rejects an unbound null archive; describe this as revision binding failure, not unsupported manifest grammar. Do not weaken an exact requested revision to accept null.
- `directories`: sorted list of relative path strings, containing `""` exactly once and first. That entry is the selected input directory, represented in tar as `private/`.
- `files`: sorted list by `path`, each with exactly `path` (nonempty string), `size_bytes` (integer, not Boolean), and `sha256` (64 lowercase hex characters).

No totals, ciphertext identity, acceptance fields, or packaging status belong to this manifest. Reject duplicate JSON keys, extra fields, invalid Unicode, nonfinite numbers, and type coercion. Producer JSON is sorted, compact, ASCII-escaped (`ensure_ascii=True`), followed by one LF; a strict canonical-byte comparison can enforce this producer-only contract after parsing. Escaped Unicode and valid surrogate pairs in JSON must work.

Files and directories share one unique namespace, including Unicode `casefold()` uniqueness. Every non-root parent is an explicitly declared directory. The root is a directory; a file cannot have descendants. Empty files, an entirely empty input tree, empty directories, hidden names, and a retained file itself named `manifest.json` are valid.

## Names and supported raw tar grammar

Validate **manifest-relative** names using the producer's rules: strict UTF-8; NFC; at most 4096 UTF-8 bytes, 128 components, and 255 UTF-8 bytes per component; no empty, `.` or `..` component; no backslash, colon, ASCII control below 32, or DEL (127). Do not impose a broader Unicode-category ban: spaces, leading/trailing spaces, `=`, non-ASCII characters, and characters above 127 remain valid producer inputs. Do not silently trim or normalize them.

Archive logical order is: regular `manifest.json`, then `private/`, then the union of all remaining directory and file paths in Python string-sorted order. It is **not** all directories followed by all files.

Ordinary headers are 512-byte POSIX USTAR headers (`ustar\0` / version `00`). Producer types are exactly ASCII `0` for regular files and `5` for directories. Regular modes are `0600`, directory modes `0700`; uid/gid/mtime are zero, owner/group/link/prefix names empty. Directories have size zero. Numeric fields use the writer's octal encoding; there are no base-256 fields or numeric PAX overrides. A 100-byte name field can be completely occupied without a terminating NUL. Device-number fields are empty NUL bytes, not necessarily octal-zero text.

**Raw directory names have one trailing slash**, including `private/`; the producer's `TarInfo.name` initially lacks it, but `get_info()` adds it before serialization. Remove only the expected single directory slash when mapping back to the manifest. A directory at the path limit has 4105 UTF-8 bytes including `private/` and its trailing slash. A regular file can have 4104 bytes. Both can have 129 components including the `private` prefix. Applying the 4096/128 limits to complete tar names incorrectly rejects producer output.

Python emits a local PAX extension immediately before the ordinary header whenever the effective name contains **any non-ASCII character** or exceeds **100 characters**, including the directory slash. Even a short name `private/é` needs PAX. Exactly 100 ASCII characters do not need PAX. Required extension grammar:

- Type `x`, fixed internal name `././@PaxHeader`, followed by exactly one length-prefixed UTF-8 `path` record; the extension's other metadata is the writer's zero/empty default.
- Record: `<decimal-byte-length> path=<effective-name>\n`; the length counts digits, space, key, equals, UTF-8 value, and LF. Parse bytes, not Unicode character counts. The value may contain spaces and `=`; only the first key separator is structural.
- PAX payload is zero-padded to 512 bytes and applies only to the immediately following regular/directory member. No global `g`, GNU `L`/`K`, sparse, link, special, repeated/chained, or unknown PAX records are produced.
- The following ordinary header name is the effective name encoded with ASCII `replace` and truncated to 100 bytes. Its `?` substitutions and truncation are expected; it need not equal the PAX path or retain a directory's final slash. Validate/compare that fallback against the producer encoding, rather than interpreting it as a second destination.

PAX metadata is not a restored member and does not consume a manifest entry. Therefore `././@PaxHeader` must not be rejected as if it were an attempted payload path.

## Bounds and termination

| Quantity | Producer bound |
|---|---:|
| Files plus directories, including `""` root | 40,000 |
| One input file | 268,435,456 bytes (256 MiB) |
| Sum of input file bytes | 1,073,741,824 bytes (1 GiB) |
| Manifest body | 16,777,216 bytes (16 MiB) |
| Largest path PAX record | 4,116 bytes (directory), 4,115 (file) |
| Largest complete member header sequence | 5,632 bytes: PAX header + padded record + ordinary header |

Do not cap plaintext archive size at `MAX_INPUT_BYTES`: manifest, member/PAX headers, padding, and terminators are additional. A safe pre-parse upper bound from current constants is `MAX_INPUT_BYTES + MAX_MANIFEST_BYTES + MAX_ENTRIES * 6144 + 2 * tarfile.RECORDSIZE` = **1,336,299,520 bytes**. After parsing the bounded manifest, compute the exact expected size with the producer's `_tar_size` formula and reject any mismatch. The bound is conservative; it does not authorize memory allocation of that size.

Each file body is padded with zero bytes to 512; directories have no payload. After the last member come two zero blocks plus zero padding to the next 10,240-byte record boundary. Reject short headers/bodies, nonzero payload padding, premature zero headers, missing terminators, nonzero trailer bytes, concatenated archives, and even additional all-zero records beyond the exact producer size. Ordinary `tarfile` member iteration alone does not validate these conditions.

## Concrete minimal examples

Empty input, using a synthetic revision of forty zeros: this manifest is **172 bytes including its LF**.

```json
{"contract_id":"p06-qualified-warm-encrypted-retention-v1","directories":[""],"expected_revision":"0000000000000000000000000000000000000000","files":[],"schema_version":1}
```

Its complete plaintext tar is **10,240 bytes**: `manifest.json` header at offset 0; manifest and zero padding at 512–1023; `private/` directory header at 1024; zero terminators and record padding thereafter.

A zero-byte hidden file adds this file object and ordinary member `private/.hidden`:

```json
{"path":".hidden","sha256":"e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855","size_bytes":0}
```

For a file named `é`, the manifest path is JSON `"\u00e9"`, while its PAX body is exactly the bytes `b"19 path=private/\xc3\xa9\n"`. The regular fallback header name is `b"private/?"`. A directory named `é` instead uses `b"20 path=private/\xc3\xa9/\n"`, followed by a type-`5` header.

## Reader/restorer scope and remaining pitfalls

- Optional public summary has exactly `schema_version`, `contract_id`, `expected_revision`, `outcome`, `encryption_passed`, `file_count`, `directory_count`, `input_bytes`, `ciphertext_bytes`, `ciphertext_sha256`. Counts exclude the manifest/PAX records and include the root directory. Match counts, revision and success shape; reject type confusion. Its digest is for **ciphertext**, never for the decrypted tar. The new caller-selected tar SHA-256 needs a separate field and comparison.
- Retention is opaque: both hosted `private/packet/...` and direct `private/...` packaging layouts, partial attempts, and failed packaging receipts are valid payloads. Do not require successful packaging or a native original during tar validation. Do not unpack inner ZIPs or execute retained helpers.
- Inspection should validate the entire open regular descriptor, hash and stable identity. Restoration should use that descriptor, verify before creating output, create descriptor-relative owned paths with exclusive/no-follow semantics, write at most the verified declared sizes, then recheck archive identity/hash and restored bytes before success. Repeated observations detect changes but do not authenticate the archive or exclude every malicious concurrent writer.
- Preserve manifest bytes and file bytes exactly, recreate empty directories, and set private modes explicitly. Never delegate creation to `extract`/`extractall`, adopt archive ownership/times, or let a success-shaped retained receipt upgrade retention consistency into native/performance/phase acceptance.
