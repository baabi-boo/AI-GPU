## Integrated conclusions

### 1. The changes preserve distinct lifecycle boundaries

The hosted change requires an explicit `commands` list for each started
dependency/native child before recording completed writer observation. The
missing-field allowance remains confined to preparation, whose actual producer
omits both `state` and `commands`. Explicit malformed inventories still reject.
Known nonstarted children and explicit empty command lists retain their
failure-closeout meanings. This is a stricter observation gate, without a new
native success path: the caller still requires writer observation before both
packaging and encryption, and complete success still has separate native,
packaging and encryption checks.

The new reader admits a complete plaintext retention stream. Restore consumes
that admission and preserves its exact opaque payloads. Neither treats an inner
ZIP, command receipt, pass-shaped report or retained script as executable code
or as an accepted native result. Failed and partial attempts remain usable as
retention data without becoming complete replay originals. The next, separate
replay route retains its own pinned expectations and semantic requirements.

### 2. Producer format, namespace and bounds agree

The producer and reader both construct fresh `TarInfo` objects with the same
regular/directory types, modes, zero mtime, default ownership/link metadata and
strict UTF-8 PAX serialization. Reader comparisons cover the complete serialized
header sequences, including local PAX records, fallback names, checksums and
padding. Manifest-first placement, root `private/`, merged string-sorted member
order, payload hashes, two terminator blocks and the exact 10,240-byte record
boundary agree with the producer. No arbitrary tar parser or extraction route
accepts alternative encodings.

The canonical compact JSON plus terminal LF agrees with the producer's
serializer. Exact schema/type checks, duplicate-key rejection, integer-only
fields, sorted arrays, NFC/UTF-8 names, shared file/directory casefold namespace
and declared directory parents are consistent. Root, empty files/directories,
hidden names, spaces, Unicode and long PAX paths remain representable. Producer
`expected_revision=null` is deliberately outside this exact-revision route and
is documented as such.

The reader imports the producer's entry, path, payload and manifest bounds.
Its conservative 1,336,299,520-byte archive cap includes the bounded PAX/header
overhead and final padding; it additionally computes and checks exact expected
archive length. Payload reads are bounded at 65,536 bytes and streamed. The
optional summary has the producer's exact keys and checks revision and retained
counts. Its ciphertext fields are only bounded/syntax checked because no
ciphertext is supplied; source comments, report limitations and guide all state
that distinction.

### 3. Validation and private metadata precede writes

`RetentionArchive.__enter__` validates the whole archive and optional summary
before marking the object ready. `restore_archive` enters that context,
checks overlap/ancestors and output absence, and performs another full source
stability check before its first `mkdir`. A malformed late member, incorrect
hash/revision or inconsistent summary therefore cannot authorize output
creation through the normal path.

Internal entry records are frozen. `.manifest` returns a deep copy, `.entries`
constructs fresh dictionaries and `.manifest_bytes` is immutable bytes. Copy
offsets, sizes and hashes come from the private validated entry index, so
mutating a public snapshot cannot redirect a copy or alter later reports.
`copy_file` writes only to a caller-owned empty single-link regular descriptor
at offset zero and rehashes the copied source. The restore layer supplies the
exclusive private file descriptors and performs the stronger final output
reread and membership checks required by its contract.

### 4. Source and output checks cover the declared observation model

Inputs are canonical absolute paths opened through no-follow directory
traversal; regular type, single link, size and descriptor/named identity are
checked. Complete input digest checks occur again during use and normal reader
exit. Restore holds the owned root and parent descriptors, tracks created
directory identities, uses exclusive no-follow file creation, sets private
modes, loops short writes, fsyncs and rereads files, verifies the exact output
tree and checks the original named root and parent chain before completion.

These repeated observations detect observed changes; they do not provide
atomicity against every same-user mutation schedule. The source, design and
guide explicitly require stopping writers and preserve that limitation. No
stronger guarantee is inferred here.

### 5. Cleanup cannot turn a failure into accepted success

The shared close helper attempts every supplied owned resource and retains the
first cleanup failure. Input/archive objects detach ownership before close;
directory walkers transfer ownership to the child before closing the old fd.
They do not retry a possibly released descriptor number. Successful-body flags
allow a new cleanup failure to reject a pending result, while secondary cleanup
errors cannot replace an existing operation/integrity failure.

Inspection's pending return remains subject to normal context exit. Restore
marks its body complete only after that exit, and its pending return remains
subject to final root/parent cleanup. Primary ordinary cleanup failures are
mapped to fixed API codes and CLI failure reports; interrupts retain their
documented boundary handling. Best-effort incomplete-marker recreation cannot
override the primary failure, and there is no recursive removal of retained
partial data or unrelated replacement trees.

A last close failure can leave a complete tree without a marker. The code and
contract explicitly disallow treating marker absence or output existence as a
success receipt; the call still fails. This is an acknowledged lifecycle limit,
not a new defect.

### 6. Replay binding and result/privacy scope remain coherent

The replay fix supplies literal expected repository paths for records,
analysis and replay itself, so direct `__main__` entry uses the same source
inventory as import. It preserves resolved-module-location checks, whole-file
hashes, helper inventory, prerequisite identities and repeated stability checks.
No record parser, frozen proof, population, performance predicate or historical
claim field is changed by that delta.

The new retention/restore errors use fixed allowlisted codes; CLI errors do not
echo retained names, payloads, paths or arbitrary exception text. The separate
existing native replay diagnostic interface is not silently relabelled as this
fixed-code API; its guide records its logs and artifacts privately. Retention
success reports retain `native_execution="not_run"`, false retained-code
execution/origin authentication, and false native/performance/phase acceptance.
The guide correctly distinguishes successful retention, successful complete
replay and the independently evaluated performance hypothesis.

Direct packaging maps to `private/qualified-warm-original.PRIVATE.zip` and
hosted packaging to `private/packet/qualified-warm-original.PRIVATE.zip`.
Restore preserves the actual manifest layout; it does not invent a uniform
location. The guide and design give both paths and require a usable complete
original before semantic replay. No residual API/producer/documentation mismatch
was established in this reviewed scope.
