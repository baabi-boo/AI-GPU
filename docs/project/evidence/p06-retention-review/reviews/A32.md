## Findings and reasoning

### 1. Attempt-all cleanup and error precedence are consistent

`retention._close_all` catches each resource's `BaseException`, remembers the
first one, and continues through the supplied owned-resource tuple. It raises
that first failure only when cleanup is not suppressing secondary errors.
Current callers supply finite tuples, so iterator failures do not create an
additional hidden cleanup path.

The reader's `_Input.close` snapshots both descriptors and clears both fields
before closing either. `RetentionArchive.close` similarly invalidates the
reader and clears both source-object fields before processing the sources.
Each source attempts both its data fd and parent fd even when its first close
fails. The archive then attempts the next source. Repeated `close()` calls have
no remembered fd to retry. Ordinary cleanup exceptions receive fixed public
codes; the reader's established control-exception propagation is retained.

`RetentionArchive.__exit__` distinguishes a body exception, a failed final
integrity check, and successful body/integrity completion. The first two paths
suppress cleanup exceptions and retain the preceding error. Only the successful
path lets a new cleanup failure reject the pending return. Initialization
cleanup follows the same precedence rule.

Restore's explicit completion flags correctly separate a new close failure
from secondary cleanup during an already failing operation. Its `_close_fds`
maps a primary `OSError`, ordinary exception, or `KeyboardInterrupt` to
`filesystem-failed`, `restore-failed`, or `interrupted`, respectively, while
still attempting every supplied descriptor. Existing operation errors retain
their prior top-level mapping. The marker recreation helper remains best effort
and cannot replace the preceding restore failure with its own close error.

### 2. Directory handoffs do not retry a descriptor after uncertain close

All three walkers assign the newly opened child to the current owned fd before
closing the previous fd. If the previous close releases its descriptor and then
raises, the unwind closes the child, not the old number. The old close is not
retried. The restore walk's initial `fstat` is now inside its cleanup scope, so
failure there also attempts the acquired root fd.

The `_mkdir`, `_new_file`, recursive tree verification, reopened-root
verification, and directory-creation loop have one cleanup site per locally
owned resource. Existing owned caller descriptors are not closed by those
helpers. There is no new retry loop or recursive removal of failed output.

The new repository tests explicitly release and reuse a descriptor number for
`/dev/null` in the direct input-close and three directory-walker cases, then
verify that the unrelated replacement remains open. This is stronger than
descriptor-count accounting alone for the uncertain-close defect. I inspected
these assertions but did not rerun A27's already executed test population.

### 3. A cleanup failure cannot return an accepted operation report

The convenience inspection return remains subject to successful context exit.
Restore does not mark its overall body completed until the reader context has
exited successfully; its pending return is then subject to successful final
root/parent cleanup. A primary final-close error is sanitized by `_close_fds`
even though it arises from the final `finally` block. The CLI catches that fixed
error and emits its existing failure report with a nonzero status. No acceptance
field, native claim, or report schema was changed by this correction.

A final directory-close error can leave a fully written private tree with no
incomplete marker, because final cleanup occurs after marker removal and may
release the last root descriptor. This is an explicit existing limitation in
the source docstring and the reviewed lifecycle contract, not a successful
return: there is no persistent pass receipt and marker absence does not prove
success. Earlier restore failures still attempt exclusive marker recreation
while an owned root fd remains available.

## Independent targeted probes

therefore did not rerun its full population or any full suite. I independently
probed the remaining changed helper branches where a missing completion flag or

constructed `tarfile.PAX_FORMAT` archive. It does not import the new test file,

the real close first. Each scenario checks open descriptor sets around the
operation; helper scenarios also verify that caller-owned descriptors remain
open.

  tests, not a fresh audit of the complete retention parser or trust model.
- A27's 57-test combined focused result was read as author evidence. It was not
  independently rerun or relabelled as A32 execution.

  implementation intentionally does not assume that every real close failure

  prove release under every kernel/filesystem failure or abrupt termination.

  remote publication, acceptance change, or maintainer approval was performed.
