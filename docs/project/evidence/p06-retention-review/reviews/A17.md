## Source conclusions and complementary coverage

- `_Input` checks regular type, one link and nonzero bounded size using no-follow
  `stat` before leaf `open`, then checks the descriptor/path identity. The tar cap
  includes metadata, padding and terminators; the manifest-derived exact size is
  checked before payload traversal.
- All payload hashing, full-archive rehashing and `copy_file` use
  `_Input.blocks`, which requests at most **64 KiB** per `pread`. Restore file
  verification uses the same read cap. Payload writes use a memoryview of one
  chunk and handle partial writes. Whole materialization sites are confined to
  the **16 MiB manifest**, **64 KiB summary** and canonical member headers
  (maximum **5,632 bytes**, consistent with A04). No allocation uses archive or
  declared file size. Restore may write the already-resident manifest in one
  larger request; that is bounded metadata, not an archive-sized payload copy.
- Accepted member paths remain **4,096 UTF-8 bytes / 128 components**, with
  **255-byte components**. Restore constructs destinations relative to held
  descriptors, so its extra `private/` prefix and absolute output prefix do not
  become a narrower member-path limit. Recursive final verification holds
  descriptors proportional to the bounded depth, not the 40,000-entry count.
- Input/summary contexts, owned-file helpers, directory walks and verification
  traversals use `finally`/context cleanup. At the root agent's direction I did
  not duplicate A15's successful maximum-path restore and descriptor-count
  checks across its five success/failure probes. A14 separately measured bounded
  streaming on a producer-generated archive. Those results remain attributed to
  their respective independent reviews.
