## 2. What the current implementation actually exposes

### Native managed operator and fixed model

`sw/runtime/ai/runtime.h` defines the internal C++ `ManagedMatmul::{create,submit,memory_info,close}` and `MatmulOperation::{wait,close,output_words,trace}`. This is experimental internal source, not a newly installed public C ABI. `vortex2.h` remains the underlying runtime interface (`docs/designs/ai_operator_contract_v1.md`, Implemented scope / Device and profile binding).

The only matmul signatures are `(8,4,8)`, `(8,4,16)`, `(16,8,16)`, each with matching FP16 or BF16 inputs and FP32 accumulation/output. A is packed row major, B packed column major, D packed row major. There is no input C, alpha/beta, batching, implicit transpose, padding, arbitrary stride, mixed input dtype, or CPU matmul fallback. Exact TFR arithmetic rules apply rather than an inferred broad IEEE claim. `runtime.cpp:78–80,273–278,500–513` enforces shape/span/profile restrictions. The execution profile is RV64, four threads/warp, four warps/core, one core, one cluster, issue width one, 16 KiB local memory, with tensor/local-memory extensions.

`sw/kernel/ai/matmul.cpp` directly includes `vx_tensor.h`, uses the ordinary `wmma_context` with an `8×4×8` tile, starts the accumulator at zero, loads A row-major and B column-major, calls `mma_sync`, and stores the native result. Accepted WGMMA or inherited HIP work does not change this particular managed kernel into a WGMMA/CUDA route.

`ManagedMlp::create` rejects nondefault workspace policy before constructing a context (`sw/runtime/ai/mlp_runtime.cpp:102–123`). Its graph submits one `(16,8,16)` and two `(8,4,8)` calls (`183–201`). It copies actual operation results to the trace, compares them against expected words, applies the explicit host bridge to actual hidden words, feeds actual bridge bytes to the next calls, and assembles actual output blocks (`212–240,269–321`). Expected data serves comparisons; it is not a successful substitute result. The public Python model entry selects a compiled frozen fixture (`python/native/module.cpp:846–865`), not caller weights.

The planner's `execution_available=false` is intentional: it computes a checked plan without allocation or dispatch. The manifest's wrapper execution availability describes a separate managed route. A caller-written 64-hex qualification ID and two profile flags are not provenance proof; the trusted runner is responsible for configuration/module/backend qualification, while runtime code checks queryable geometry. That boundary is explicit in `docs/designs/ai_operator_contract_v1.md`, so it is not a newly found authentication defect.

### Python and PyTorch

`python/vortex_ai/_api.py` exposes immutable tensor metadata; `Session.open`, `submit`, `model`, `pending_operations`, `memory_info`, `close`; and owned operations with status, wait/advance, close, detached output, trace and model-record access. `Tensor` accepts exact packed one-dimensional byte exporters representing rank-two FP16/BF16 data (`230–290`); submission checks the six combinations and registers an owner before the native call (`458–519`). `runtime.cpp:538–540` copies inputs into operation-owned staging; returned Python bytes/words are detached. This is a copying interface, not device tensor or zero-copy interoperability.

The source-bound bundle is a substantive boundary. `python/native/module.cpp:404–412` constructs the native binding from `VerifiedBundle`; `python/native/runtime_loader.cpp` checks compiled receipt/hash/path identities, constrains loader paths, and resolves symbols from the expected libraries (`216–236,414–467,628–650,719–738`). This audit sampled those relevant boundaries; it is not a complete loader/security verification.

`python/vortex_ai/torch_ops.py:17–44` requires exactly PyTorch `2.15.0+cpu` without CUDA/HIP builds, little-endian Linux x86_64, CPython 3.12 and the GIL. Qualification further pins patch version 3.12.14. The two schemas (`340–345`) are `matmul_v1(Tensor a, Tensor b, int session_token, int poison)` and `fixed_mlp_v1(str case_id, int session_token, int poison)`. `TorchSession` borrows an existing qualified session and retains it behind a process-local token; detach does not close the borrowed session (`194–288`).

Input/output tensors use CPU storage. Input bits are reinterpreted as integers and packed little-endian; native `Session.submit` or `Session.model` performs the matmul work; only after successful completion and explicit operation close is native output copied to a new FP32 CPU tensor (`74–119,291–337`). CPU storage therefore does not mean an arithmetic CPU fallback. The `Autograd` registration is a guarded dispatcher path, not a backward formula: original `requires_grad` and forward tangents are rejected before reinterpretation (`74–84`).

## 3. Serial ownership and resident workspace agree across layers

The two restrictions are distinct:

1. **One live managed context per linked runtime instance.** `runtime.cpp:15–69,435–497` atomically reserves before device open, returns a clean reservation on setup failure, and permanently latches an observed cleanup error. Raw clients and independently linked runtime copies are not covered by that reservation; `docs/designs/serial_matmul_workspace_v1.md` expressly excludes such coexistence. Individual owners remain single-caller objects.
2. **One operation lease until completed healthy close.** `runtime.cpp:500–569` validates first, rejects while leased, and acquires the lease before staging/enqueue. `wait` establishes completion and output without clearing the lease (`609–665`). `close` releases events, queue and appropriate buffers, then returns the lease only with healthy cleanup (`181–213,668–675`). Partial dispatch and timeout retain resources. A live operation retains the context after its owner is destroyed. Failed cleanup hides that operation's output and prevents new work.

These are deliberate containment boundaries. The underlying queue's launch-setup lock is a queue member (`sw/runtime/common/queue.cpp:478–528`), while SimX initializes/finalizes the singleton `SimPlatform` from processor construction/destruction (`sim/simx/processor.cpp:44–45,231–232`). This inspection does not independently prove all cross-queue races; it corroborates the documented reason that raw multiple queues or contexts cannot be treated as supported managed concurrency.

The binding adds a process-wide native lease, main-interpreter/fork checks and busy guards (`python/native/module.cpp:36–71,137–175`). It explicitly blocks another matmul after successful wait (`636–705`), suspends an idle matmul context before model creation, and lazily resumes afterward (`415–429,870–903`). Python owner gates reject concurrent/reentrant use (`_api.py:297–321`). Successful waiting is never permission to bypass explicit close.

Two apparent differences are contractual rather than defects: C++ `ExecutionResult::ok()` checks error channels while leaving completion separate; Python `ExecutionStatus.ok` also requires completion. A native owner close with a live operation returns incomplete without permanently entering closing state; public Python `Session.close()` intentionally latches closing and forbids further new work (`runtime.h:30–39`, `runtime.cpp:579–594`, `_api.py:541–558`; corresponding contracts state both).

| Policy | Implemented behavior | Current caller boundary |
|---|---|---|
| `per_operation` | Allocate/release A/B/D on every operation; all six signatures retained. | Default for existing model/Python/Torch and cold callers. |
| `reusable_single_tile` | Only `(8,4,8)`; allocate A128/B64/D128 during context creation, retain 320 requested payload bytes until context teardown, borrow them per operation. | Internal managed C++ opt-in; no public Python/Torch policy argument. |

The resident path still creates fresh host staging, queue and events, rewrites all A/B/D poison bytes, launches once and reads all D bytes on every operation (`runtime.cpp:19,320–331,349–425,500–550`). It is neither resident model weights nor a general memory pool, cache, zero-copy path, multi-shape allocator, or overlapping execution. Unknown policies and unsupported resident shapes reject before new work. Native MLP explicitly rejects the candidate; native binding construction leaves the default field untouched. Thus exposing it to Python now would expand scope; it is not a missing fix required to measure the current native treatment.

## 6. Development recommendation

Keep the current candidate and measurement contract fixed. After the existing publication/governance/input/capacity/admission prerequisites are satisfied, obtain one complete fresh qualified warm original: FP16 then BF16, both policies in the same source/binary per format, 24 processes, 792 launches, and 25,344 exact checked FP32 words; preserve failures and require independent complete replay before the frozen decision. `docs/designs/qualified_warm_workspace_v1.md` fixes this population and restricts the reviewed source extension; further measurement-source changes require a new reviewed pin and fresh attempt. `docs/designs/warm_workspace_benchmark_v1.md` fixes the treatment as buffer-lifetime change alone and measures instrumented host time, not physical acceleration.

A negative result is useful: it answers whether retaining these buffers helps this deliberately small serial workload under the declared costs. A positive result remains bounded and does not automatically close P06-A02/A03 or justify CUDA/concurrency/training claims. New features can be selected using that result and the accepted model/operator boundary. None of the intentional restrictions above is evidence of a defect requiring a pre-experiment feature expansion. An actual numerical/lifetime/admission failure found during the required gates would change that ordering; this audit did not find or waive one.
