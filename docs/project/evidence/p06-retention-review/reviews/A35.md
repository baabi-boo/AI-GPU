### Real close faults and owned-resource accounting

- `faulty_closes` saves the real `os.close`, removes an fd's label before the
  call, invokes the real close, and raises the selected exception afterward.
  Thus the injected failure does not leave the target intentionally open, and
  later reuse of the same numeric descriptor does not re-trigger its label.
- The tests populate labels from the actual opened `_Input` objects, actual
  `_mkdir` return values, or the actual file descriptor passed to the writer.
  Expected close-label sequences require every intended resource to have been
  reached. A hook that never fires cannot produce a passing attempt list.
- `no_fd_leaks` snapshots descriptors before and after the operation. It closes
  extras as test hygiene, but compares the **pre-remediation** `after` snapshot
  with `before`; its cleanup therefore cannot turn a production leak into a
  passing assertion.
- The initial-`fstat` regression enters descriptor accounting before patching
  `os.fstat` and restores the patch before taking the final snapshot. Its
  measurement cannot silently classify every fd as absent through the fault
  being injected.

### Reuse is observed and the unrelated descriptor is protected

Both reuse tests call the real close, immediately open `/dev/null`, and assert
that its returned descriptor equals the just-released number. They then
require `os.fstat` on that replacement to succeed after the tested cleanup.
The input case repeats `source.close()` and requires exactly the original
data/parent close sequence. The directory-walker cases require exactly two
distinct attempted descriptors, covering the old handle and the newly owned
child. These conditions cannot pass merely because a replacement was allocated
at an unrelated number.

The saved real close is used to release the test's replacement after the mock
scope. In the defective baseline the directory walker closes the unrelated
replacement; the test's own final release can consequently report `EBADF`.
The surrounding accounting still closes the leaked child/root descriptors and
fails the test. The independent after-test audit below confirmed no descriptor
change survives that failing path. This diagnostic roughness does not conceal
the regression or contaminate a later test.

### Primary and first-cleanup errors are distinguishable

The reader body cases retain the exact `RetentionError`, `RuntimeError`, and
`KeyboardInterrupt` objects using `assertIs`. The final-integrity, input-init,
restore-verification, incomplete-marker, and failed-writer cases likewise
check the captured primary object where one is injected. The actual
summary-mismatch and identity-probe cases check the specific domain diagnostic
generated by production code.

The restore terminal-close matrix deliberately pairs a first root `OSError`
with a later parent `RuntimeError`, expecting `filesystem-failed`. The new-file
case does the same with file versus parent descriptors. Returning the last
cleanup failure would instead yield `restore-failed`, so these cases distinguish
first-error precedence even though public APIs intentionally replace private
exception objects with fixed diagnostic errors. Reader cleanup's ordinary
errors intentionally converge on `retention-invalid`; object identity there is
not a public guarantee. Attempt lists independently check that handling the
first error does not skip the rest.

### Cleanup and monkeypatch restoration on failures

All monkeypatches are bounded `with mock.patch.object(...)` contexts. The
descriptor-accounting context surrounds them, so its post-operation snapshot
runs only after those patches have unwound. Temporary directory cleanup is
registered with `addCleanup` in `setUp`.

The comparison independently checked these 11 patch targets after **each**
method, including every failed baseline method: `os.close`, `os.open`,
`os.fstat`, reader `_directory`, `_Input.__init__`, `_Input.assert_identity`,
`RetentionArchive.report`, `RetentionArchive.assert_unchanged`, restore
`_mkdir`, `_verify_tree`, and `_open_owned_directory`. Every target retained
its original function identity. It also compared the open fd set and each
fd's `(st_dev, st_ino, st_mode, st_rdev)` identity before and after each method,
and over each suite. All comparisons matched. An unrelated `/dev/null`
sentinel held open across each entire suite remained valid.

There are no skip decorators, `skipTest` calls, or conditional platform skips
in the new module; both executions recorded zero skips. The tests explicitly
depend on Linux `/proc/self/fd`, `/dev/null`, descriptor-relative APIs, and
the existing no-follow/directory flags. This establishes validity in the
project's prepared Linux environment, not portability to unsupported hosts.

## Limitations and next action

The baseline logs include secondary `AttributeError` diagnostics from assertions
after a failed `subTest` whose `assertRaises` never captured an exception. Thus
some baseline methods stop after their first failing subcase; the result proves
that 14 methods reject the baseline, not that every baseline matrix entry was
separately completed. The fixed suite completes all methods successfully.
Moving such assertions inside their subtest contexts would improve negative
diagnostics, but this is an F0 observation, not a hidden pass or a blocker.

The fd helper is appropriate for these synchronous, isolated host tests. Its
set-difference repair would require different ownership accounting if these
methods were later run concurrently in one process with unrelated fd-opening
threads. No such execution was exercised or claimed. The external audit
confirms no cross-test descriptor or patch contamination in the actual runs.

This is focused synthetic-host evidence. It does not establish full strict
governance qualification, native execution, performance, origin authentication,
concurrent-writer resistance, crash durability, or phase acceptance. No tests
cover every possible close behavior: these injections deliberately release the
descriptor before raising, and do not claim every real close error releases it.

Next action: combine this test-validity review with the independent production
review and the coordinator's source-bound validation/publication workflow.
No test change is required by this review.
