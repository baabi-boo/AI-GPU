## Data-integrity observations

**F0, high confidence, static proof — shallow history is a preservation
constraint, not a missing-base-tree problem.** The base and checkpoint raw
objects and trees are available. The base's raw commit still names its earlier
parent even though local log traversal stops at the shallow boundary. The
publication must attach to the existing provider base commit. It must not
recreate that base as a root or infer an empty parent list from the grafted log.
No history deepening or submodule initialization was needed for these checks.

**F0, high confidence, static proof — unchanged special entries must remain
inherited.** The base has 7,584 leaf entries; the checkpoint has 7,591. Both
contain 135 executable blobs, one symlink and five gitlinks. The five gitlink
commit objects are absent from the superproject's local object database, which
did not prevent the complete tree reconstruction. Preserve those entries by
their existing modes and object IDs; do not dereference them as blobs, flatten
submodules into files, or read the symlink's filesystem target. The reviewed
helper correctly ignores unchanged entries and rejects changed special ones.

**F0, high confidence, static proof — current UTF-8 handling is byte preserving.**
All nine committed checkpoint blobs and all observed candidate files satisfy
the strict encoding requirement. The helper fails on unsupported content
instead of replacing characters. If later final artifacts require binary
handling, publish their exact bytes through an appropriate blob encoding and
retain the same identity checks; do not silently relax decoding.

**F0, high confidence, static proof — local and provider commit IDs are distinct
identities.** The connected create-commit interface accepts a tree, message and
ordered parents but does not expose the local commit's complete author and
committer serialization. Tree equality therefore supplies the required content
comparison; a provider commit must be recorded using its returned SHA. Do not
label the local checkpoint or eventual local final commit as published merely
because its tree was reproduced.

**F0, high confidence, bounded review — no final helper execution is implied.**
The final local commit does not yet exist in this snapshot. The helper does not
itself enforce completion of independent reviews, final index/worktree
cleanliness, local checks, API-tree equality, remote-head freshness or CI.
Those remain orchestration gates. They are explicitly planned and are not
reported here as defects merely because assembly is ongoing.

## Required publication gates

1. **Finish and freeze the candidate.** Complete the intended assignment packet,
   artifact index, source identities and documentation. Review the actual
   changed files and run all required local metadata, baseline, link, privacy
   and source checks. Explicitly stage only intended files. Keep private notes,
   payload staging, routing data, keys and private originals out of the public
   commit. Commit the finished result with the local checkpoint as parent.

2. **Verify the committed final scope.** Record the full local final commit and
   its root tree. Check the base-to-final and checkpoint-to-final path/mode
   inventories, protected inputs and all intended untracked additions. Confirm
   the index matches the commit, materialized tracked bytes/modes match the
   index, and any remaining unstaged, untracked or ignored files are explicitly
   accounted for rather than silently assumed absent. A clean `git status`
   alone does not establish the governance source-binding contract. Changes
   after this freeze require updated checks and a new frozen candidate.

3. **Run the immutable base classifier on that actual commit.** Because the
   change touches `.github/**`, apply the audited base's classifier and policy
   to the audited-base-to-final-commit range, as review policy section 5
   requires. The observed workflow diff adds exactly the new contract path to
   push and pull-request filters, with the corresponding test-oracle addition.
   Existing review identifies R2 CI enforcement. I did not rerun a final-commit
   classifier because that commit did not yet exist.

4. **Prepare final payload exclusively from committed objects.** Use the local
   checkpoint as the final helper's base and the actual local final commit as
   its head. Bind every payload entry to committed bytes/mode/object identity.
   For bounded transfer into the tool execution store, validate complete
   reassembly against payload byte length and digest; reject truncation,
   missing chunks, duplicate chunks or mixed payload generations. Never rebuild
   payload contents by copying mutable worktree files or edited tool output.

5. **Verify both API-created trees before any branch move.** For an unchanged
   provider base, create the checkpoint tree using the existing provider base
   tree and the checked checkpoint delta. Its returned root tree SHA must equal
   `72dc5c78acb8f117780abd269d6d5d8158f7dbf1`. Create the provider checkpoint
   commit with the existing provider base as parent. Create the final tree using
   the checkpoint tree and checkpoint-to-final delta; require its returned root
   SHA to equal the frozen local final tree. The final provider commit's parent
   must be the returned provider checkpoint commit SHA. Check returned commit
   trees and parents. Creating these objects must not separately move master
   through the intermediate checkpoint. GitHub's tree API inherits only from
   the specified base tree; omitting it with a partial delta deletes omitted
   parent files. See [GitHub's Git trees documentation](https://docs.github.com/en/rest/git/trees).

6. **Preserve concurrent master with a late read and guarded update.** Read the
   live authorized branch immediately before the sole final ref update. Local
   `origin/master` and this review are not that late observation. If the branch
   differs from the expected base, inspect and preserve the concurrent work;
   regenerate the candidate, parents, payloads and affected checks as needed.
   Do not merely change the lease value while retaining a stale final tree.
   Use the connected update-ref tool with an explicit `expected_sha` equal to
   the freshly observed expected head and `force=false`. Its documented
   expected-SHA check and GitHub's fast-forward enforcement are separate
   safeguards; this review does not assert an independently tested atomic-CAS
   implementation. On rejection, reread before any retry. GitHub documents
   `force=false` as enforcing a fast-forward update in its
   [Git references API](https://docs.github.com/en/rest/git/refs).

7. **Read back delivery and distinguish local/provider history.** Verify the
   resulting provider branch SHA, the provider final commit's parent chain and
   tree, and fetched raw bytes/modes against the frozen local tree. A local
   final commit and an API-created final commit can have equal trees while
   local master and provider master have different SHAs. Do not manufacture
   equality by relabeling either revision, and do not treat creation of an
   unreachable provider object as successful publication.

8. **Qualify the exact provider SHA.** Observe relevant workflows for that exact
   published final commit. Retain and inspect the complete uninterrupted strict
   Project Governance result and original artifact for its actual run and
   attempt. Verify discovery/events, zero skips/failures/errors, checked/stable
   environment, source before/after identities, published HEAD/tree, upload
   identity and original ZIP digest. Base results, checkpoint results and
   focused runs cannot qualify the changed provider SHA. Keep any later source
   or workflow corrections tied to their own new commit and results.
