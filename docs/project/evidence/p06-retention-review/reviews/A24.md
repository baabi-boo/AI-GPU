## Static diagnostic review

`RetentionError` and `RestoreError` constructors admit only fixed allowlisted string codes. Manifest/summary JSON decoding suppresses original `UnicodeError`, `ValueError`, and `RecursionError` messages; archive admission compares expected serialized producer headers, including PAX bytes, without exposing a generic tar parser's retained-name diagnostics. The public report contains selected identity/count metadata, not paths, file inventories, payload text, or retained receipts.

The CLI's parser subclass ignores argparse's interpolated error message and raises `RestoreError("invalid-arguments")`. Both parser levels disable abbreviation. Unknown/missing/abbreviated arguments were already exhaustively exercised by A21; this assignment inspected that boundary and A21's recorded 38-case result rather than rerunning its grid or adding its count to this assignment's fresh evidence.

Within the operation boundary, the CLI catches `Exception` and `KeyboardInterrupt`, translates known domain errors or uses fixed fallback codes, and does not format `str(error)` or `repr(error)`. Its output-write/flush exception branch also returns nonzero without printing the original error. That final reporting-output branch was inspected, not separately fault-injected here. Success reports preserve the same false native/acceptance scope as failures; retained payloads are copied as opaque bytes and never consulted for a qualification decision.

## F1 — Final close bypasses API normalization and stops further cleanup

**Severity:** F1, narrow cleanup trigger and discrepancy with the new documented API error guarantee. **Confidence:** high. **Evidence type:** static-proof, reproduced by deterministic syscall fault injection.

In `ci/project/p06_qualified_warm_restore.py`, the domain-error translation ends at lines 363–376. The `finally` block at lines 377–380 then closes `(root_fd, parent_fd)` with no per-descriptor guard. An exception while closing `root_fd` therefore escapes outside that translation and prevents the loop from closing `parent_fd`. The new design document's API section says API errors use fixed `RetentionError.code` / `RestoreError.code` values; this terminal branch does not satisfy that statement.

The reproducer first calls the actual `os.close(root_fd)` and then raises `OSError(EIO, synthetic_message, synthetic_filename)` at exactly the final root close. It thus models an error reported after releasing the descriptor rather than keeping the root open artificially. In two separate invocations, the CLI returned fixed `restore-failed` JSON, while the direct API raised the original `OSError` rather than `RestoreError`. `/proc/self/fd` observations confirmed exactly one additional open descriptor, the unattempted parent close, for each invocation. The harness cleaned those descriptors after observation. No operation reported success.

This is **not evidence that ordinary `os.close` leaks a retained filename**: that syscall receives an integer fd and ordinarily supplies no filename. The injected filename only establishes the lack of API normalization. The demonstrated CLI boundary still drops it completely. The review does not infer hostile-host control or a broad confidentiality failure from this hook.

Recommended follow-up: make terminal cleanup attempt every independently owned descriptor, preserve the first operation/cleanup failure, and place cleanup failures within the public API's fixed-error mapping. Do not blindly retry a failed close after the descriptor may already have been released. The retention reader's `_Input.close` (lines 171–176) also has a sequential unguarded-close pattern, and `RetentionArchive.close` sequentially closes the optional summary and archive objects without guarding each attempt. Those related patterns were inspected, not separately injected or counted as additional reproductions. No production fix or contract relaxation was made in this read-only assignment.
