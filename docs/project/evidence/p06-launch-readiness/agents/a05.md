# A05 — Managed preflight launch checkpoint

## Scope and finding

Base: `e3ad6bd1e2b002aa234d57cd8a02519cec915830`; tests exercised the
uncommitted shared worktree on CPython 3.12.14 / Linux. This is bounded host
orchestration evidence using the existing synthetic `ManagedHarness`. No native
compiler, GPU process, download, commit, or push was run.

**F2, high confidence, reproduced:**
`ci/project/p06_managed_preflight_execute.py` appended an unresolved command and
set the first native command's execution disposition to `unknown` before its
launch checkpoint. That checkpoint was outside the command exception handler.
A checkpoint failure before `run_bounded` therefore retained an unresolved
`process_started=None` row even though the monitor was never entered. The first
native checkpoint also left `native_execution=unknown`; a later checkpoint left
the unstarted command unresolved despite already completed native work. Such a
row cannot establish the determinate process state required for partial
retention.

## Change

The launch checkpoint now has a separate exception boundary. A failure there
records `process_started=False`, `cleanup_complete=True`, `outcome=blocked`,
`exit_code=None`, and the original reason, then rethrows for ordinary finalization.
For a native command it restores the previous native disposition, preserving
earlier `run` evidence. The existing monitor exception path remains unchanged:
without a reliable receipt it keeps the start observation unresolved and retains
any partial log. The successful-command requirement still demands
`process_started is True`, a passing outcome, an integer zero exit code,
completed cleanup, and no failure reason.

Owned changes:

- `ci/project/p06_managed_preflight_execute.py`
- `ci/project/test_p06_managed_launch_failures.py`
- This report.

No frozen proof, threshold, workload, or acceptance record changed. Full
governance qualification and native execution remain unperformed by this task;
independent review is the coordinator's next step.
