## F2 — inference mode concealed an existing forward tangent

The original `_operand` inspected
`torch.autograd.forward_ad.unpack_dual(value).tangent` directly. In this pinned
PyTorch version, entering `torch.inference_mode()` hides a pre-existing forward
AD tangent from that inspection. An already-created dual tensor passed as either
A or B therefore reached `Session.submit` and produced a successful output,
contrary to the stated original-input precondition.

Reproduction structure:

```python
with torch.autograd.forward_ad.dual_level():
    dual_a = torch.autograd.forward_ad.make_dual(a, torch.ones_like(a))
    with torch.inference_mode():
        torch.ops.vortex_ai.matmul_v1(dual_a, b, adapter.token, poison)
```

Both A-dual and B-dual cases produced exactly one scripted native submission and
returned a tensor in the original probe. Neither left pending work; this was a
representation/dispatch acceptance bug, not an owner leak.

The fix temporarily disables inference mode only while inspecting the original
forward tangent. Context restoration is automatic. It does not convert or
replace the input, run native work, or change how result tensors are created.
The existing reverse-gradient check remains in force. The three added tests
cover A and B dual rejection within inference mode, newly created ordinary
inference tensors both inside and outside inference mode, and primal inference
tensors inside an otherwise empty forward-AD level.

## Observed limitation — higher-level APIs can evaluate eager calls

The pinned `torch.func.linearize` implementation begins by executing
`output = func(*primals)` before it enters a forward-AD level or tracing mode.
That invocation has ordinary eager tensors and no transform key. Universal
zero-execution rejection would require identifying arbitrary caller intent or
inspecting Python call stacks. Neither is part of this adapter.

The following are measured unqualified behaviors:

| Context | Result | Scripted native calls |
|---|---|---:|
| `torch.func.linearize` of matmul | Primal executes, later dual call rejects | 1 |
| `torch.func.linearize` of input-free model | Returns `(output, jvp_fn)` | 2 |
| `torch.fx.symbolic_trace` of matmul | Captures op with proxies | 0 |
| `torch.fx.symbolic_trace` of input-free model | Evaluates model and captures constant | 1 |
| TorchScript scripting of matmul/module | Creates scripted module | 0 |
| Running that scripted matmul | Invokes registered operator | 1 |
| TorchScript scripting of model/module | Creates scripted module | 0 |
| Running that scripted model | Invokes registered operator | 1 |

All observed calls completed explicit native-owner close in the mock. These
observations do not establish support for FX, TorchScript execution or
linearization. They show why “unsupported” cannot honestly mean every
higher-level entry is guaranteed to reject before any eager work.

Recommended contract wording is separately provided in
`w03_a1_dispatch_limitation.md`. Retain the supported eager-only scope and the
specific guarded paths; explain that higher-level functions may evaluate
ordinary eager calls before entering a detectable transform. A later transform
exception must not be used as evidence that no work happened. Pending native
owners and retained records remain authoritative.
