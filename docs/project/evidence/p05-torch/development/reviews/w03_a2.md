## Findings

### OWN-01 — incomplete Session initialization is accepted by adapter construction

Severity **F2**, confidence **high**, evidence type **static-proof**, corroborated
by execution against real CPython 3.12.14 / PyTorch 2.15.0+cpu and scripted native
responses.

A retained `error.session` can have an allocated native handle while its
`Session.open` call failed before publishing validated identity. `_ready()` only
called `_ensure_open()` and checked pending owners. `_ensure_open()` tests the
handle/closing state; it does not mean the opening procedure finished. The
adapter constructor therefore accepted all four independently injected cases:

- Native creation status reports primary failure.
- Native session identity has an invalid schema.
- Identity publication raises `KeyboardInterrupt`.
- Native creation status itself has an invalid schema.

Each resulting adapter's first model call raised `KeyError('format')`, rather
than rejecting the uninitialized owner at attachment. No native model submission
occurred in these probes, and each retained native Session could be closed.

**Fix proposed and tested:** require the validated, nonempty `Session.info`
snapshot inside the Session gate during `_ready()`. On failure raise a binding
state error with the retained Session. This relies on the existing binding's
invariant: `_info` is empty until `_info_snapshot` fully validates the native
identity. No new caller-supplied provenance or test bypass is introduced.

Regression: `test_failed_session_initialization_rejected_before_attach`, including
four subcases and checks that the Session remains recoverable and no scripted
native work is submitted.

### OWN-02 — failed constructor publication loses the registered adapter identity

Severity **F2**, confidence **high**, evidence type **static-proof**, corroborated
by an actual CPython return trace interruption.

The registry intentionally retains adapters strongly. An interruption on
`TorchSession.__init__` return can occur after registry insertion but before the
caller receives an adapter. The return trace hook raised `KeyboardInterrupt`
outside the constructor's exception attachment path. One registry entry remained.
Retrying `TorchSession(session)` correctly reported duplicate attachment, but its
`BindingError.adapter` incorrectly pointed to the fresh, unregistered attempted
adapter, which had token zero. Closing that attempted adapter did not detach the
registered owner. Normal public retry therefore did not recover the identity.

**Fix proposed and tested:** when duplicate attachment is detected, retain the
already registered adapter in the constructor exception path. The duplicate
`BindingError.adapter` then exposes the actual owner, allowing explicit detach
or continued use. Strong token retention, monotonic tokens and native ownership
rules remain unchanged. No new public API is added.

Regressions:

- `test_duplicate_attach_error_retains_existing_adapter` checks exact adapter and
  Session identity.
- `test_constructor_return_interruption_keeps_recoverable_adapter` injects the
  return-boundary interruption, recovers the actual adapter through a subsequent
  duplicate-attachment error, closes it, creates a fresh token, and completes a
  new host-mock matmul with explicit native-owner close.

This recovery procedure assumes the borrowed native Session is still open, as
required for new adapter construction. If the caller closes that Session before
recovering the lost adapter, construction fails at `_ready()` before registry
lookup; its closed Session/adapter registry entry can then remain until process
exit. This narrow residual memory-retention scenario does not retain active
native work after successful Session close. Document the recovery order; if a
future API promises recovery after Session close, it needs an explicit owner
lookup/recovery mechanism or lookup-before-readiness implementation with review.

## Other ownership conclusions

- The adapter never becomes the authoritative holder of interrupted native
  submissions. `Session._pending` remains the authoritative recovery inventory,
  including errors that cannot accept attached Python attributes.
- Matmul success requires both successful wait and explicit successful close
  before output conversion. Model success additionally checks the terminal model
  result before and after close. The adapter never treats successful cleanup as
  proof of successful model numerics.
- Every adapter-owned native wait/advance/close receives a positive bounded
  timeout no larger than 100 ms. The aggregate retry budget is checked between
  native calls; it is correctly described as a retry deadline, not whole-call
  cancellation. A native model advance can itself include multiple waits.
- Nonretryable validation, primary and cleanup errors do not publish output.
  An expired budget leaves the native owner retained for explicit caller recovery.
- Adapter close refuses pending native work and detaches without closing the
  borrowed Session. Detached tokens no longer dispatch.
- Registry and adapter gates use nonblocking acquisition and reject reentrancy.
  The reviewed original/proposed lock order does not retain the registry gate
  across acquiring an adapter gate or invoking native work.
- Process identity guards occur before registry or owner use. This review inspected
  the guard paths and ran the existing host process-identity test; it did not run
  an actual forked native context.
- Output-allocation failure occurs after native close; a later call may proceed
  once underlying Session state permits. Existing output views are independent
  of native owner lifetime.
