## Priority decision

**Proceed with P05's scoped PyTorch custom-operator milestone.** It is a concrete,
useful next slice supported by the current dependency graph and accepted native
owners. `docs/project/roadmap.json` makes P05 depend only on completed P04.
`docs/project/p05-entry-handoff.md` and the current backlog explicitly select
this work after the accepted copying Python binding. The P05 phase guide defines
A02 as simulated framework execution and A03 as tested-version/operator/failure
compatibility. No new hardware datapath is needed to meet either obligation.

P06 is also eligible after P04, but its first step requires a separate frozen
performance experiment. It does not supersede the already prepared P05 seam.
The inherited P01-A03 vendor `hw_emu` blocker bars P01 closure and P07 closure,
not P05 development. The existing 267-to-283 DSP area failure remains a genuine
separate obligation; unchanged host/framework work neither fixes nor worsens
that measured RTL result. Preserve both in current status and handoff.

The accepted surface is narrow: six matmul signatures, ten frozen model cases,
copying representations, one live native context, explicit close, no autograd,
and no full framework device backend. A useful addition is real tensor ingress
and egress for those operators, not a renaming of the existing plain-Python
checker. Native reference execution must remain independent of the new caller.

## Proposed runner and verifier seams

Use three explicit stages: unchanged fresh P04 native model run; fresh existing
P05 native-matmul/plain-Python/package run; separate installed-framework run.
The third stage consumes the exact second-stage packet. It must not invoke the
first two stages through nested process monitors or rebuild a different package
behind a retained source identifier.

### 1. Trusted input packet

The framework runner takes a completed P05 packet directory, the same clean
source root, a provisioned wheelhouse/lock, and new separate work/output roots.
At entry, require `contract_id=p05-installed-python-execution-v1`, schema 1,
`state=finished`, `outcome=pass`, `reason=null`, `development=false`, clean and
stable source, SimX, the selected format and exactly two iterations. A matching
`outcome` string alone is not proof of its contents.

Retain a descriptor for the P05 report (relative path, size, SHA-256), plus the
complete immutable input packet inventory. Copy or retain the referenced packet
bytes so the final packet can be replayed after the build host disappears.
Verify the report's descriptors against actual retained bodies and reparse raw
native/Python records; verify command outcomes, logs, source snapshots, manifest,
wheel, sdist and comparison identity. Cross-check the current source commit/tree
and bound source inventory, qualification IDs, profile and fixture pins, selected
case lists, bundle artifacts, original native P04 report and the independent
native matmul observations. Freeze input packet/package/bundle identities before
and after the framework stage. Reject a different revision even if its selected
outputs happen to match.

Relevant existing seams are `p05_execute.py:263-341` (run envelope, command
records and stability checks), `:366-421` (retained native packet, independent
model logs, exact bundle), and `p05_execution_records.py:187-285` (exact ordinary
and model observations). The old provenance/dispatch auditors show the necessary
cross-binding checks. Their historical evidence should remain immutable; add a
versioned new verifier where the expanded package/source inventory needs it.

The current `p05_execution_records._installation` checks live absolute files
with `resolve(strict=True)` (`:107-139`). It is suitable during execution but is
**not itself a relocated archive verifier**. Do not make an offline replay pass
by weakening those live checks or rewriting original path strings. A separate
read-only packet reader must verify archived bodies, recorded path relationships
and hashes without requiring the original filesystem or executing archived code.

### 2. Fresh framework environment

Create a separate `venv --copies` without system-site packages. Install a fully
versioned and hash-locked CPU wheel closure offline, then the freshly bound
Vortex wheel with no dependency resolution. Retain install commands, successful
exit/cleanup, lock bytes, wheel filenames/hashes and installed metadata. The
parent selected candidate `torch==2.15.0+cpu`; availability is not yet acceptance.
Record actual `torch.__version__`, distribution version, CPU build identity,
CPython patch/platform, resolved module paths and installed file hashes. Use
streaming hashes and appropriate bounds for large Torch shared objects.

Run a copied checker outside the source tree using `python -I -B` through the
existing verified launcher. Check both `vortex_ai` and Torch load from the fresh
venv. Keep plain `import vortex_ai` working with Torch absent. An editable install,
ambient PYTHONPATH module or a modified adapter placed beside an old wheel is
not clean installed evidence. Keep expected outputs external validation data,
never an alternative implementation of the operator.

### 3. Actual framework observations

Use new contract IDs for the framework request, observations and execution
report. Do not relabel `p05-installed-observations-v1` as PyTorch execution or add
ambiguous optional fields to that historical strict schema.

Each request binds the exact implementation/lock/manifest/source hashes, format,
canonical case order, two poisons, clean prefix and operator schemas. Each
observation must record a unique ordered `(operator, case_id, iteration)` key,
actual input tensor dtype/device/shape/element strides/storage offset/grad state,
raw operand bytes or exact words, actual returned FP32 tensor metadata/words,
completed native status and close status, detached native trace/model record,
resource observations, and explicit framework copying counts. Log the same
observations using dedicated markers and require exact raw-log/file equality.

A result must be read back from the **returned torch tensor**. The native owner's
`output_bytes()` alone cannot prove correct framework output materialization.
Likewise, record the actual tensor operand serialization and link it to the
submitted bytes; expected fixture bytes by themselves cannot prove tensor ingress.

The framework consumer should validate these extra fields, then reuse the
unchanged P03/P04 numerical/dispatch validators for actual native records. It
must independently derive counts rather than trust producer totals. Cross-check
hidden, bridge and output-block lineage for every model, not final output alone.
Freeze exact fixture membership and numerical comparisons; no new tolerance or
CPU matmul path is needed. Host ReLU/exact cast/assembly retain their existing
scope; adapter serialization/result copies are additional host work and must not
be presented as device DMA or accelerator computation.

## Execution accounting

The existing matrix has, per format, six standalone matmul launches plus ten
model runs containing thirty launches: **36 native comparison launches** and
**36 plain-Python launches**. A new full framework matrix adds **36** per format.
Across FP16 and BF16, therefore:

| Route | Distinct native launches | Event/profile pairs with existing policy |
|---|---:|---:|
| Independently executed native reference | 72 | 300; its twelve standalone matmul launches are unprofiled |
| Plain-Python regression | 72 | 360 |
| New PyTorch route | 72 | 360 |
| Entire three-route workflow | 216 | 1,020 |

These are expected counts to check against observations, not executed results.
A02 may report its comparison scope as native plus Torch (144 launches, 660
pairs), provided the 72 plain-Python regression launches are explicitly excluded
from that subtotal. Copying the native packet into another directory adds zero
executions. A framework report should name `new_framework_execution` separately
from `referenced_native_execution` and `referenced_plain_python_execution` so
aggregation cannot double-count nested evidence. Independent clocks and nested
host timing intervals must not be added into a fabricated device latency.

## Concrete acceptance tests

The following resolve risks introduced by this milestone rather than rerunning
unrelated hardware sweeps:

- All six dtype/shape signatures and all ten frozen models, with both poisons,
  exact output and input lineage, explicit close and restored native resources.
- Direct `torch.ops` as well as facade entry: required gradients inside ordinary
  and `no_grad` contexts, wrong/closed/stale/cross-process tokens, invalid dtype,
  mixed format, wrong device, rank/shape/strides/offset, unsupported tensor views
  and every framework mode the contract promises to reject.
- Bit-preserving FP16/BF16 transport and raw FP32 output ownership, including
  signed zeros, nonfinite payloads and storage surviving owner/session close.
  Label these host transport probes separately from native arithmetic coverage.
- Host-injected submission/wait/close/cleanup failures and interruptions: no
  successful tensor, no hidden CPU fallback, and pending native owners remain
  reachable for explicit recovery. A later successful close must not erase the
  primary error or a model mismatch.
- Consumer mutations: corrupt only the returned tensor words, only operand
  metadata/bytes, only native trace, one iteration/case/poison, the claimed launch
  count, source/lock/package identity, a command exit or raw log; reject all.
- Relocated archive replay using an independently supplied report/archive digest;
  reject missing bodies, paths escaping the packet, symlink substitutions,
  duplicate/extra records and a rehashed summary that disagrees with retained raw
  observations. Replay is data verification, not another native execution.

## CI and review obligations

New externally visible operator schemas and package/enforcement changes deserve
independent R3-level contract review under `docs/review/code-review-policy.md`,
even if the mechanical classifier reports a lower class for Python paths. Run
that classifier using the base revision's policy and code for the final diff.
A workflow edit makes its own hosted classifier summary untrusted under policy
section 5; retain the local base-policy result. Do not invent human approval or
a waiver. The user's explicit publication instruction supplies task authority;
it does not make an unresolved F2/F3 engineering finding disappear.

Reuse the existing hosted-workflow protections: contents read only, no secrets,
no persisted checkout credentials, no fork-reachable self-hosted runner,
restore-only caches, pinned CPython/build tools, bounded jobs/deadlines/RSS/disk,
and always-uploaded evidence including hidden config stamps. Cover new adapter,
lock, runner/checker/verifier and contract changes in triggers. Preserve all
unconditional native and plain-Python checks. A separate job may consume a
verified artifact from the same revision; do not silently fetch the latest
successful artifact from another source.

The original full source suite, new meaningful framework tests, package/source
inventory tests, workflow checks and independent data auditors must pass at the
stated implementation revision. Preserve failed attempts and their scopes. No
Beacon/model-parity rerun is implied by host-only changes that do not alter RTL,
SimX or their timing, and no existing tolerance/golden may be changed here.
