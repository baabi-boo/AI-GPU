## Exhaustive 16-bit packing checks

Every possible unsigned 16-bit encoding was constructed directly as little-endian
bytes, reinterpreted as the selected floating dtype, then extracted through an
integer view. The packed bytes matched exactly, including NaNs, infinities,
subnormals, and both zeros. No arithmetic or float-valued Python intermediate
was used.

| Dtype | Operand layout | Encodings | Bounded chunks | Outcome |
|---|---|---:|---:|---|
| torch.float16 | A | 65,536 | 256 | pass |
| torch.float16 | B | 65,536 | 512 | pass |
| torch.bfloat16 | A | 65,536 | 256 | pass |
| torch.bfloat16 | B | 65,536 | 512 | pass |

That is **262,144 checked input words** across four transport routes. A uses
`(16,16)` with strides `(16,1)`; B uses `(16,8)` with strides `(1,16)`.
All six declared dtype/shape signatures were separately checked with distinct
non-symmetric encodings, exact shape/stride metadata and a row-major FP32 result.

The safe candidate, after validation on the original tensor, is:

```python
physical = tensor.t() if column_major else tensor
values = physical.view(torch.int16).flatten().tolist()
packed = struct.pack(f"<{len(values)}h", *values)
```

For accepted B, `tensor.t()` is a metadata view sharing the same backing storage;
it exposes the physical column-major sequence as contiguous row-major storage.
The reinterpretation uses signed 16-bit integers only; `struct.pack('<h', ...)`
reconstructs the original bits and explicitly selects little-endian output.

**Confirmed failure mode:** for physical B words `0..31`, the correct route
returns `0,1,2,...`. Serializing `b.contiguous()` produces `0,8,16,24,1,9,...`.
The latter silently changes operand order even though shape and dtype look valid.
Never call `contiguous()` on B inside the adapter to repair the layout.

## FP32 output and independent ownership

`torch.frombuffer(bytearray(raw), dtype=torch.float32).clone()` preserved exact
bits for **200,729 FP32 words**: 25 explicit edge patterns, all 65,536 high-half
patterns crossed with low halves `0000`, `0001`, and `ffff`, plus 4,096 seeded
arbitrary 32-bit words. This includes positive/negative zero, minimum and maximum
subnormals, finite extrema, infinities, signaling and quiet NaNs, signed NaNs,
and the prescribed output poisons. This is broad transport coverage, not an
exhaustive test of all 2^32 FP32 bit patterns.

The cloned output retained its bytes after its source bytearray was zeroed.
Mutating the returned tensor did not mutate that bytearray. All six supported
result geometries also passed `clone().reshape(M,N)` with strides `(N,1)` and
storage offset zero. The output had `requires_grad=False`.

Use the native owner's immutable output bytes as input, build a temporary
bytearray, then clone into independent tensor ownership. To validate the returned
framework tensor, reinterpret it as `torch.int32`, flatten, and pack signed
little-endian words; do not read floats or compare only native-owner bytes.

## Metadata and differentiation hazards

The local candidate validation rejected 13 intended scenarios: rank three,
transposed A, nonzero storage offset, padded rows, expanded zero stride, wrong
dtype, requires-grad input, negative lazy view, complex conjugate input,
meta device, sparse layout, requires-grad inside `torch.no_grad()`, and
forward-mode dual input.

**Check differentiation before any integer view.** On the pinned actual version:

- `requires_grad=True` floating input becomes `requires_grad=False` after
  `view(torch.int16)`.
- A forward-mode dual can have `requires_grad=False`; its tangent is present
  before the integer view and absent afterward.
- Thus `requires_grad` alone misses forward-mode differentiation. The tested
  detector is `torch.autograd.forward_ad.unpack_dual(original).tangent is not None`.
- `torch.no_grad()` does not erase the original tensor's `requires_grad` flag,
  so an explicit original-input check rejects it consistently.

The negative lazy bit is independently meaningful: dtype reinterpretation raises
`RuntimeError` while it is set. Reject it explicitly on the original tensor.
Conjugated complex inputs were rejected by the dtype rule; no supported FP16/BF16
conjugate representation was established. Preserve an explicit `is_conj()` guard.

These are direct tensor helper probes, not proof of how a registered PyTorch
operator's dispatcher presents inputs to its kernel. The separate W01 A4
registration audit must ensure direct `torch.ops` dispatch does not strip the
flags before enforcement.

## Accessible extent and storage policy

A valid offset-zero `(8,8)` tensor backed by a larger 256-byte storage serialized
only its 128 logical bytes. The integer-view/list route does not read unrelated
trailing storage and avoids raw pointer access. The contract may safely permit
larger backing storage while requiring exact logical shapes/strides and offset
zero; if the chosen contract requires exact backing size instead, add that
explicit check. Do not conflate logical tensor byte extent with storage size.

The probe asserted host byte order is little-endian. The selected Linux x86_64
contract can keep this fixed; a future endian/platform extension needs its own
representation qualification.

## Recommendation

Use validated metadata-only B transpose plus integer reinterpretation for input
packing, and native bytes to mutable buffer to cloned FP32 tensor for outputs.
Check original dtype/device/layout/rank/shape/stride/offset, grad/dual and lazy
value flags first. Keep no-NumPy support; the installed Torch import issued an
optional NumPy-unavailable warning, while `numpy` remained absent from
`sys.modules` and every probe completed successfully. Qualify actual framework
native dispatch separately using these transport helpers and retained receipts.
