Reviewer: `/root/w01_a4_torch_dispatch`. Repository: `baabi-boo/AI-GPU`,
base `bdd3485243f820947df94f7962641d10f2169834`. Read-only repository audit;

behavior, **not native execution or numerical qualification**.

## Decision

Use `torch.library.Library` with explicit eager dispatch registrations. The
installed, actually imported version was **PyTorch 2.15.0+cpu**, CPython 3.12.
A no-tensor fixed-model operator works through `CompositeExplicitAutograd` and
needs no decorative tensor or device argument. Retain the `Library` object in
a module global because its lifetime owns the registrations.

A counted dummy callback was used as the execution boundary. Two variants were
probed: high-level `custom_op` and explicit `Library`. The final script exercised
23 conditions for each. For the recommended `Library` variant, the three
supported eager cases reached the dummy body once each; all 20 unsupported
cases raised with **zero body calls**. No accelerator arithmetic was performed.

## Why backend checks alone are insufficient

The high-level `custom_op` variant had backend guards for gradient, forward AD,
exact tensor type, device, negative/conjugate views, autocast and tracing, plus
rejecting `register_fake` and `register_vmap` callbacks. Nevertheless it executed:

| Unsupported context | Observed dummy-body calls |
|---|---:|
| Unresolved negative view | 1 |
| Unresolved negative view under inference mode | 1 |
| Functionalized matmul / fixed model | 1 each |
| `torch.func.jvp` matmul / fixed model | 1 each |
| Fixed model nested in `vmap` | 1 |
| TorchScript trace of matmul / fixed model | 5 each |

The high-level dispatcher can process or hide those contexts before the backend
function's checks. In particular, `torch.jit.is_tracing()` inside that function
was insufficient, and a fixed-model op without tensor inputs did not reach its
registered vmap callback. This is a concrete F2/high-confidence implementation
hazard if the adapter promises to reject these modes before native submission.

The first probe's output formatter incorrectly called `.shape` on a returned
ScriptFunction and labelled those two trace results `rejected`; its positive
body counts already showed execution. The corrected final probe properly labels
the trace returns and preserves the initial script/log separately. Use the final
log for the conclusions here.

## Recommended registration shape

The exact public names and token type are for the final contract. This tested
registration structure preserves the original tensors until the matmul guard:

```python
_LIBRARY = torch.library.Library("vortex_ai", "DEF")
_LIBRARY.define("matmul_v1(Tensor a, Tensor b, int session_token, int poison) -> Tensor")
_LIBRARY.define("fixed_mlp_v1(str case_id, int session_token, int poison) -> Tensor")
_LIBRARY.impl("matmul_v1", _matmul_eager, "CPU")
_LIBRARY.impl("matmul_v1", _matmul_eager, "Autograd")
_LIBRARY.impl("fixed_mlp_v1", _fixed_mlp_eager, "CompositeExplicitAutograd")

for name in ("matmul_v1", "fixed_mlp_v1"):
    for key in (
        "Meta", "FuncTorchBatched", "FuncTorchVmapMode", "Functionalize",
        "Tracer", "AutocastCPU", "Negative", "Conjugate",
        "FuncTorchDynamicLayerFrontMode",
    ):
        _LIBRARY.impl(name, _reject_transform, key)
```

The eager matmul entry must check both input tensors before packing or accessing
the native owner: exact `torch.Tensor` type; CPU device; explicit allowed dtype,
rank, shape, strides and storage offset; no unresolved `is_neg()`/`is_conj()`;
no `requires_grad`; no tangent from `torch.autograd.forward_ad.unpack_dual`.
The raw `torch.ops` path and convenience method must share this guarded entry.

Both eager entries must additionally check `torch.is_autocast_enabled('cpu')`
and reject it. A no-tensor fixed model did not select the `AutocastCPU` kernel,
so the runtime check is required even with the registered rejection. Runtime
`torch.compiler.is_compiling()` and `torch.jit.is_tracing()` checks are useful
additional guards, but must not replace the dispatch-key rejections.

`Autograd` here uses the guarded eager implementation and does not implement a
backward formula: requiring gradients raises before any body execution, including
inside `torch.no_grad()`. This avoids silent detach. The CPU registration remains
necessary for ordinary inference tensors that omit Autograd dispatch keys.
Negative/Conjugate rejection kernels also remain necessary in inference mode,
where Autograd is absent and the default fallback could otherwise resolve a view
before the CPU guard observes it.

`FuncTorchDynamicLayerFrontMode` blocks actual `torch.func` transforms such as
JVP, while direct forward-AD duals are caught by the tangent check. A no-tensor
fixed-model call has no differentiable input; merely entering a direct dual-level
context with no dual input is not itself an execution/gradient claim.

No fake implementation should return a plausible output shape. The `Meta`
rejection plus exact-type guards prevented fake tracing, compilation and the
no-input fixed model from causing dummy execution in these probes. No claim is
made for user-installed arbitrary dispatch modes, monkeypatches, graph-break
policies or versions beyond the exact tested version. All such extensions remain
unsupported rather than implicitly qualified by these examples.
