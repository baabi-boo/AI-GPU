## Current package contracts and concrete implications

1. **The module inventory is an enforcement boundary.** `python/vortex_ai/_bundle.py:17` enumerates all 22 current source inputs. `setup.py:56` rejects Python/native files outside that inventory; `PinnedBuildPy` and `PinnedWheel` verify exact installed Python bytes. Every new adapter/helper `.py` under `python/vortex_ai` must appear in `SOURCE_PATHS` and `MANIFEST.in`. Put the adapter in a single module initially: the package list in `pyproject.toml:25` only includes `vortex_ai`, not nested packages. A silent omitted module is a packaging failure, not a runtime fallback opportunity.
2. **Adding the adapter changes the source pin.** `BuildIdentity` (`setup.py:125`) hashes the inventory including `setup.py`, `pyproject.toml` and `_bundle.py`; a bound extension embeds that exact digest. The bundle manifest validates identical source records and binds native source revision/tree. An old accepted wheel or manifest cannot simply be relabelled or patched to run the new adapter. Generate fresh native/P05 packets, bundle, sdist and wheel from the new clean revision. Preserve the historical A01 record unchanged; the old result remains valid for its original bytes.
3. **Keep PyTorch optional by import and provisioning.** `pyproject.toml:14` intentionally has `dependencies = []`; `__init__.py` only imports `_api`, which lazily imports the extension. Keep it that way. `import vortex_ai.torch` may require exactly the selected Torch version and give an actionable missing/incompatible-version error. Do not import Torch, NumPy, download dependencies or register operators during plain `import vortex_ai`.
4. **An optional-dependency extra has non-obvious package effects.** `PinnedSDist.make_release_tree` (`setup.py:245`) allows four egg-info metadata files, excluding `requires.txt`. `p05_execute._extract_sdist` (`ci/project/p05_execute.py:153`) expects exactly that existing archive membership. The retained independent `docs/project/evidence/p05-python/reviews/audit_provenance.py:588` rejects any `Requires-Dist`, including an extra's conditional dependency. The least invasive route is a separate reviewed framework requirements lock and documented explicit installation, leaving package metadata dependency-free. An extra is possible, but needs deliberate producer/consumer/test changes and a new independent metadata review; do not weaken the historical auditor.
5. **Version changes are widespread, not required here.** The current package version `0.1.0` is fixed in the wheel inspector, installed checker and observation validator (`p05_execute.py:234`, `p05_installed_check.py:200`, `p05_execution_records.py:107`). A new operator contract ID/version can identify this surface while preserving the package's existing alpha version; if the package version is bumped, update every live producer and consumer together. Historical evidence remains unchanged.
6. **The bound sdist already supports offline independent rebuilds.** It preserves exact source inventory, generated pin header and bundle manifest, omits native libraries, and rejects changed/replaced pins. Continue using that route; do not introduce editable installs or repository-path imports as qualification evidence.

## Framework dependency pin and archive recommendations

Freeze `torch==2.15.0+cpu` only after the downloaded wheel's metadata and actual import match that candidate. Freeze every transitive runtime dependency with its wheel SHA-256. The exact CPU index/local version suffix matters: an unqualified `torch==2.15.0` dependency resolved against an arbitrary default index can select a different build and pull CUDA packages. `--extra-index-url` is unnecessary when using an explicit CPU wheel plus a reviewed closure; an offline wheelhouse with exact hashes is the clean qualification boundary.

Torch contains large shared libraries. Do not reuse small 16 MiB source-file limits or blindly read entire framework binaries into memory. Stream hashes with a declared per-file/total bound. Preserve distribution metadata and license/notice inventory, and retain third-party wheels as workflow artifacts if useful; large framework wheels need not enter the Git repository. Identify system ELF dependencies separately; no manylinux or arbitrary-host portability claim follows from one hosted result.
