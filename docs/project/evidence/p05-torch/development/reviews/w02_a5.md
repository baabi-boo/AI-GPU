## Runner behavior

The CLI is the frozen third-stage interface:

```sh
python3 ci/project/p05_torch_execute.py run \
  --source-dir ROOT --python-work ABS_P05_WORK --python-output ABS_P05_OUTPUT \
  --wheelhouse ABS_WHEELHOUSE --work-dir NEW_ABS_WORK --output NEW_ABS_OUTPUT \
  --format fp16 --timeout-seconds 600 --run-timeout-seconds 300
```

The new interpreter is exactly `NEW_ABS_WORK/venv/bin/python`, matching the
explicit real-Torch host-suite step planned by the CI owner. All roots are
canonical, fresh where appropriate, and pairwise separate. Source must be the
current clean checkout, with the existing 15 GiB reserve and 4 GiB available-RAM
preconditions. External commands use the existing bounded process-group monitor
with 4 GiB RSS and 16 MiB logs. No earlier execution entry point is called.

### Original native/Python proof

Before creating the framework environment, the runner preserves the entire
original P05 packet, including hidden files, and revalidates:

- Exact finished/pass/no-development envelope, same clean source commit/tree,
  before/after source snapshots, imported helper bytes, retained source bodies,
  original paths, selection, resource budget, current tools, and dependencies.
- Complete original P05 command membership/order, successful exit and cleanup,
  raw log hashes/sizes, exact arguments, working directories, and environments.
- Original P04 packet inventory and its retained copy, raw native model records,
  qualification IDs and compiler/artifact identities. The existing in-process
  `p05_bundle.create_bundle` revalidates the live original P04 packet and creates
  a fresh copied bundle whose manifest and artifact bytes must exactly equal
  the freshly produced P05 bundle. Its metadata probes do not execute native
  workloads or nest the earlier runners' process monitors.
- Original native matmul compiler stamps, artifacts, effective-header record,
  derived qualification binding, retained executables, and six raw results.
- Original bound sdist and wheel identities/membership, wheel payload, staged
  source inventory, independently extracted sdist sources and preserved pins.
- Original venv interpreter and exact installed wheel bytes, retained installed
  bodies, copied checker and request, six plain-Python matmuls and ten models
  revalidated against both frozen fixtures and freshly executed native raw
  observations, including original live installation checks.

P05's helper inventory depends on its entry-point imports. The new runner checks
the original packet's exact declared source set against the current source and
reconstructs the expected set; it deliberately does not compare a newly imported
P05 helper list against the standalone original P05 list. Historical validators
are unchanged, including their absolute live path requirements.

### Framework installation and observation

The manifest and lock must describe exactly eleven closed CPU wheels. Missing,
extra, symlinked, duplicated, or changed wheelhouse entries fail. Every active
lock line must exactly match the manifest's version and SHA-256. There are no
network operations in the runner.

The runner creates `venv --copies`, verifies interpreter identity and isolation,
and inventories its initial pip/interpreter files. It installs the framework
closure with `--no-index --find-links ... --only-binary=:all: --require-hashes
--no-deps --no-compile --no-cache-dir`, then installs the freshly bound Vortex
wheel without dependency resolution.

Framework wheel members are streamed to derive installed file hashes, with
explicit path, duplicate, type, symlink, per-file, member-count, and aggregate
bounds. Wheel installation schemes and generated console-script paths are
handled explicitly. Installed immutable bytes must match those wheel members;
rewritten `RECORD`, the installer's metadata additions, reviewed entry-point
names, and unchanged seed files are the only permitted additions. Unexpected
installed files, changed seed files, omitted files, or collisions fail.

The limits are 2 GiB per framework file, 3 GiB total, and 50,000 files; the
existing small native/source limits remain unchanged. An actual read-only scan
of all eleven locked wheels observed 16,220 regular payload members totaling
851,893,786 bytes, with no collisions. The largest Torch file is 440,280,512
bytes, which is why the existing 16 MiB source-file reader is unsuitable.

Only after installed bytes have been checked can the isolated framework probe
import Torch. It records CPython patch/platform/GIL, prefix and executable,
actual Torch version/CPU build/module origin/configuration, the exact
distribution closure and each distribution's independently hashed installed
files. Full installed identities and observed environment data are compared
before and after the framework checker. Framework binaries are identified in
manifests, not copied into the evidence archive.

The runner copies `p05_torch_installed_check.py`, `p05_torch_records.py`, unchanged
`p05_installed_check.py`, and the frozen contract outside the checkout. It adapts
only the original request's prefix and copied bundle path, adds framework and
adapter identities, and runs the installed `vortex_ai.launch` under `-I -B`.
The checker receives mandatory `--request`, `--output`, and `--contract`.
Agent 4's pure verifier independently derives result counts from the exact
observed Torch tensors/native records and raw log. The per-format report counts
36 new native launches through 16 framework calls. Original native and plain
Python routes remain 36 each, for 108 distinct launches per format; copied
packets add zero launches. Acceptance and phase-completion flags remain false.

### Failure and identity retention

Every external command gets a checkpoint and raw log, including nonzero exits.
Original packet files are copied before their revalidation begins. Failed
checker output is retained when present. Source snapshots, original packet
inventory, wheelhouse inventory, and available installed identities are captured
again at the end. Source/helper/package/bundle/installation/input changes fail
stability checks; source copies and recorded command logs are also checked.
Nothing is cleaned up or relabeled as success after failure.

## Validation performed

The focused suite passed **20 tests** in its final run:

```sh
PYTHONDONTWRITEBYTECODE=1 \
PYTHONPATH=p05-torch-work/drafts:AI-GPU/ci/project \
python3 -B -m unittest discover -s p05-torch-work/drafts \
  -p test_p05_torch_orchestration.py -q
```

The tests cover required and fresh paths, root overlap and symlinks, absence of
earlier-runner entry-point calls, exact closed wheel/lock identity, changed and
rehashed unpinned requirements, duplicate/bool schema rejection, archive path
traversal/duplicates/symlinks/oversize, explicit wheel data and entry-point paths,
streaming a 17 MiB member without whole-file reads, installed byte tampering,
extra files/missing scripts/seed mutation, and symlinked installed files.

The inert stage tests also show that a rejected original packet is retained
without any process execution, a nonzero initial provisioning command retains
its log and fails, a tampered retained packet cannot remain blocked/pass, a
bare `outcome=pass` report is rejected, and changed raw command logs are rejected.
No default test downloads, installs, or imports Torch. The read-only real-wheel
layout scan executed no installed framework/native code.
