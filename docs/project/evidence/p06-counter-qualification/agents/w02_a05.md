# Wave 02 agent 05 — explicit qualification execution

## Implementation

Added `ci/project/p06_counter_qualification_execute.py` and extended the shared
managed executor with an exact Boolean `counter_qualification=False` keyword.
The new mode requires both lifetime and dependency modes. Only the new CLI
exposes the required proof, diagnostic-original and control-original paths and
their independently selected SHA-256 identities. Legacy CLI imports do not
load qualification helpers.

The qualification module is imported only inside the explicitly selected route,
before helper capture. Complete dependency admission runs first, followed by
qualification admission before any recorded version, build or native command.
The new admission's additional helper and fixed prerequisite-input paths join
the retained source inventory, including the separate pending-accessor probe.
Invalid proof produces no commands and leaves native execution `not_run`.

The qualified report adds these exact fields:

- `counter_qualification_sha256`
- `counter_qualification_admission`
- `counter_qualification_admission_before`
- `counter_qualification_admission_after`
- `retained_counter_qualification`
- `counter_qualification_passed`

The exact proof bytes are retained as
`artifacts/counter-qualification/proof.json`, independently of the input's
basename. The copy must match the admitted byte count and digest and participates
in final retained-file verification.

Common build bindings include the proof digest and reconstructed admission;
each process binding also includes the digest before hashing. The existing
native `--qualification-id` argument carries the resulting process binding.
All existing command checkpoints and finalization recheck admission stability.
The derived result requires the complete dependency/native result plus matching
initial/final admission observations. The four-process plan, compiler and build
validation, native arguments, raw lifetime checks and all seven historical
nonacceptance fields remain unchanged.

The inherited `unresolved_obligations` labels remain in the shared record;
the new result is explicitly scoped to a fresh four-process preflight, not
future warm-process qualification or phase/performance acceptance.
