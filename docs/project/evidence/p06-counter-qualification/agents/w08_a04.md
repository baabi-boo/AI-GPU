## Finding and correction

**F2, high confidence, static proof, fixed:** `DependencyBuildTests.setUp`
selected host tools using the caller's ambient `PATH`, then ran them using
`build.clean_environment`. This allowed a selected program to depend on a
different environment from the one that actually invoked it. The concrete
failure was `/home/agent/.local/bin/cmake`: it succeeded with the ambient
environment, but its Python import failed under the fixture's sanitized `HOME`.
The original test failed with `ModuleNotFoundError: No module named 'cmake'`.
The same fixture supplies `ActualGeneratedOptionControls` and
`ActualCMakeReviewTests`, explaining both dependent class-setup errors.

The correction constructs the sanitized environment before tool discovery and
passes its `PATH` explicitly to `shutil.which`. This matches the existing
production `tool_inventory` behavior. Production discovery, validation,
enforcement, build commands and golden data remain unchanged.

A new regression places failing substitutes for all seven host tools in the
caller's `PATH`. It requires the fixture's selected identities to remain the
same, then exercises the real Make/compiler/archive fixture. This regression
failed against the original selection behavior before the correction was
applied. Its final passing run verifies both selection and actual execution.

not usable with the clean fixture environment. Validation therefore invoked
the existing Python executable through a new scratch-only alias directory
containing an alias to the existing functional CMake installation. Python
retains that invocation path in `sys.executable`, making the directory part of
the already-defined clean environment. No toolchain was installed or modified.

and GNU Make **4.4.1**. CMake's resolved executable SHA-256 was
