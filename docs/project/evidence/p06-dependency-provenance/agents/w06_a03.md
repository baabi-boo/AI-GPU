## Finding 1 — extra owned linker inputs

**F2; high confidence; executable boundary reproduction.** The original driver
checked that each expected direct input appeared exactly once in a parsed map.
It did not reject additional inputs. The real pinned map parser accepted an
extension baseline with its object and admitted Ramulator library. Appending
either a fresh-source-root shared library or a build-root object still passed
the unchanged `all(loads[input] == 1)` guard.

This reproduction establishes the real parser/direct-input boundary defect; it
does not claim that a complete 413-record original was accepted. No such actual
original was available during this review. Inspection found the same omission
in the published formal dependency reader, and W06-A04 received the finding
and reproduction before implementing its independent correction.

The diagnostic's new `validate_project_loads()` first preserves the existing
one-load requirement for every selected input. It then requires the entire
normalized `LOAD` multiset inside the full helper/source checkout or diagnostic
workspace to equal exactly the selected direct-input population. The roots
cover source copies, build objects, temporary directories and retained output,
without leaving an evidence-directory escape.

Only compiler-support archive paths already admitted by the actual
compiler-resolution and archive checks are excluded from that comparison.
This preserves existing GNU map multiplicity for those verified support
archives and does not assume that they live under `/usr`. Other system inputs
outside the two roots retain their explicit provenance limitations.

The focused controls use the unchanged real map parser. They establish a
passing exact/relative-path baseline, then reject additional source, build,
temporary and output loads, relative duplicate objects, missing objects, and an
unverified compiler-support-looking path. A caller-supplied already-verified
compiler-support path can retain its repeated GNU `LOAD` entries. That last
unit boundary does not itself claim to verify a compiler archive.

## Finding 2 — post-marker intake failure was not retained

**F2; high confidence; actual diagnostic CLI reproduction.** Configuration
validation and `PacketReader` construction originally occurred after creation
of the exclusive execution marker but outside the retained `try/finally`.

On a separate synthetic intake fixture, the actual driver was invoked with a
changed recorder configuration. It exited 1 and printed the correct blocked
reason, `recorder configuration changed`. However, its retained report still
said `state="prepared"`, `outcome="not_run"`, `reason=null`, `failures=[]`, while
the attempt marker existed. No compilation occurred. The marker prevented
reuse, but the original failure was absent from the retained report.

The correction places post-marker initialization inside the retained failure
and finalization boundary. The first failure is saved before any secondary
stability/inventory failure. `outcome` becomes `fail` only when an outer child
was actually observed to start; an intake failure with zero commands remains
`blocked`. The exclusive marker and rejected-repeat behavior remain intact.

Two actual CLI controls use changed and absent configurations in separate
synthetic fixtures. They require `finished/blocked`, the original retained
reason, zero commands and records, a preserved first failure despite a later
stability failure, and a second invocation that rejects without changing the
first report. They cannot reach compiler execution.
