## Independently observed failure and correction

The sealed attempt03 evidence contains three passing compiler records and one
failing record for `s_shortShiftLeft128.c`. The failed record's real dependency
prepass started and exited zero; its final compiler tool did not start. Its
first reason is `dependency input inventory is empty, duplicated or oversized`.
The four record summaries and exact hashes are retained in the
[review receipt](../validation/w09_a06-repeated-inputs-review.json).

The original 1,130-byte GCC depfile has 24 prerequisite tokens and 23 distinct
normalized names. `../../source/include/primitiveTypes.h` appears twice. Its
SHA-256 is `db6caaf93bafa268d5c32322b87e005f8094957f10033bcb69ecdd5060bae7e8`.
The new self-contained regression embeds those exact bytes and parses them
without opening or resolving any recorded path. It does not depend on the
original workspace or pinned dependency repositories being present in CI.

Independent Git-source inspection confirmed that both `dependency_paths()` and
`_absolute()` were identical at published `5527cb06` and `8b71ee07`. The faulty
condition rejected repeated normalized prerequisites even though the recorded
compiler had successfully emitted them. A separate tiny GCC experiment also
produced the same pattern: a source includes `bridge.h`, which includes
`selected.h`, and then directly includes `selected.h`. This establishes a
self-contained actual-compiler regression without copying the full dependency
source or treating a fabricated successful compiler receipt as evidence.

The parent's change applies the unchanged maximum to the **raw prerequisite
token count before deduplication**, then records each normalized absolute name
once in first-seen order. The raw prepass and actual-compile depfiles remain
separately retained and hashed. Their reconstructed ordered unique inventories
must both equal the observed input inventory, whose before/after byte identities
must remain equal. Normalization remains lexical; distinct symlink spellings
are not collapsed by resolving the recorded filesystem.

The existing receipt reader still rejects duplicate input-identity rows.
Source/output graph identities, duplicate recorder invocation protection,
exact archive member order and uniqueness, generated-target inventories, and
link-map multiplicity checks are unchanged. The revised design text accurately
describes the narrow prerequisite-list semantics. This corrects acceptance of
valid compiler output; it does not turn repeated build operations or archive
members into equivalent evidence.

## New regression controls

| Control | Actual observation |
| --- | --- |
| Exact retained GCC depfile | Its original hash matches; 24 raw tokens produce 23 ordered unique inputs without filesystem access. |
| Raw token bound | Exactly `MAX_INPUTS` repetitions remain bounded; one additional raw token and an empty list reject before any deduplication could hide their count. |
| Real repeated-header compilation | Both actual GCC children exit zero; both raw depfiles retain the header twice; the stable observed inventory records it once. |
| Inert replay after cleanup | All producer directories are deleted before the successful record is verified; subprocess execution, file opening and path resolution are prohibited during that verification. |
| Rehashed depfile changes | Six cases add, remove or reorder inputs in either prepass or compile payload, repair the payload digest/size, and still reject on included-input closure. |
| Duplicate receipt rows | Duplicating the same row in both before and after inventories still rejects for duplicate input identities. |
| Real compile-time closure changes | Three cases change the actual source's include list between successful prepass and successful compiler execution; added, removed and reordered inputs all produce failed recorder results with `included-input set changed during compilation`. |

The final new module has six test methods; several methods contain multiple
positive and negative cases. Its actual-compiler fixture produces one successful
record and three intentional failed records per run. Those operations are tiny
host compiler controls, outside every managed native population. The raw-output
mutations are explicitly synthetic changes to actual retained compiler evidence.

The initial new-module run failed its inert checks because its test setup used
the recorder-only environment rather than the reader's required clean producer
environment. I changed only the new fixture to invoke compilation under
`builder.clean_environment`. The [initial log](../validation/w09_a06-repeated-inputs-initial.log)
is retained. No production check was relaxed to repair that setup.
