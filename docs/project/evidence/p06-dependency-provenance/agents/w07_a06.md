## Shared view and archive ownership

`p06_dependency_native_replay.verify_view` validates the revision and all three
report/snapshot pins before reading either supplied view. It checks the native
report pin before dependency semantics, calls the real dependency `verify_view`
itself, and rechecks the dependency report bytes before constructing its native
context. It does not accept a caller-provided dependency verification summary.

The shared function's documented contract deliberately leaves resource
ownership and hosted-envelope verification to its caller. Its two views and API
are trusted Python inputs, not a general external intake interface. The public
native and combined-control wrappers each instantiate exactly one
`ArchiveReader`, derive every selected view from that owner, check the hosted
envelope, and return only after the context manager exits. The combined reader
uses the already reconstructed native context for the two control joins; it
does not reopen the archive or run a second native replay.

The shared archive helper pins the original ZIP before parsing, checks the
canonical regular-file identity during reads, and hashes the whole original
again in `close()`. Its `finally` release closes both ZIP and file resources
even when the final check fails. Both wrappers build their receipt inside the
context but cannot return that success result before the close check succeeds.
Only the explicitly named local archive and trusted checkout inputs are live
paths. Producer paths are joined syntactically; selected retained members are
never extracted or executed.

The current limits remain 256 MiB original ZIP, 1 GiB expanded members,
20,000 members, 2 GiB cumulative reads and 100,000 read attempts. The dependency
cache adds its exact selected inventory and one-read-per-cache-entry behavior;
each control cache adds exact final membership and a packet-byte cap. These
are bounded consistency readers, not an unrestricted ZIP loading interface.
The actual hosted artifact has not been obtained, so fitting a real original
inside those reviewed bounds is still an original-intake obligation.

### Source-inventory completeness correction

A static traversal of top-level local Python imports, without importing those
modules, found complete closure for the dependency and native reader inventories
(53 and 57 Python module names respectively). The initial combined-control
inventory contained 60 names, but its transitive top-level imports also included
`p06_dependency_build`: `p06_dependency_substitution` imports it as `builder`.
It was absent from the combined reader's `_reader_sources()` additions.

The current inert path calls `substitution.recipes`, `derived_source`, and
`verify_observation`, and reconstructs tool records itself. It does not call
builder functions. The original builder source is also retained in the native
source inventory and is bound by the external native snapshot pin. Therefore
this review did not establish a retained-data admission bypass from the omitted
current-reader inventory entry. The precise limitation was that drift of this
already-imported current helper was not covered by the combined reader's
source-stability receipt.

The parent added `p06_dependency_build` to the trusted current helper list.
The repeated independent static analysis now finds **61 frozen Python module
names and 61 transitive top-level local imports, with no omission**. This change
checks the current builder module's origin and bytes without calling its build
functions or executing retained code.

With the parent's explicit authorization, this assignment added
`test_p06_dependency_control_trust_review.py`. One control substitutes an
existing wrong module-origin path and requires rejection before archive API
creation. The other independently hashes the actual current builder file,
