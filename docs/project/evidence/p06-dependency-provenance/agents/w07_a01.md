## Reproduced behavior

The prior child function called `Popen`, then populated the child row through
one `row.update(...)` expression that included `os.getpgid(process.pid)`.
Python evaluates those arguments before updating the dictionary. If the group
lookup raises after `Popen` has returned, the row therefore retains its initial
`process_started=false` and `pid=null`. The parent tool-stage flag also remains
false, and execution never reaches the existing child-finalization boundary.

The existing cleanup boundary also caught only `KeyboardInterrupt` from the
wait. An ordinary wait-monitoring `OSError` reached the outer failure handler
without stopping and reaping the already started child.

The focused test selects a hashed, executable tiny Python fixture as its test
archiver. Its input object is explicitly synthetic. The fixture writes a ready
marker and sleeps; it does not generate an archive or change process groups.
The two monitoring cases wait for that marker before observing the result.
Only the named monitoring call is instrumented to fail.

| Case | Instrumentation | Behavior before correction |
| --- | --- | --- |
| Group observation fails after launch | `os.getpgid` raises an `OSError` after the actual child reaches readiness | Both start flags remain false; recorded PID, group and child finish timestamp remain null; the actual child is alive when the recorder returns |
| First wait observation fails | The first `process.wait` raises an `OSError`; subsequent waits use the real method | Both start flags correctly remain true, but the actual child is still alive when the recorder returns |
| Process creation fails | At the launch boundary, the test removes the selected executable's execute permission; the real `Popen` attempt receives `PermissionError` from the OS | Both start flags remain false, with no recorded PID, group, exit code or output; the ready marker is absent |

The third case is a real OS execution refusal, not a mocked favorable return
from `Popen`. It is the passing control that prevents the correction from
marking every attempted creation as a successful start. The two monitoring
exceptions are injected, while child creation, readiness, running state and
cleanup are actual observations. Test cleanup always kills and reaps its own
remaining children, including when an assertion fails.

## Correction and independent review

The parent moved child creation and monitoring inside one retained cleanup
boundary. The independent read confirmed the following behavior:

- `process` begins as `None`, so a creation failure cannot imply an observed
  child or trigger operations on an absent process object.
- Immediately after `Popen` returns, the known PID and child start flag are
  recorded. The top-level selected-tool start flag changes only for the tool
  stage; dependency prepass observations retain their separate meaning.
- The known start is persisted before querying the process group. A failed
  group observation remains unknown (`null`) without erasing the known start.
- Group observation, group validation, receipt writes and waiting share the
  failure boundary. Ordinary errors and interruptions retain the first reason
  before any cleanup operation can fail.
- Cleanup acts only on the selected direct child. The existing two-second
  termination wait and two-second kill wait remain bounded, with secondary
  errors appended separately. It never signals the recorder's inherited group.
- Finalization records the observed child finish timestamp and exit status.
  A known creation failure keeps its PID and exit status absent. All failure
  paths remain unsuccessful.

The prior interruption-specific stage label is preserved. The ordinary
successful child path, immutable input checks, requested/actual arguments,
output freshness, receipt schema and resource limits retain their scope.
