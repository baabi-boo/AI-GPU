## Workflow authority, resource limits and failure retention

The new workflow has a single hosted `ubuntu-22.04` job and
`permissions: contents: read`. Checkout does not persist credentials. There is
no self-hosted runner, elevated token permission or configured secret. The
cache action restores the pinned toolchain only; it neither saves caches nor
restores dependency-library products.

The job retains a 90-minute limit, two build jobs, one simulator, disabled
compiler caches, explicit Python 3.12.14 provisioning/verification, and bounded
native execution. It records workflow/job identity before resource admission
and requires 15 GiB disk plus 4 GiB memory. Prepare, fresh dependency build,
caller receipt pinning, managed native execution and pending probe are
sequential. Shell stages use `set -euo pipefail`; no stage masks a failed build
or substitutes a successful fixture for native execution.

The added substitution step follows the successful managed population and
pending probe. It uses the already admitted FP16 build, managed report,
dependency receipt and caller pin, while writing to a separate control
directory. Its extra 33 launches are explicitly outside the managed population
of 132. The control cannot replace the original population's evidence or grow
its denominator.

missing artifact and retains the artifact for 30 days. The governance-workflow
diff only adds the new workflow/design paths to push and pull-request triggers;
existing governance checks are retained. The dependency ZIP reader explicitly
reports native execution as not run and preserves its narrow consistency-only
scope. Retained commands and helper payloads are not execution authority.
