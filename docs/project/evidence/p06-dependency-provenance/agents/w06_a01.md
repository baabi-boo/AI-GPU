## Reproduced finding

The recorder originally handled a `KeyboardInterrupt` from `process.wait()`
by calling `process.terminate()`, waiting up to two seconds, and then
re-raising the interruption. A termination error or a timeout in that cleanup
escaped before the re-raise. The outer failure accumulator therefore received
the cleanup error as its first failure, losing the original interruption.

The independent reproduction selected a hashed, executable, tiny Python
archiver fixture. It reached a readiness marker, ignored `SIGTERM`, and slept.
Its archive input was explicitly synthetic and no successful compilation or
archive claim was made. Only the first wait was instrumented to raise
`KeyboardInterrupt("review interruption")`. Two cases exercised the actual
recorder path:

| Case | Additional injection | Observed original behavior |
| --- | --- | --- |
| Child ignores termination | None; the two-second wait really timed out | The timeout became the sole failure reason; the child remained live after the recorder returned |
| Termination monitoring fails | `process.terminate()` raises `OSError("termination monitor failed")` | The termination error replaced the interruption; the child remained live |

The test always killed and reaped its own remaining child in `finally`, so the
reproduction did not leave a process behind. Both original assertions failed
at the intended first-reason check:

```text
PYTHONPATH=ci/project python3 -B -m unittest -v \
  test_p06_dependency_execution_review

Ran 1 test in 2.113s
FAILED (failures=2)
```

This was a failure-evidence defect, not a passing-build bypass. The original
record still reported failure. In the formal producer, the enclosing bounded
supervisor also owns the process group and remains responsible for descendant
cleanup. Those facts do not repair the recorder's lost initial reason.

## Correction and independent read

The parent's patch records the interruption before attempting cleanup. It then
tries direct-child termination and a bounded wait, followed by direct-child
kill and another bounded wait when necessary. Each signal/wait exception is
appended as a secondary failure. The original interruption is re-raised after
cleanup, and the normal finalization records the actual observed exit code and
finished timestamp.

The independent diff review confirmed:

- The first reason is captured before any cleanup operation can fail.
- Each wait remains bounded to two seconds; the enclosing command budget and
  resource supervisor are unchanged.
- Cleanup uses the selected child's process methods. It does not signal the
  recorder's inherited process group, which also contains its supervising
  build process.
- A failed cleanup cannot turn the outcome into a pass. If all cleanup attempts
  fail, the failure remains explicit and the outer supervisor still supplies
  its independent cleanup result.
- The ordinary successful child path, requested/actual arguments, output
  freshness checks, record schema and immutable-source checks are unchanged.

The parent ran the new regression on the settled production patch:

```text
Ran 1 test in 4.081s
OK
```

That is one test with two actual child cases, no skips. It requires the original
reason first, the actual cleanup error retained separately, failure status,
recorded process start/group, a reaped negative child exit matching the record,
and no successful output. The initial interruption and the second case's
termination error are explicit fault injection; the child execution,
termination timeout and final reaping are actual observations. The parent owns
this post-correction run; this assignment did not duplicate it.

## Other reviewed execution boundaries

The recorder claims an exclusive receipt before launch and rejects pre-existing
outputs, unsupported input-expansion flags, uncontrolled compiler input
environment and a changed selected executable. Each successful compile requires
both the actual dependency-prepass child and actual compile child. Its
`process_started` field describes the selected output-producing tool; a
prepass-only failure retains its separate child observation and cannot become
a successful compile.

The compile prepass uses `-M`; the actual compile uses `-MD`, preserving system
include observations such as `-isystem` headers. The source is observed across
the prepass, complete included inputs are retained before and after compilation,
and both dependency files must describe the same input sequence. The complete
receipt reader separately joins owned input bytes to the locked Git source
manifest. These checks do not purport to defeat malicious concurrent writers
or qualify the entire host compiler/system closure.

The pure receipt reader requires observed child starts, integer zero exits,
valid PIDs and process-group identities, ordered child intervals, exact child
arguments and nonempty fresh outputs. Successful-looking text cannot replace
those records. Consistent retained records still establish consistency rather
than producer authentication.

The builder's outer commands require actual start, passing result, exact zero
exit, no failure reason and completed process-group cleanup. Every recorded
tool operation must also pass before the next phase. The source manifest,
selected tools, helper bytes and staged inputs are checked at the prescribed
boundaries. The builder's failure accumulator keeps the initial reason while
appending final-stability or retention errors and clearing its formal success
flag.

Archive creation consumes the exact completed compiler outputs in the selected
order. Indexing joins its before-image to the creator and its after-image to
the final archive. Link prerequisites must finish before the link starts, and
their object/archive/product descriptors join the retained bytes. The review
did not replace these relationships with a printed aggregate count.

Preparation requires clean selected source/gitlinks, fresh destinations, the
matching restored toolchain cache identity and passing supervised acquisition
commands. It retains the first failed command and stops acquisition. The
alternate-library producer marks native execution unknown before an uncertain
launch; a supervisor exception cannot turn that state into a known non-run.
Its first failure is retained across later stability or retention failures.
