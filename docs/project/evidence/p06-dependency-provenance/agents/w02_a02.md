# W02-A02 — observed dependency tool-child recorder

## Implemented scope

Implemented `ci/project/p06_dependency_record.py` and its focused test module.
The new recorder is independent of the historical preflight and lifetime entry
points. No existing implementation file, contract, phase gate, golden data or
historical evidence was edited by this assignment. No commit or push was made.

The caller supplies a digest-pinned exact-schema configuration with canonical,
disjoint `sources`, `build`, `receipts` and `payloads` roots and the selected
`gcc`, `g++`, `ar` and `ranlib` identities. Configuration bytes and the selected
tool identity are rechecked through finalization. The recorder calls the actual
selected executable with an argument list, never through a shell, and leaves its
child in the inherited supervisor process group.

Each output/role has one exclusively claimed receipt. It retains started and
finished state, actual child PID/group, invocation, exit and monotonic timestamps.
It rejects replacing an earlier invocation. Independent compiler invocations can
finish in either order; their receipts and shared content-addressed payloads are
protected with bounded file locks. `.records.lock` and `.retention.lock` are
bookkeeping outputs, not source inputs or executable evidence.

The `compile` role requires one selected source/object pair. It first invokes the
same compiler in dependency-only mode, hashes and retains the observed included
inputs, then performs the real compilation with full `-MD` dependency output.
The resulting include set and all included bytes must match their pre-compilation
observations. This covers headers reached through `-isystem` and records system
headers actually reported by the compiler. The source is additionally checked
around the preliminary dependency observation.

The `archive` role admits only ordinary fresh archive creation, the `index` role
observes the existing archive before and after `ranlib`, and the `link` role
requires a fresh shared-library output and explicit fresh linker map. Direct
objects, archives and libraries selected from explicit `-L` roots are recorded
before and after the link. Outputs, maps, dependency files and observed inputs
are retained as inert bytes with exact identities. A nonpassing child stays
nonpassing even when it leaves output bytes, which are retained where possible.

## Integration API

```text
python3 p06_dependency_record.py
  --config CONFIG --config-sha256 SHA256
  --tool gcc|g++|ar|ranlib --role compile|link|archive|index
  [--compiler-launcher] -- ARGUMENTS...
```

The CMake compiler/linker-launcher option validates and removes the appended
compiler token; the receipt's actual child argv includes that selected compiler.
Python callers can use `run(...)`, `file_identity(...)`, `invocation(...)`,
`dependency_paths(...)` and `without_dependency_flags(...)`.

Configuration fields are exactly `schema_version`, `contract_id`,
`contract_sha256`, `roots` and `tools`. The recorder contract identifier is
`p06-dependency-tool-recorder-v1`; its parent contract digest is the current
`p06_dependency_contract.contract_hash()`. Each tool identity has `path`,
`resolved_path`, `sha256` and `size_bytes` fields.

Retained file descriptors additionally have a `payload` basename, relative to
the configured payload root. The receipt field `output_absent_before` records
freshness explicitly. `output_before` is null for fresh outputs and identifies
the pre-existing archive for indexing; a pre-existing compile/archive/link
product is retained and rejected. Dependency prepass and primary tool children
are separate entries in `children`, without turning preprocessing into an
additional translation unit.

The exact real compile projection is:

```text
without_dependency_flags(requested_arguments)
  + [-MD, -MF, selected_depfile, -MT, absolute_object]
```

Only `-MD`, `-MMD`, `-MP`, and the `-MF`/`-MT`/`-MQ` operand pairs are removed.
All semantic options remain. The original `-MF` destination is preserved when
present. This projection is necessary because GCC accumulates repeated `-MT`
targets instead of replacing the first one. The dependency prepass also removes
the compile/output controls and writes `<object>.p06-before.d`.

Compiler-input environment variables are rejected even when present with an
empty value: an empty `GCC_EXEC_PREFIX` changes GCC's support-file lookup and is
not equivalent to omitting it. A clean builder environment must omit these keys.

## Verification actually executed

Executed from the source root with CPython 3.12.14:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s ci/project -p 'test_p06_dependency_record.py' -v
git diff --check
```

**22 tests passed in 0.699 seconds**, exit 0. The source diff check also exited 0.
The tests run actual small GCC preprocessing/compilation children, `ar`,
`ranlib`, and a shared-library link with a real map. They also exercise the CLI
and two simultaneous compiler invocations. This is host recorder validation,
not execution of the full dependency graph or the GPU workload.

Meaningful rejecting controls cover stale objects/depfiles/maps, wrong config or
tool identity, duplicate invocation replacement, symlink source/output paths,
external outputs, response files and unsupported input expansion, compiler-input
environment injection, echo-only success with absent products, a header changed
after the prepass, malformed dependency syntax, unsupported thin archives and
wrong tool-role selection. An actual compiler failure remains the original
reason when a later config-stability check also fails.

The first local run exposed empty `GCC_EXEC_PREFIX` in the test environment;
those were failed tests, not native evidence. The second run exposed GCC's
repeated-target `-MT` semantics. Both issues were repaired before the final
passing run described above.

## Scope limits and handoff

The parent must retain and independently validate the complete graph, enforce
the expected source/recipe inventory, apply the bounded outer process supervisor
and join these records to archive members, selected linker-map inputs and loaded
products. This recorder alone cannot authenticate a producer or reject an entire
coherently forged packet. It observes the selected compiler driver performing a
link, not each compiler-internal subprocess. Compiler support files, every system
library and malicious concurrent filesystem writers remain outside the claimed
closure.

No full dependency build, managed native process, complete governance suite,
qualification, warm benchmark or phase acceptance was executed by this assignment.
Independent review and integration remain necessary.
