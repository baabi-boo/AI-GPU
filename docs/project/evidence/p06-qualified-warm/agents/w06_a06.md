## Recovery alternatives and limits

1. **Current-task duplicate validation files are negligible.** Byte-for-byte
   comparison identified 110,563 logical bytes
   (126,976 allocated bytes) duplicated in retained
   repository evidence. The 1,467,287-byte uncompressed historical replay also
   exactly matches its retained gzip after decompression. Those duplicates could
   be removed by the coordinator after retention review, but the combined
   recovery is below two megabytes and cannot resolve either blocker. All files
   remain present.
2. **Generated caller probe binaries total 381,728 bytes.** They belong to this
   task and are reproducible from retained source/commands, but retaining or
   removing them has no material resource effect. They remain present.
3. **A properly recreated Git worktree could share the main object store.** The
   current clean clone's main objects occupy 161,263,616 allocated bytes; its
   submodule metadata occupies another 17,809,408 bytes and still needs separate
   provision. Sharing the main objects could at most recover the former amount
   before metadata overhead. On this snapshot it would leave only
   **47,824,896 bytes** above the reserve after the preceding workspace's
   allocation, before all warm growth and transients. It would not recover the
   missing RAM. No alternate object file, repack, clone replacement or worktree
   conversion was attempted; the previously verified source remains intact.
4. **Discarding the fresh source would require recreating it before native
   execution.** That is therefore not net native capacity provision. It would
   also discard a verified clean checkout useful for the upcoming independent
   governance run. No such action was taken.
5. **Previous extracted tools are not current-task disposable files.** The
   previous `tools/` tree contains approximately 1.87 GB of logical data, mostly
   the 1,429,869,084-byte RISC-V toolchain and 432,215,417-byte LLVM directory.
   Its extracted/reproducible nature alone does not establish that no prior
   workflow still needs those paths or authorize deletion. This audit does not
   nominate it for automatic cleanup. It also would not resolve the independently
   observed RAM shortfall by itself.

No capacity gain here is sufficient to justify launch under the unchanged
resource contract. The coordinator can run the independent governance work in
its separately reviewed order, then remeasure capacity. A later native attempt
needs enough actual RAM and peak disk headroom, rather than revised thresholds
or optimistic allocation estimates.
