## Producer checks and temporal order

| Boundary | Actual checks and consequence |
| --- | --- |
| Live qualification construction | `p06_qualified_warm_admission.Admission.__init__` requires the complete live dependency admission, the selected revision/source relationship and a successful fresh dependency receipt. It verifies the extended proof, original proof, exact original diagnostic/control archive identities, all current measurement sources, helper/reference inputs and both complete historical prerequisite replays. It calls `verify_stable()` before returning. |
| Admission stability | `Admission.verify_stable` rehashes the selected extended proof, both original prerequisite archive paths, all measurement sources, the trusted helper closure and fixed prerequisite input files in both the execution source and trusted implementation checkout. It also invokes the live dependency admission's stability check. |
| Before every recorded child command | The shared producer's nested `command()` first calls `stable("before-command-" + name)`. That checks loaded helper bytes, the source snapshot, selected tools/interpreter, dependency payloads, complete dependency admission, existing model links and qualified admission. This applies to version/configuration/build commands as well as all native processes. |
| Before and after each native process | Frozen build artifacts are rehashed on both sides of the command. The raw output and duration must validate, then `stable("after-process-" + id)` must pass before the process outcome becomes `pass`. A last-process source/tool failure therefore cannot be concealed by already complete launch totals. |
| After a format and at finalization | The producer verifies format artifacts and the post-variant stability observation. Its `finally` block observes source/tools/dependencies again, rehashes all final frozen artifacts, verifies both admissions, checks original logs and retained evidence, and checks the final disk reserve. Errors enter the failure path. Qualification is derived only after these final checks and exact completion counts. |

The main anchors are `p06_managed_preflight_execute.execute` and its nested
`stable`/`command` functions; `p06_qualified_warm_admission.Admission`; and the
historical `_identity` helper reused by that admission. `_identity` requires
canonical paths without symlink components, a bounded regular file with one
link, and `O_NOFOLLOW`; it compares descriptor/path device, inode, size,
timestamps and link count while hashing. The returned persistent identity is
path, byte digest and size. This is a byte-stability contract, not a promise
that a byte-identical file can never be replaced between observations.

## Reader checks and exact scope

The new public reader chooses `_QualifiedWarmReplay` from trusted code. Its
process plan, source proof pin, expected 57 commands and 24-process population
are fixed by the selected route. Packet fields do not select a permissive
reader, proof or historical shortcut.

`verify_view` checks the trusted reader input closure before reading the
externally pinned native report and fully reconstructing dependency evidence.
The route's `validate_route_provenance` then checks the retained proof against
the fixed extended pin and retained source bytes, verifies the current source
projection, and calls both original prerequisite validators with the unchanged
original proof. It reconstructs the admission summary rather than accepting
the supplied summary. The historical projection remains nested under
`historical_prerequisites`; it is not relabeled as the current caller projection.

The shared `_NativeReplay.run` reconstructs the complete source/build/load,
raw-process and lifetime relationships, checks every required stability record
in exact order and chronology, and requires exact bound member inventories.
Only after that return does `verify_view` check the trusted closure again and
call analysis; it checks the closure once more after analysis. Public
`replay_archive` keeps the main candidate ZIP open through that work and verifies
the trusted closure again after the archive context exits.

The fixed archive reader's `close()` calls `_verify_original()`, which checks
file/path stability and rehashes the complete ZIP against the external intake
pin before releasing it. This applies to the main candidate and independently
to each prerequisite reader's archive context.

**Temporal distinction:** the historical diagnostic and control archives are
verified through their respective prerequisite reader closes. They are not
held open or rehashed again after the later warm analysis. Those already
verified semantic results describe the consumed, pinned original bytes. The
checks after warm reconstruction/analysis concern the trusted reader and fixed
proof/reference-input closure. They should not be described as continuous
custody of every prerequisite pathname for the duration of the whole warm
reader call. No existing documentation reviewed here makes that stronger claim.

## Guarantees that are not established

Persistent byte drift present at a required observation rejects. The checks do
not provide a filesystem lock over all compilation/execution inputs or exclude
a malicious writer that changes and restores bytes between observations.
Hashing trusted files also does not attest to arbitrary in-memory monkeypatching
of a trusted Python process. Those are trust-environment limitations, not
properties supplied by content hashing.

The selected graph does not establish complete provenance for system headers,
compiler support files, all loaded system libraries, the operating system or
an arbitrary untrusted producer. A coherent retained packet can establish
consistency with independently selected pins without authenticating its claimed
execution origin or independently proving Git membership.

These boundaries are consistent with:

- The new contract's `LIMITATIONS`, which explicitly excludes malicious
  concurrent writers and complete host provenance.
- The dependency admission's existing limitations on system headers/support
  files and authentication of untrusted producers.
- The design document's qualified boundary observations and retained-consistency
  interpretation.
- The runbook's requirement for independently selected external hashes, separate
  acquisition evidence for the host installation, and explicit statement that
  replay cannot authenticate an untrusted producer or establish Git membership.
- The public reader's `native_execution="not_run"`,
  `retained_code_executed=false` and `origin_authenticated=false` results.

The README remains an implementation checkpoint and makes no native warm,
performance or phase claim. This review neither changes the current native
resource blocker nor supplies a new qualification result.
